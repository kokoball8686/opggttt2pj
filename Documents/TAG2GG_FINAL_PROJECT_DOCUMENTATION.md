## 1. 이 문서의 목적

이 문서는 단순한 사용 설명서가 아니라, 프로젝트를 처음부터 마지막 배포 단계까지 다시 이해할 수 있도록 작성한 기술 백업이다. 다음 내용을 한곳에 모은다.

1. 프로젝트가 왜 시작되었는지
2. RPCS3 프로세스 메모리에서 어떤 값을 읽는지
3. 경기 시작·진행·종료를 어떤 상태 머신으로 판정하는지
4. Supabase에 어떤 데이터가 저장되는지
5. 웹사이트가 데이터를 어떻게 가져와 통계로 변환하는지
6. 데스크톱·모바일·PWA 화면이 어떻게 구성되었는지

8. 개발 중 발생한 문제와 해결 과정
9. 현재 구현된 것, 구현되지 않은 것, 운영상 주의할 점
10. 개인정보·백신·코드 서명·보안에 대한 최종 판단

이 문서는 현재 `C:\1`에 남아 있는 파일과 작업 백업 기록을 기준으로 작성했다. 이미지, PDF, PyInstaller 임시 산출물처럼 사람이 직접 읽는 소스가 아닌 바이너리 파일은 내용 전체를 텍스트로 옮기는 대신 종류·용도·수량·생성 결과를 기록한다.

## 2. 프로젝트 한 문장 요약

사용자의 PC에서 실행되는 `TAG2GGTracker.exe`가 RPCS3의 경기 관련 메모리를 읽고, 온라인 경기만 골라 닉네임·점수·캐릭터 조합·시작/종료 시간을 Supabase에 업로드한다. `TAG2.GG` 웹사이트는 Supabase에서 경기 행을 조회하고, 브라우저 JavaScript로 TOP 10·프로필·픽률·태그 조합·상대 전적·최근 경기 등의 통계를 계산해 표시한다.

구조를 단순화하면 다음과 같다.

```text
RPCS3 + Tekken Tag Tournament 2
            │
            │ Win32 ReadProcessMemory
            ▼
      TAG2GG Tracker
      (Python / EXE)
            │ HTTPS REST POST
            ▼
      Supabase PostgreSQL
            │ HTTPS REST GET
            ▼
       TAG2.GG 웹사이트
     (Netlify 정적 호스팅)
            │
            ▼
       브라우저 통계 화면
```

Supabase가 데이터 저장과 REST API를 담당하는 백엔드이고, Netlify는 HTML/CSS/JavaScript와 이미지 파일을 전달하는 정적 호스팅이다. 웹사이트 자체에는 별도의 Python·Node 서버가 없다.

## 4. 개발 목표와 초기 설계

처음 목표는 다음과 같았다.

- RPCS3에서 Tekken Tag Tournament 2를 플레이할 때 경기 결과를 자동으로 기록한다.
- 사용자가 경기 후 수동으로 닉네임·점수·캐릭터를 입력하지 않는다.
- 여러 사람이 같은 경기를 보고 있을 때 동일 경기가 여러 번 저장되는 문제를 줄인다.
- 저장된 데이터를 OP.GG와 비슷한 전적 사이트로 보여준다.
- 사용자는 회원가입·로그인·닉네임 입력 없이 EXE를 실행하기만 하면 된다.
- 웹은 PC와 모바일 모두 사용할 수 있어야 한다.
- Android에서는 웹사이트를 홈 화면 앱처럼 설치할 수 있어야 한다.
- Python을 설치하지 않은 사용자도 단일 EXE를 실행할 수 있어야 한다.

초기 구현 계획에는 계급/랭크까지 수집하는 목표도 포함되어 있었지만, 메모리 조사와 경기 시작·종료 판정 안정화가 더 중요했기 때문에 최종 버전에는 계급 시스템이 들어가지 않았다.

## 5. RPCS3 메모리 추적 기술

### 5.1 왜 절대 주소를 그대로 쓰면 안 되는가

처음에는 특정 컴퓨터에서 보이는 `0x3...` 대역의 절대 주소를 기준으로 메모리를 읽었다. 그러나 다른 PC에서 실행하거나 RPCS3를 재시작하면 운영체제가 프로세스 메모리 영역을 다르게 배치할 수 있다. 그러면 같은 절대 주소가 더 이상 같은 게임 데이터를 가리키지 않는다.

이 문제를 해결하기 위해 다음 형태로 변경했다.

```text
실제 주소 = RPCS3 게스트 RAM base 주소 + 검증된 상대 오프셋
```

즉, 특정 PC의 고정 주소에 의존하는 대신 실행 중인 RPCS3 프로세스에서 게스트 RAM 매핑의 기준점을 확인하고, 게임 빌드에서 확인한 상대 오프셋을 더한다. 이 변경으로 RPCS3 재시작과 다른 PC에서의 실행 가능성이 크게 좋아졌다.

### 5.2 현재 주요 오프셋

`tracker.py`에 현재 기록된 주요 값은 다음과 같다.

| 항목 | 오프셋/계산식 | 형태 | 용도 |
|---|---|---|---|
| 기준 RAM base | 동적으로 찾음, 참고값 `0x300000000` | 프로세스 주소 | 모든 상대 주소의 기준 |
| 1P 닉네임(1P로 실행 중인 레이아웃) | `ram_base + 0x167D118` | 최대 32바이트 문자열 | P1 닉네임 |
| 2P 닉네임(1P로 실행 중인 레이아웃) | `ram_base + 0x167F3B8` | 최대 32바이트 문자열 | P2 닉네임 |
| 1P 닉네임(2P로 실행 중인 레이아웃) | `ram_base + 0x167D140` | 최대 32바이트 문자열 | P1 닉네임 |
| 2P 닉네임(2P로 실행 중인 레이아웃) | `ram_base + 0x167F390` | 최대 32바이트 문자열 | P2 닉네임 |
| 전투 구조체 포인터 | `ram_base + 0x100D2ABC` | 4바이트 Big-Endian | 점수·캐릭터 구조체 위치 |
| 대전 상태 플래그 | `ram_base + 0x168172F` | 1바이트 | 값이 1일 때 유효한 대전 상태 |
| 오프라인 플래그 | `ram_base + 0x193190C` | 1바이트 | 값이 1이면 기록하지 않음 |
| P1 라운드 승수 | `battle_base + 0xB` | 1바이트 | 0~3 |
| P2 라운드 승수 | `battle_base + 0xB + 0xD4` | 1바이트 | 0~3 |
| P1 메인 캐릭터 | `battle_base + 0x1B3` | 4바이트 little-endian ID | 캐릭터 조합 |
| P2 메인 캐릭터 | `battle_base + 0x1B7` | 4바이트 little-endian ID | 캐릭터 조합 |
| P1 서브 캐릭터 | `battle_base + 0x1BB` | 4바이트 little-endian ID | 캐릭터 조합 |
| P2 서브 캐릭터 | `battle_base + 0x1BF` | 4바이트 little-endian ID | 캐릭터 조합 |

메모리 오프셋은 RPCS3와 게임 빌드에 종속된다. 따라서 RPCS3 또는 게임 버전이 바뀌면 “프로그램이 영원히 보장된다”고 볼 수 없고, 실제 경기로 다시 검증해야 한다.

### 5.3 Win32 API 사용

Python의 `ctypes`로 Windows `kernel32` API를 호출한다.

- `OpenProcess`: `PROCESS_VM_READ | PROCESS_QUERY_INFORMATION` 권한으로 RPCS3 핸들 획득
- `ReadProcessMemory`: 특정 주소에서 바이트 읽기
- `CloseHandle`: 프로세스 핸들 정리용 API 정의
- `tasklist`: `rpcs3.exe`의 PID 탐지

이 때문에 트래커는 Windows 전용이다. macOS나 Linux에서는 현재 코드 그대로 실행되지 않는다.

### 5.4 문자열·포인터·캐릭터 읽기

- 닉네임은 최대 32바이트를 읽고 null byte 뒤를 버린다.
- UTF-8 문자열로 디코드하며 잘못된 바이트는 무시한다.
- 전투 포인터는 Big-Endian 정수로 읽고, 0이면 유효하지 않은 전투로 취급한다.
- 캐릭터 ID는 4바이트 little-endian 정수로 읽는다.
- ID는 트래커의 영문 캐릭터 이름 사전과 웹의 한국어 캐릭터 이름 사전으로 표시한다.
- 알 수 없는 ID는 `Unknown ID (숫자)` 또는 `ID 숫자`로 표시한다.

현재 캐릭터 사전은 58개 ID를 지원한다. Paul, King, Jin, Kazuya, Lili, Lars, Alisa, Ganryu 등 기본 캐릭터와 DLC/특수 캐릭터가 포함되어 있다.

## 6. 경기 감지 상태 머신

### 6.1 프로세스 연결

1. 프로그램이 시작되면 `rpcs3.exe`를 찾는다.
2. 찾지 못하면 약 2초 간격으로 계속 기다린다.
3. PID를 찾으면 RPCS3 프로세스에 읽기 핸들을 연다.
4. 연결이 끊기거나 읽기 실패가 발생하면 연결 상태를 초기화하고 다시 탐지한다.

### 6.2 폴링 주기

유효한 상태를 약 0.3초마다 읽는다. 대전 후보가 발견된 뒤 약 2초 동안 상태가 유지되어야 실제 대전으로 확정한다. 이 지연은 캐릭터 선택 화면이나 이전 대전의 메모리 잔상이 새 경기로 잘못 인식되는 것을 줄이기 위한 것이다.

### 6.3 유효한 대전 조건

`poll_state()`는 다음 조건을 모두 확인한다.

1. 두 닉네임이 모두 비어 있지 않다.
2. 대전 상태 플래그가 1이다.
3. 전투 구조체 포인터가 유효하다.
4. 두 점수를 읽을 수 있다.
5. 네 개의 캐릭터 ID를 읽을 수 있다.
6. 두 점수가 3보다 크지 않다.

조건을 만족하지 못하면 `None`을 반환한다.

### 6.4 시작 판정

- P1/P2 점수가 0:0인 유효 상태가 관찰된다.
- 그 상태가 약 2초 유지된다.
- 오프라인 플래그를 다시 검사한다.
- 오프라인이면 `[OFFLINE MATCH IGNORED]`를 출력하고 저장하지 않는다.
- 온라인이면 `in_match=True`로 바꾸고 UTC 시작 시간을 기록한다.

### 6.5 진행 판정

점수가 바뀔 때마다 콘솔에 현재 스코어를 출력한다. 같은 점수를 반복해서 출력하지 않도록 마지막 점수를 보관한다.

### 6.6 종료 판정

P1 또는 P2의 라운드 승수가 3이 되면 경기 종료로 판단한다.

- `has_logged_match` 플래그로 한 경기의 중복 업로드를 막는다.
- UTC 종료 시각을 기록한다.
- 승자를 3승을 달성한 닉네임으로 결정한다.
- 캐릭터 조합과 경기 시간을 콘솔에 출력한다.
- Supabase REST API로 JSON을 POST한다.

### 6.7 로비 복귀와 잔상 방어

유효한 대전 상태가 약 5회 연속, 즉 약 1.5초 동안 사라지면 로비나 메뉴로 돌아온 것으로 간주한다. 그때 경기 상태, 점수, 시작 시간, 오프라인 무시 플래그를 초기화한다. 이 로직은 이전 경기의 닉네임과 포인터가 메모리에 남아 새 경기로 잘못 감지되는 문제를 줄이기 위해 추가되었다.

## 7. Supabase 백엔드와 데이터 모델

### 7.1 역할

Supabase는 이 프로젝트의 백엔드다. 다음을 담당한다.

- PostgreSQL 데이터베이스
- REST API
- 경기 행 저장
- 웹사이트의 경기 조회
- 트래커 로그 저장을 위한 별도 테이블(운영 설정에 따라 사용)
- 중복 경기 방지용 데이터베이스 로직

Netlify는 백엔드가 아니다. Netlify는 정적 웹 파일을 전달할 뿐이며, 실제 데이터는 Supabase에서 가져온다.

### 7.2 `public.matches` 주요 스키마

현재 트래커가 보내는 경기 payload는 다음 필드를 포함한다.

```text
id                         bigint identity primary key
p1_name                    text
p2_name                    text
p1_score                   smallint
p2_score                   smallint
p1_main_character_id      integer
p1_sub_character_id       integer
p2_main_character_id      integer
p2_sub_character_id       integer
winner                     text
start_time                 timestamptz
end_time                   timestamptz
created_at                 timestamptz default now()
```

초기 계획서에는 닉네임·점수·승자·시작/종료 시간 중심으로 기록되어 있었고, 개발 중 캐릭터 ID 네 개가 추가되었다. 그래서 현재 웹사이트는 단순 승패뿐 아니라 캐릭터 픽률과 태그 조합까지 계산할 수 있다.

### 7.3 업로드 방식

트래커는 다음 REST 엔드포인트에 POST한다.

```text
https://<supabase-project>.supabase.co/rest/v1/matches
```

요청에는 공개용 publishable key를 `apikey` 헤더로 넣고, JSON payload를 전송한다. 키는 비밀 관리자 키가 아니며 EXE와 웹사이트에 포함될 수 있는 공개 키다. 그렇다고 무제한 권한을 주어도 된다는 뜻은 아니다. Supabase 권한 정책을 실제 운영 권한에 맞게 설정해야 한다.

### 7.4 시간 처리

- 트래커의 `start_time`, `end_time`은 UTC 기준으로 만든다.
- 웹사이트가 화면에 표시할 때 `Asia/Seoul`(KST)로 변환한다.
- 최근 경기 정렬과 경기 번호 계산은 `created_at` 기준으로 정리되었다.
- 프로필의 경기 시간과 총 플레이 시간은 `start_time`과 `end_time`의 차이로 계산한다.

### 7.5 중복 업로드 문제

같은 경기를 양쪽 플레이어의 트래커가 동시에 읽으면 동일한 경기가 두 번 저장될 수 있었다. 이 문제는 Python 트래커를 계속 복잡하게 만드는 대신 Supabase 쪽에서 해결하는 방향으로 정리했다.

작업 기록에는 동일한 경기의 선수·점수·시간을 기준으로 약 30초 시간 창에서 중복을 합치는 로직과, 동시 요청을 직렬화하기 위한 PostgreSQL advisory lock 기반 처리가 기록되어 있다. 이 구조의 핵심은 여러 클라이언트가 동시에 POST해도 DB가 같은 경기를 하나로 취급하도록 하는 것이다.

중복 방지는 데이터베이스의 실제 trigger/function/index 설정에 의존하므로, 새 Supabase 프로젝트로 이전할 때는 해당 SQL을 함께 백업해야 한다.

### 7.6 RLS와 운영 보안

현재 작업 기록상 개발 편의를 위해 RLS(Row Level Security)가 꺼져 있는 상태로 이해된다. 이것은 테스트에는 편하지만 공개 배포에는 위험하다.

- 브라우저와 EXE에 공개 키가 들어 있다.
- 공개 키는 사용자 PC에서 추출할 수 있다.
- RLS가 꺼져 있으면 의도하지 않은 INSERT·UPDATE·DELETE가 허용될 수 있다.
- 사용자가 임의의 경기 기록을 넣거나 바꿀 가능성이 있다.

현재 데이터가 커뮤니티 통계용이고 신뢰를 우선한 선택이었다고 해도, 장기 운영에서는 최소한 다음을 검토해야 한다.

1. 공개 사용자는 필요한 작업만 가능하도록 RLS 정책 설정
2. `matches`에 불필요한 UPDATE/DELETE 제한
3. 관리자 키는 절대 EXE나 웹에 넣지 않기
4. 필요하면 트래커 업로드를 별도 Edge Function/API로 중계
5. 로그 테이블에는 호스트명·사용자명 같은 식별 정보가 필요 이상 저장되지 않도록 검토

## 8. 트래커 데이터와 개인정보 범위

트래커는 RPCS3 프로세스의 특정 메모리 위치만 읽는다. 현재 목적상 수집하는 정보는 다음과 같다.

- 게임 닉네임 두 개
- 승리 라운드 수 두 개
- 네 개의 캐릭터 ID
- 경기 시작 UTC 시각
- 경기 종료 UTC 시각
- 서버가 부여하는 `created_at`

현재 경기 업로드 코드가 직접 수집하지 않는 정보는 다음과 같다.

- 사용자의 문서·사진·다운로드 파일
- 브라우저 방문 기록
- 비밀번호
- 키보드 입력 전체
- 화면 캡처
- IP 주소를 별도 필드로 저장하는 로직

그러나 다른 프로세스의 메모리를 읽고 인터넷으로 전송하는 행동 자체는 민감하게 보일 수 있다. 따라서 배포 시 “무엇을 읽고, 무엇을 보내며, 무엇은 읽지 않는지”를 사용자에게 설명해야 한다.

또한 `test_log_sender.py`는 경기 데이터와 별개로 호스트명, Windows 버전, 사용자명 환경 변수 등을 `tracker_logs`에 보내는 테스트 코드다. 이것은 일반 경기 업로드와 범위가 다르므로, 실제 배포 EXE에 포함할지와 운영 로그에 저장할지를 반드시 구분해야 한다.

## 9. 웹사이트 구조

### 9.1 정적 단일 페이지 애플리케이션

`ttt2_web/index.html`이 사실상 전체 앱이다.

- HTML: 화면 구조
- CSS 파일: 데스크톱·태블릿·모바일 레이아웃
- 인라인 JavaScript: 라우팅, REST 조회, 집계, 렌더링, 이벤트 처리
- 별도 빌드 도구나 프론트엔드 프레임워크 없음
- Netlify에 폴더 그대로 배포 가능

해시 라우팅을 사용한다.

```text
#home
#players
#matches
#profile/<닉네임>
```

### 9.2 공통 화면

- 상단 고정 바
- TAG2.GG 브랜드
- 플레이어 닉네임 검색창과 자동완성
- 좌측 통계 메뉴
- LIVE DATA 표시
- 모바일에서는 햄버거 메뉴로 사이드바를 열고 닫음

### 9.3 홈 대시보드

홈은 Supabase에서 최신 경기 행을 받아 다음 항목을 표시한다.

- 전체 대전 수
- 등록 플레이어 수
- 캐릭터 픽률 TOP 6
- 고승률 태그 조합 TOP 6
- 이번 주 급상승 플레이어
- 최근 30일 일별 경기 수 SVG 라인 차트
- 최근 경기 목록

현재 대시보드 쿼리는 `created_at.desc`와 `limit=1000`을 사용한다. 따라서 대시보드는 한 번에 최대 1,000개의 경기 행을 브라우저로 가져와 집계한다. 이것은 Supabase 전체 데이터가 1,000개로 제한된다는 뜻이 아니라, 현재 프론트엔드 요청이 한 번에 읽는 양이 1,000개라는 뜻이다.

### 9.4 클라이언트/프론트엔드 계산

여기서 “클라이언트에서 계산한다”와 “프론트엔드에서 계산한다”는 같은 의미다. 사용자의 브라우저에서 실행되는 JavaScript가 Supabase 원본 경기 행을 받아 계산한다.

브라우저에서 계산하는 항목:

- 전체 경기 수
- 플레이어 수
- 캐릭터 선택 횟수와 픽률
- 태그 조합별 경기 수·승리 수·승률
- 최근 7일과 직전 7일의 승률 변화
- 최근 30일 일별 경기 수
- 플레이어 승률·승패·총 경기 시간·최근 접속
- 플레이어가 가장 많이 사용한 태그 조합
- 최근 상대 5명과 상대 전적
- 경기 번호·정렬·페이지네이션

이 구조는 통계를 추가하기 쉽고 서버를 별도로 만들 필요가 없다는 장점이 있다. 반대로 대시보드가 읽는 데이터가 많아지면 브라우저 처리량과 REST 응답 제한의 영향을 받는다.

### 9.5 캐릭터와 태그 조합

웹에는 numeric character ID를 한국어 이름과 이미지로 바꾸는 사전이 있다.

- 이미지 경로: `assets/characters/<id>.webp`
- 일반 태그 조합: 두 이미지를 나란히 표시
- 동일 캐릭터/동일 캐릭터: 한 장만 표시하는 솔로 표시
- 누락된 ID: `ID 숫자` 표시

고승률 태그 조합은 최소 10경기 이상인 조합만 후보로 삼는다. 경기 수가 너무 적은 조합이 우연히 100% 승률로 TOP에 오르는 문제를 줄이기 위한 기준이다.

### 9.6 급상승 플레이어

UTC 달력 기준으로 다음 두 기간을 비교한다.

- 최근 7일
- 그 직전 7일

두 기간 모두 최소 10경기 이상인 플레이어만 후보로 만들고, 최근 승률에서 이전 승률을 뺀 증가폭이 가장 큰 플레이어를 표시한다. 최근 승률이 이전보다 높지 않으면 “아직 없다”고 표시한다.

### 9.7 TOP 10

플레이어 디렉터리는 경기 데이터를 기반으로 플레이어별 경기 수·승률·대표 태그 조합을 보여주는 영역이다. 초기 구현 과정에서 데스크톱에서는 닉네임·대표 캐릭터 이미지·기록을 넓게 배치했고, 모바일에서는 닉네임 줄임과 대표 조합을 다음 줄에 배치하도록 조정했다.

### 9.8 플레이어 프로필

프로필에는 다음 내용이 있다.

- 닉네임
- 승률
- 총 경기 수·승·패
- 총 플레이 시간
- 마지막 경기 시각
- 주력 태그 조합 TOP 3
- 최근 상대 5명
- 특정 상대 검색
- 경기 목록
- 경기 번호
- WIN/LOSS
- 점수
- 두 플레이어의 닉네임
- 캐릭터 이미지와 한국어 이름
- 경기 지속 시간
- 시작/종료 시각
- 정렬(최신·승리·패배)
- 페이지네이션

### 9.9 최근 경기 모바일 레이아웃

모바일 화면 폭이 좁아 닉네임과 캐릭터가 겹치는 문제가 여러 차례 발생했다. 최종 구조는 경기 행 안에서 다음처럼 보이도록 정리되었다.

```text
닉네임
캐릭터 이미지
캐릭터 이름
```

점수와 `vs`, 경기 시간도 별도 열로 유지하고, 360px 이하 화면에서는 글자와 이미지 크기를 추가로 줄인다. 모바일 최근 경기의 닉네임이 공간 부족으로 사라지던 문제는 2026-09-09 최종 수정에서 해결되었다.

### 11.3 Android 설치 안내서

`TAG2GG_PWA_설치_가이드.html`은 Android Chrome 기준으로 다음 6단계를 이미지와 함께 설명한다.

1. 단톡방 링크를 다른 브라우저로 열기
2. Chrome 선택
3. Chrome의 점 3개 메뉴 열기
4. 홈 화면에 추가

## 12. Windows GUI 런처와 EXE

### 12.1 런처 기능

`gui_launcher.py`는 Tkinter 창을 만든다.

- TAG2.GG Tracker 제목
- RPCS3를 먼저 실행하라는 안내

트래커의 콘솔 출력은 GUI EXE에서 보이지 않도록 `os.devnull`로 보낸다.

### 12.2 버전 확인

실행할 때 다음 GitHub API를 호출한다.

```text
https://api.github.com/repos/opggttt2pj/TAG2GG-Tracker/releases/latest
```

`tag_name`을 `vMAJOR.MINOR.PATCH` 형식으로 해석해 현재 EXE의 `VERSION`과 비교한다.

- 최신 Release가 현재 버전보다 높으면 실행 차단
- 최신 버전이 같거나 낮으면 트래커 실행
- GitHub 연결 실패 또는 응답 형식 오류면 실행 차단
- 업데이트 필요 시 Release 페이지를 열지 묻는 창 표시
- Draft Release는 `/releases/latest`에 포함되지 않음

이 설계는 오래된 EXE가 잘못된 오프셋이나 오래된 데이터 구조로 계속 동작하는 것을 막기 위한 것이다.

### 12.3 PyInstaller 설정

`TTT2TrackerGUI.spec`은 다음을 설정한다.

- 시작 스크립트: `gui_launcher.py`
- 포함 데이터: 192px·256px PNG, SVG 아이콘
- 출력 이름: `TAG2GGTracker`
- Windows 아이콘: `app-icon.ico`
- 버전 메타데이터: `version_info.txt`
- 콘솔 창 숨김
- `upx=True`
- 코드 서명 설정은 비어 있음

현재 EXE는 Python 런타임과 필요한 모듈을 묶어 사용자의 PC에 Python을 설치하지 않아도 실행되도록 만든다.

### 12.4 Windows 파일 메타데이터

`version_info.txt`의 최종 값:

- Product name: TAG2.GG Tracker
- Internal name: TAG2GGTracker
- Original filename: TAG2GGTracker.exe
- Product version: 0.1.0
- File version: 0.1.0.0
- Description: TAG2.GG online match tracker
- Author: legbreaker
- Copyright: 2026 legbreaker

이 정보는 코드 서명 인증서가 아니다. 단지 Windows 파일 속성에 표시되는 제품 정보다.

### 12.5 빌드 절차

`BUILD_EXE.md`에 기록된 일반 절차는 다음과 같다.

```powershell
cd C:\1\ttt2_tracker
python --version
python -m PyInstaller --clean --noconfirm C:\1\ttt2_tracker\TTT2TrackerGUI.spec
```

빌드 전에는 Python 문법 검사와 PyInstaller 설치 여부를 확인하고, 빌드 후 `C:\1\dist\TAG2GGTracker.exe`의 존재·버전·파일 크기를 확인한다. 최종 EXE는 GitHub Release asset으로 업로드한다.

### 12.6 코드 서명과 백신

현재 `TTT2TrackerGUI.spec`에는 `codesign_identity=None`으로 되어 있어 EXE에 Windows 코드 서명이 적용되어 있지 않다.

코드 서명은 웹사이트 SSL과 목적이 비슷하지만 대상이 다르다.

- SSL/TLS 인증서: 웹사이트와 서버 통신의 신원·암호화
- 코드 서명 인증서: EXE 제작자 신원과 서명 이후 파일 변조 여부

완전 무료이면서 모든 사용자 PC가 자동으로 신뢰하는 코드 서명 인증서는 사실상 없다. 자체 서명 인증서는 무료지만 사용자가 별도로 신뢰 루트에 설치해야 한다. 일반 배포에서는 유료 인증서나 조건부 오픈소스 지원 서비스를 검토해야 한다.

서명해도 새 프로그램의 SmartScreen 경고가 100% 사라지는 것은 아니다. 서명되지 않은 PyInstaller EXE가 다른 프로세스 메모리를 읽고 네트워크 통신을 하는 것은 백신의 휴리스틱 경고 대상이 될 수 있으므로, 배포 설명에 수집 범위와 소스/해시 검증 방법을 투명하게 적는 것이 중요하다.

## 15. 보안·신뢰·배포에 대한 최종 판단

### 15.1 EXE가 의심받을 수 있는 이유

다음 행동은 정상적인 트래커에도 필요하지만 악성 프로그램에서도 자주 보인다.

- 다른 프로세스의 메모리 읽기
- 외부 HTTPS 통신
- PyInstaller로 묶인 서명되지 않은 EXE
- 실행 시 GitHub에 연결
- 사용자의 입력 없이 백그라운드 실행

따라서 백신 경고가 발생할 가능성은 있다. 경고가 곧 악성 프로그램이라는 증거는 아니지만, 사용자 신뢰를 얻기 위해 다음을 제공해야 한다.

- 수집 데이터 목록
- 전송 목적과 Supabase 주소
- 수집하지 않는 데이터 목록
- 공개 소스 또는 코드 검토 방법
- 배포 파일 SHA-256 해시
- 최신 Release 링크
- 코드 서명 적용 여부

### 15.2 서버에 코드를 넣고 사용자 PC에 주입하는 방식

서버가 임의의 사용자 PC에 코드를 주입하는 방식은 안전하고 적절한 설계가 아니다. 서버가 RPCS3 메모리를 읽으려면 사용자의 PC에 동의받은 에이전트가 설치되어 있어야 한다. 현재 트래커 EXE가 바로 그 에이전트 역할을 한다.

Rust로 다시 작성한다고 문제가 자동으로 해결되지는 않는다. 핵심 문제는 언어가 아니라 다음이다.

- RPCS3 내부 데이터 접근
- 사설 서버가 어떤 데이터를 알고 있는지
- 서버 프로토콜을 수정할 수 있는지
- 클라이언트 동의와 인증
- 잘못된 조작·치팅·보안 문제 방지

사설 서버가 닉네임·점수·캐릭터·경기 종료 이벤트를 이미 모두 알고 API로 제공한다면 서버 통합을 검토할 수 있다. 그렇지 않으면 현재처럼 사용자 PC에서 읽는 별도 클라이언트가 필요하다.

### 15.3 역분석 가능성

PyInstaller EXE는 Python 런타임과 바이트코드를 포함하므로 완전한 비공개 소프트웨어가 아니다. 숙련자는 패키지를 추출하거나 문자열·모듈·일부 로직을 분석할 수 있다. 따라서 EXE 안에 관리자 키나 비밀 API 키를 넣으면 안 된다. 공개 키를 사용하고 DB 정책으로 권한을 제한해야 한다.

## 19. 최종 결론

이 프로젝트는 단순한 Python 스크립트에서 출발해 다음 구성요소를 가진 실제 서비스 형태로 완성되었다.

- RPCS3 메모리 기반 자동 경기 감지
- 다른 PC를 고려한 상대 오프셋 구조
- 온라인 경기 필터
- 닉네임·점수·캐릭터 조합 수집
- Supabase 중앙 데이터베이스
- 동시 업로드 중복 방지
- TAG2.GG 전적 웹사이트
- TOP 10, 프로필, 상대 전적, 픽률, 태그 조합, 급상승 플레이어 통계
- 데스크톱·모바일 반응형 레이아웃
- Android PWA 설치
- Windows GUI 런처
- PyInstaller 단일 EXE 배포
- GitHub Release 기반 구버전 실행 차단
- 설치 가이드 HTML/PDF
- 다른 PC 테스트와 단톡방 배포

아직 계급 시스템, 자동 재전송 큐, 코드 서명, 강한 Supabase 권한 정책은 남은 과제다. 하지만 핵심 목표였던 “RPCS3에서 실제 온라인 대전을 감지하고, 중앙 DB에 저장하고, 누구나 웹에서 전적을 확인하는 시스템”은 완성되었다.

이 문서는 현재 구현을 보존하기 위한 최종 기준점이다. 이후 수정이 발생하면 코드만 바꾸지 말고, 트래커 payload·Supabase 정책·프론트엔드 조회/집계·빌드 버전·배포 안내를 함께 갱신해야 한다.
