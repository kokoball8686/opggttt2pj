# 04. Supabase 백엔드 상세 문서

## 1. 백엔드의 의미

이 프로젝트에서 Supabase가 백엔드다. Netlify는 정적 파일 호스팅일 뿐이고, Supabase PostgreSQL과 REST API가 데이터 저장·조회 기능을 제공한다.

## 2. 경기 테이블

논리적 `public.matches` 모델은 다음과 같다.

```sql
id bigint generated by default as identity primary key
p1_name text not null
p2_name text not null
p1_score smallint not null
p2_score smallint not null
p1_main_character_id integer
p1_sub_character_id integer
p2_main_character_id integer
p2_sub_character_id integer
winner text
start_time timestamptz
end_time timestamptz
created_at timestamptz default now()
```

점수·닉네임·승자만 저장하던 초기 구상에서 캐릭터 ID 네 개가 확장되었다. 이 확장으로 웹에서 픽률과 태그 조합을 계산할 수 있게 되었다.

## 3. REST 쓰기

트래커는 `/rest/v1/matches`에 JSON POST를 한다. 헤더에는 공개 API 키와 `Content-Type: application/json`을 넣는다. 관리자 service-role 키는 클라이언트에 넣지 않는다.

## 4. REST 읽기

웹사이트는 필요한 필드만 `select`하고 `created_at.desc`로 정렬한다. 대시보드는 현재 `limit=1000`이며 프로필은 닉네임 검색 조건을 사용한다.

## 5. 중복 제거

두 플레이어가 같은 경기를 각각 추적하면 같은 경기의 POST가 두 번 발생할 수 있다. 이 문제는 Supabase에서 경기 식별값과 시간 창을 이용해 처리하는 방향으로 정리했다. 동시 요청이 같은 경기를 처리할 때 PostgreSQL advisory lock으로 직렬화하는 구조도 작업 기록에 남아 있다.

새 DB로 이전할 때는 테이블만 만들고 끝내면 안 된다. 다음을 함께 백업해야 한다.

- trigger/function
- 중복 판정 기준
- 인덱스
- advisory lock 처리
- 컬럼 타입
- REST 권한

## 6. RLS

Row Level Security가 꺼져 있으면 공개 키를 가진 사용자가 허용된 REST 작업을 넓게 수행할 수 있다. 현재 프로젝트가 커뮤니티 통계용으로 운영되더라도 다음 단계에서는 읽기와 쓰기 권한을 분리하는 것이 좋다.

- 웹 공개 사용자: 필요한 읽기만
- 트래커: 필요한 경기 INSERT만
- 관리자: 별도 인증을 거친 관리 작업
- UPDATE/DELETE: 일반 공개 사용자 차단

## 7. 로그 테이블

`test_log_sender.py`는 `tracker_logs`에 테스트 로그를 보낸다. 호스트명·Windows 사용자명·Windows 버전 같은 값은 경기 데이터와 성격이 다르므로, 실제 운영 시 수집 목적과 보관 기간을 명확히 해야 한다.

## 8. 백엔드 변경 체크리스트

컬럼을 추가하거나 이름을 바꾸면 다음 네 곳을 함께 확인한다.

1. 트래커 payload
2. Supabase 테이블과 정책
3. 프론트엔드 REST `select`
4. JavaScript 집계·렌더링

하나라도 빠지면 업로드 성공 후 화면에 값이 안 보이거나, REST 요청 자체가 실패할 수 있다.
