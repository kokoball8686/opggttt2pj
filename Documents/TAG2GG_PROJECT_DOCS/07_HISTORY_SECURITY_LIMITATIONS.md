# 07. 개발 연대기·보안·한계

## 1. 주요 개발 흐름

### 메모리 조사

처음에는 특정 PC의 절대 주소에 의존했지만, RPCS3 재시작과 다른 PC 배포를 고려해 게스트 RAM base + 상대 오프셋 방식으로 전환했다. 1P/2P 닉네임 주소, 전투 포인터, 점수 구조체, 대전 상태 플래그를 단계적으로 확인했다.

### 감지 안정화

2P 닉네임 누락, 닉네임 위치 반전, 캐릭터 선택 잔상, 연속 리벤지, 온라인/오프라인 구분 문제를 해결했다. 2초 안정화와 로비 복귀 초기화가 핵심 방어 로직이다.

### 웹 확장

캐릭터 조합, PWA, 그래프, 원형 차트, 프로필, 상대 전적, TOP 10, 급상승 플레이어, 모바일 레이아웃을 순서대로 추가했다.

### 배포

다른 PC 테스트 후 PyInstaller EXE를 만들고, GitHub Release의 최신 버전 확인과 구버전 실행 차단을 추가해 단톡방 배포용으로 정리했다.

## 2. 수집 데이터와 수집하지 않는 데이터

경기 업로드에는 닉네임, 점수, 캐릭터 ID, 시작·종료 시간이 들어간다. 현재 경기 코드가 문서·사진·브라우저 기록·비밀번호를 수집하는 것은 아니다. 다만 프로세스 메모리 읽기와 HTTPS 전송은 민감한 동작이므로 사용자에게 사전 고지해야 한다.

별도 `test_log_sender.py`는 호스트명·사용자명·Windows 버전을 로그 테스트 payload에 넣는다. 일반 경기 수집과 분리해 운영해야 한다.

## 3. 백신 오탐 가능성

서명되지 않은 PyInstaller EXE가 다른 프로세스 메모리를 읽고 네트워크 연결을 하므로 백신 휴리스틱에 걸릴 수 있다. 이를 숨기기보다 다음을 공개하는 편이 안전하다.

- 수집 필드
- Supabase 전송 목적
- 공개 소스 또는 코드 확인 방법
- 파일 해시
- 코드 서명 여부

## 4. 현재 한계

- 계급/랭크 미구현
- 업로드 재시도 큐 미구현
- 대시보드 1,000행 조회 제한
- RLS 운영 정책 재검토 필요
- RPCS3/게임 빌드 변경 시 오프셋 재검증 필요
- Windows 전용
- Python EXE 역분석 가능
- 코드 서명 미적용

## 5. 향후 우선순위

1. Supabase RLS와 쓰기 권한 정리
2. 업로드 실패 로컬 큐와 재전송
3. 서버 집계 또는 페이지네이션으로 데이터 규모 확장
4. 코드 서명과 배포 해시
5. 계급 데이터 조사
6. 사용 동의·삭제 요청·보관 기간 문서화

## 6. 변경 시 함께 갱신할 것

DB 컬럼, 경기 payload, 프론트엔드 select, 통계 계산, 빌드 버전 중 하나를 변경하면 나머지 문서와 구현을 함께 확인한다. 이 프로젝트는 Python·Supabase·프론트엔드가 하나의 데이터 파이프라인으로 묶여 있기 때문이다.
