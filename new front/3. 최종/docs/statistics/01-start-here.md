# 통계·대전 데이터 전면 교체 기록

이 문서는 이번 작업을 왜 시작했고, 어떤 잘못된 결과와 확장성 문제를 해결하려 했으며, 무엇을 바꾸고 어떻게 검증했는지를 기록하는 **프로젝트 기술 회고의 목차**입니다. 단순히 현재 구조를 소개하기 위해 만든 문서가 아닙니다.

## 왜 이 작업을 했나요?

기존 데이터 경로는 Supabase에서 경기 기록을 최대 1,000건까지만 받아온 뒤, 그 받아온 행을 기준으로 통계를 계산하거나 목록 화면에 사용했습니다. 이 설계는 전체 기록이 1,000건 이하일 때에만 전체 표본을 다룰 수 있었습니다.

실제 기록이 1,001건이 되면 최소 한 경기 행이 조회 결과에서 빠집니다. 화면이 받은 행만으로 합계·승률·캐릭터 픽 같은 값을 계산하면 그 결과는 전체 통계가 아닙니다. 1,000건 제한은 단순히 오래된 경기 목록을 덜 보여주는 문제가 아니라, **불완전한 표본을 전체 데이터인 것처럼 표시할 수 있는 정확성 결함**이었습니다.

기록이 수만 건으로 늘면 클라이언트가 큰 경기 행 묶음을 받아 처리하는 방식도 네트워크 전송량, 브라우저 메모리, 변환 및 계산량 면에서 맞지 않습니다. 기존 제한을 더 높이는 것만으로는 잘못된 분모와 누락 문제를 해결하지 못하고, 데이터가 다시 그 상한을 넘으면 같은 문제가 반복됩니다.

그래서 목표는 숫자를 맞추는 임시 보정이나 1,000이라는 상수를 늘리는 것이 아니었습니다. **무엇을 전체 범위에서 계산해야 하는지와, 실제 행을 화면에 보여주기 위해 무엇만 가져오면 되는지를 데이터베이스 작업 계약부터 다시 나누는 것**이었습니다.

## 무엇을 이 문서 묶음에 포함했나요?

이 문서 묶음은 기존 최대 1,000건 조회로 인해 발생한 정확성 문제와 대용량 확장 한계를 해결하기 위해 진행한 전체 교체 작업을 기록합니다. 작업에는 두 가지 서로 보완하는 데이터 경로가 있습니다.

- **통계:** 대시보드·플레이어 순위·프로필 통계는 DB 집계 RPC로 옮겼습니다. RPC가 조건에 맞는 전체 기록을 기준으로 계산하고, 브라우저에는 집계 결과와 제한된 목록만 반환합니다. “전체 범위 집계”란 전체 기록을 클라이언트에 모두 전송한다는 뜻이 아닙니다.
- **경기 목록:** 전체 기록과 플레이어별 기록은 화면에 실제 경기 행이 필요하므로 페이지 번호 RPC를 사용합니다. 한 요청은 현재 페이지 최대 10행과 정확한 `total_count`만 돌려주며, 사용자가 페이지를 이동할 때 추가 행을 요청합니다. 전체 기록을 한 번에 브라우저로 당겨오지 않습니다.

두 변화 모두 같은 근본 문제—상한이 걸린 클라이언트 조회를 전체 데이터의 기준으로 삼는 것—에 대응하지만 해결 방식은 다릅니다. 통계는 DB 안에서 계산하고, 목록은 필요한 페이지의 실제 행만 전달합니다.

## 이 문서가 기록하는 작업의 증거

- 기존 JavaScript 계산과 새 RPC 결과를 표본 전체와 대조했습니다.
- 당시 172건은 페이지 API를 끝까지 조회하고 고유 ID 수까지 확인해 완전성을 검사했습니다.
- DB 함수 소유자, `SECURITY DEFINER`, `search_path`, 실행 권한과 반환 상한을 확인했습니다.
- 화면 연결 및 응답 계약, 오류 처리와 입력 경계를 확인했습니다.
- 앱/API 왕복 시간과 DB 실행 시간을 구분해 기록했습니다.

각 확인의 구체적인 수치와 한계는 03과 04에 있습니다. 172건 표본에서 일치했다는 사실은 테스트 표본의 정확성을 뒷받침하지만, 수만 건에서의 성능 보증이나 부하 검증을 뜻하지는 않습니다.

## 05~08 SQL 파일을 실행할 때

05~08은 설명용 의사 코드가 아니라 데이터베이스 함수 정의와 권한을 변경하는 SQL 및 실행 뒤 결과를 확인하는 SQL을 포함합니다. 04는 앱과 DB 목록 RPC 사이의 데이터 흐름, 계약과 페이지 규칙을 설명합니다. 08은 사용자가 제공한 과거 대화의 SQL 원문을 바탕으로 두 함수를 최종 이름인 `get_all_matches_by_page`와 `get_player_matches_by_page`로 정리한 문서입니다.

- `BEGIN`부터 `COMMIT`까지는 함수와 권한 변경을 한 transaction으로 적용합니다.
- `COMMIT` 다음 SELECT 문은 정의/권한/응답을 확인하는 검증 쿼리입니다.
- 이미 적용된 DB에 무심코 재실행하지 마세요. 현재 정의와 권한, 환경을 확인한 뒤 적용해야 합니다.
- 문서 파일의 SQL과 운영 DB 함수 정의가 항상 자동으로 동기화되는 것은 아닙니다. DB를 변경했다면 원문과 이 문서를 함께 갱신하고 결과를 다시 검증해야 합니다.
