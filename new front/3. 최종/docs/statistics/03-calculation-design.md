# 03. 집계 설계와 계산 규칙

이 문서는 DB 집계로 전환한 이유, 원본 경기의 표현, 각 통계의 계산 규칙, 보안 결정과 확인 결과를 설명합니다. 전체 파일 순서는 [01. 문서 읽기 안내](./01-start-here.md), 실제 요청 경로는 [02. 데이터 흐름](./02-data-flow.md)부터 읽으세요.

함수 구현을 읽을 때는 아래 설명과 SQL 원문을 함께 보세요. 각 SQL 파일은 문장과 주요 표현 가까이에 동작 주석을 둡니다.

- 전체·개인 경기 기록 페이지 조회(집계가 아닌 원본 경기 행): [`04-match-history-pagination.md`](./04-match-history-pagination.md)

## 먼저 알아둘 SQL 용어

| 용어/표현 | 쉬운 뜻 |
|---|---|
| 행(row) | 표의 한 줄. 여기서는 한 경기 또는 한 선수 관점 기록 |
| RPC | 데이터베이스 함수에 이름과 인자를 주어 실행하는 API 호출 |
| View | 저장 결과가 아니라 정해진 조회 모양을 재사용하는 DB 객체 |
| CTE (`WITH`) | 복잡한 SQL을 이름 붙인 중간 계산 단계들로 나누는 구문 |
| `MATERIALIZED` | CTE 결과를 중간 결과로 만들어 해당 쿼리에서 재사용 |
| `btrim(x)` | 문자열 앞뒤 공백 제거 |
| `coalesce(a, b)` | 왼쪽부터 보아 첫 NULL이 아닌 값을 반환 |
| `nullif(a, b)` | a와 b가 같으면 NULL, 다르면 a를 반환 |
| `FILTER (WHERE ...)` | 집계 함수가 조건을 만족하는 행만 세도록 제한 |
| `::integer`, `::numeric`, `::date` | 값을 정수, 소수 계산용 숫자, 날짜 형식으로 변환 |
| `->` / `->>` | JSON에서 값 꺼내기. 전자는 JSON, 후자는 문자열 형태 |
| `ASC` / `DESC` | 오름차순(작은 값부터) / 내림차순(큰 값부터) |
| `LIMIT n` | 결과 최대 개수를 n개로 제한 |
| `[시작, 끝)` | 시작은 포함하고 끝은 제외하는 시간 구간 |
| `COLLATE "C"` | 지역/언어 정렬 설정에 덜 의존하도록 일관된 문자 정렬 적용 |

## 1. 원래 문제: 1,000행 상한을 전체 데이터처럼 사용

기존 경로는 경기 전체를 이어서 페이지 조회하는 대신 Supabase에서 한 번에 최대 1,000개 행을 받아 JavaScript에서 통계를 계산했습니다. 가져온 행 목록을 전체 데이터로 간주했기 때문에, 실제 경기 수가 1,001건이 되는 순간 적어도 한 건은 계산에서 누락됩니다. 실제 기록이 수만 건이면 상한 뒤의 기록 대부분이 결과에 들어오지 않습니다.

이것은 단순히 “더 오래된 목록을 못 본다”는 UI 문제가 아닙니다. 화면에 표시하는 값이 조회된 1,000행에서 만들어지면서도 사용자에게는 전체 통계처럼 보일 수 있는 데이터 정확성 문제입니다.

| 지표 | 1,000행만 계산에 쓸 때 생길 수 있는 오류 |
|---|---|
| 전체 경기 수 | 1,001건 이상이어도 최대 1,000건으로 계산 |
| 플레이어별 경기/승/패 | 상한 이후 경기가 누락되어 실제 전적보다 작아짐 |
| 승률 | 누락된 경기의 승패 분포에 따라 위아래로 편향 |
| 캐릭터/조합/맵 통계 | 누락된 경기에서 쓰인 픽과 조합이 빠지거나 횟수가 적게 계산 |
| 최근 날짜/급상승 | 받은 1,000행 안에 필요한 기간 데이터가 전부 있다는 보장이 없음 |
| 순위 | 잘린 표본의 승률·경기 수로 순위를 매기면 순서와 자격이 달라질 수 있음 |

더 큰 limit으로 바꾸는 것은 해결책이 아닙니다. 데이터가 새 limit을 넘어설 때 같은 결함이 다시 나타나며, 브라우저로 보내고 파싱하고 유지해야 하는 행 수만 커집니다. 수만 건을 클라이언트에 보내 그곳에서 합산하는 구조는 네트워크, 메모리, 렌더링 전 작업량 측면에서도 데이터가 자랄수록 부담을 키웁니다.

### 해결 원칙: 집계와 목록을 서로 다른 계약으로 분리

1. 통계는 각 RPC의 입력과 필터를 통과하는 전체 대상 행을 DB에서 집계합니다.
2. 통계 API는 계산된 요약과 화면에 필요한 항목 상한이 정해진 배열만 반환하고 경기 전체 행은 반환하지 않습니다.
3. 실제 경기 기록을 보여줘야 하는 목록은 한 번에 모두 가져오지 않고, 현재 페이지의 최대 10행과 `total_count`를 요청합니다.
4. 통계 숫자는 기존 JavaScript 계산 의미와 전체 표본 대조로 확인합니다.
5. 반환 배열 상한, RPC 권한, 입력/응답 검증을 SQL과 애플리케이션 양쪽에서 명시합니다.

여기서 “DB가 전체를 집계한다”는 것은 전체 결과가 브라우저로 이동한다는 뜻이 아닙니다. 반대로 페이지네이션은 사용자가 목록을 전부 탐색할 수 있게 하지만 브라우저가 첫 요청에서 모든 행을 받는 방식도 아닙니다.

> **성능상 중요한 한계:** 이 구조는 클라이언트로 보내는 데이터량을 통제하고, 1,000행 잘림으로 생기는 통계 오류를 제거합니다. 하지만 DB가 집계 대상 전체를 읽거나 `total_count`를 세는 비용까지 없애지는 않습니다. 큰 테이블에서 실행 시간이 항상 일정하다고 보장하지 않으며, 실제 대규모 데이터에서 쿼리 계획·인덱스·실행 시간을 다시 측정해야 합니다.

## 2. 요청에서 DB까지: 각 구성요소의 역할

| 계층 | 책임 | 예시 |
|---|---|---|
| 화면 | 받은 숫자와 목록을 보여줌 | `DashboardHome`, `PlayersRanking`, `ProfileView` |
| Hook | API 호출, 로딩/오류, 자동 갱신/취소 | `useDashboardStatistics`, `useProfileStatistics` |
| Next.js API | 입력 검사, 서버에서 RPC 호출, 결과 형식 검사 | `src/app/api/statistics/dashboard/route.ts` |
| Supabase RPC | DB 안에서 집계하고 결과 계약을 고정 | `get_dashboard_statistics()` |
| 공통 View | 원본 경기를 선수별 관점의 행으로 표현 | `public.v_player_match_rows` |
| 원본 테이블 | 실제 경기 기록을 저장 | `public.matches` |

브라우저에는 Supabase 서비스 롤 키를 두지 않습니다. 서버 코드는 공개 anon key로 RPC를 호출합니다. 이 RPC들은 제한된 집계만 반환하므로 anon/authenticated에 실행 권한을 부여할 수 있습니다. View 자체는 anon/authenticated가 직접 SELECT할 수 없게 막았습니다.

## 3. 공통 View의 역할

객체 이름은 `public.v_player_match_rows`입니다. `public`은 스키마 이름이고 `v_player_match_rows`가 객체 이름입니다. 일반 View는 결과를 물리적으로 저장하지 않는 SQL 조회 정의입니다.

원본 경기 한 건을 두 행으로 표현합니다.

| 원본 경기 필드 | 첫 번째 관점 행 | 두 번째 관점 행 |
|---|---|---|
| P1/P2 이름 | P1은 `player_name`, P2는 `opponent_name` | P2는 `player_name`, P1은 `opponent_name` |
| 승자 | 승자가 P1인지 `is_win`에 기록 | 승자가 P2인지 `is_win`에 기록 |
| 캐릭터 | P1 캐릭터 두 칸 | P2 캐릭터 두 칸 |
| 경기 ID/맵/시각 | 원본 값을 공유 | 원본 값을 공유 |

함수를 `SECURITY DEFINER`로 실행하는 이유는 앱 역할이 View를 직접 읽지 못하게 하면서도 제한된 DB 집계를 허용하기 위해서입니다. 소유자는 `postgres`, 함수 검색 경로는 `pg_catalog, public`으로 고정합니다. `matches`의 FORCE RLS가 비활성인 확인 당시 구성에서는 postgres 소유 함수가 RLS 정책으로 제한되지 않습니다. 즉, 함수 실행을 공개할 때는 그 함수가 전체 데이터 범위를 보여도 되는지 검토해야 합니다. 현재 서비스는 전체 경기 목록도 공개 RPC로 반환하는 구성이지만, 비공개 경기/테넌트가 추가되면 공개 실행 권한을 재검토해야 합니다.

### View 정의의 각 절이 하는 일

실제 적용했던 정의는 다음과 같습니다. 이 코드에는 데이터베이스 객체를 생성하고 권한을 회수하는 명령이 있으므로, 이미 View가 존재하는 DB에서 다시 실행할 SQL로 복사하지 마세요. 아래는 동작 설명용 정의입니다.

```sql
CREATE VIEW public.v_player_match_rows AS
SELECT
  m.id AS match_id,
  m.p1_name AS player_name,
  m.p2_name AS opponent_name,
  lower(m.winner) = lower(m.p1_name) AS is_win,
  m.p1_main_character_id AS player_main_character_id,
  m.p1_sub_character_id AS player_sub_character_id,
  m.map_id,
  m.start_time,
  m.end_time,
  coalesce(m.end_time, m.created_at) AS played_at
FROM public.matches AS m
UNION ALL
SELECT
  m.id AS match_id,
  m.p2_name AS player_name,
  m.p1_name AS opponent_name,
  lower(m.winner) = lower(m.p2_name) AS is_win,
  m.p2_main_character_id AS player_main_character_id,
  m.p2_sub_character_id AS player_sub_character_id,
  m.map_id,
  m.start_time,
  m.end_time,
  coalesce(m.end_time, m.created_at) AS played_at
FROM public.matches AS m;
```

- `CREATE VIEW ... AS`: 이름을 정하고 그 아래 SELECT들을 View의 정의로 저장합니다.
- 첫 번째 `SELECT`: 각 원본 행을 P1 플레이어 관점으로 변환합니다. `AS`는 결과 열의 이름을 붙입니다.
- `lower(winner) = lower(p1_name)`: 영어 대소문자 차이는 무시하고 P1 승리 여부를 계산합니다. 승자값이 NULL이면 결과도 NULL이므로 임의로 패배 처리하지 않습니다.
- `coalesce(end_time, created_at)`: 종료 시각이 있으면 그것을, 없으면 등록 시각을 `played_at`으로 사용합니다.
- `UNION ALL`: 두 SELECT 결과를 합치되 중복 제거 작업을 하지 않습니다. 경기마다 P1 관점 행과 P2 관점 행을 반드시 각각 보존합니다.
- 두 번째 `SELECT`: 같은 원본 행을 P2 플레이어 관점으로 바꾸고 P2 승리 여부를 계산합니다.
- 두 SELECT가 모두 `public.matches`에서 읽으므로 결과는 한 경기당 최대 두 행입니다.

생성 직후 적용한 권한 관련 명령의 의미:

```sql
REVOKE ALL PRIVILEGES ON TABLE public.v_player_match_rows
  FROM PUBLIC, anon, authenticated;
NOTIFY pgrst, 'reload schema';
```

- `REVOKE ALL PRIVILEGES`: 기본 권한으로 이미 붙을 수 있는 직접 권한을 회수합니다. `PUBLIC`은 모든 DB 역할을 가리키는 의사 역할입니다.
- `NOTIFY pgrst, ...`: PostgREST에 DB 함수/스키마 캐시를 다시 읽으라고 알립니다.
- View 생성과 권한 회수는 하나의 transaction 안에서 실행해 외부 역할이 그 사이 View를 읽을 수 있는 틈을 만들지 않습니다.

## 4. RPC 4개의 책임과 반환 상한

| 함수 | 기능 | 브라우저로 반환하는 결과 |
|---|---|---|
| `get_dashboard_statistics()` | 글로벌 KPI·캐릭터·조합·급상승·활동 계산 | 활동 날짜 30개, 캐릭터 최대 6개, 조합 최대 6개, 급상승 0~1명, 전체 경기 행 없음 |
| `get_player_rankings()` | 플레이어별 경기/승/승률 및 주력 조합 계산 | 최대 10명, 각 플레이어 20전 이상 |
| `get_player_statistics(name, opponent)` | 한 플레이어 프로필 요약·조합·맵·상대 집계 | 조합 최대 5개, 맵 최대 50개, 상대 최대 5명, 선택 상대 0~1개 |
| `search_player_names(query, exclude)` | 접두어(prefix)가 맞는 이름 검색 | 최대 10개 이름, 빈 검색은 빈 배열 |

함수 입력의 주요 계약:

- 이름과 검색어는 최대 100자입니다.
- 프로필 함수는 플레이어 이름을 필수로 받고 상대 이름은 선택적으로 받습니다.
- 이름 검색은 입력한 문자열로 시작하는 이름을 찾습니다. 임의 위치 포함 검색이 아닙니다.
- 각 SQL 파일은 소유자, `SECURITY DEFINER`, 고정 `search_path`, `EXECUTE` 권한을 명시하고 적용 후 검증 SELECT를 포함합니다.

SQL 코드의 구문별 설명과 그대로 실행할 본문은 각 SQL 파일의 주석을 기준으로 하세요. 파일 중간의 `BEGIN`/`COMMIT`은 DB 변경을 하나의 transaction으로 묶고, transaction 이후 SELECT들은 검증용 읽기 쿼리입니다.

## 5. 계산 의미

### 대시보드

- **전체 대전:** 이름이 비어 있지 않은 P1/P2 관점 행을 경기 ID로 다시 묶어 원본 경기 수를 셉니다.
- **등록 플레이어:** 양끝 공백을 제거한 이름의 서로 다른 개수를 셉니다. SQL은 대소문자를 보존하는 그룹 기준입니다.
- **오늘 대전:** 한국 시간(KST) 자정부터 통계 조회 시각까지의 경기 수입니다. 미래 시각으로 기록된 경기는 제외합니다.
- **캐릭터 픽률:** 두 플레이어의 메인/서브 4칸을 모두 셉니다. 픽률 분모는 전체 경기 수 × 4입니다.
- **조합:** 플레이어별 메인·서브를 작은 ID부터 정렬해 태그 순서가 다른 동일 조합을 합칩니다. 10전 이상 조합 중 승률 상위 6개입니다.
- **급상승:** KST 오늘을 포함한 최근 7일과 직전 7일 각각 10전 이상인 플레이어를 비교합니다. 승률 상승이 있는 사람 중 상승폭이 가장 큰 1명을 반환합니다. 없으면 JSON `null`입니다.
- **활동 그래프:** 오늘 포함 최근 KST 날짜 30개 각각의 경기 수입니다. 경기 없는 날짜도 0으로 반환합니다.

### 순위

- 한 경기를 각 플레이어 관점에서 한 경기로 셉니다.
- 승리 여부는 View의 `is_win`을 사용합니다.
- 그룹별 20전 이상을 남기고 승률 내림차순, 경기 수 내림차순, C collation 기준 이름 오름차순으로 최대 10명을 선택합니다.
- 대표 조합은 가장 많이 사용한 조합이며, 사용 횟수 동률이면 캐릭터 ID 오름차순으로 선택합니다.

### 프로필과 이름 검색

- 프로필 경기/승/패/승률은 지정 플레이어 관점에서 계산합니다.
- 플레이 시간은 시작/종료 시각이 모두 있고 종료가 시작보다 이르지 않은 경기만 초 단위로 합산합니다.
- 조합은 플레이어의 태그 쌍별 경기·승리 수, 맵은 `map_id IS NOT NULL` 기록만 집계합니다.
- 최근 상대는 상대 이름을 소문자 키로 합치고 가장 최근 경기 순으로 최대 5명 반환합니다.
- 이름 검색은 대소문자 무시 prefix 일치입니다. 표기 이름은 그 이름으로 기록된 가장 최근 경기에서 가져옵니다.

## 6. 보안 용어를 이 설계에서 해석하는 법

- `SECURITY DEFINER`: 함수 소유자 권한으로 쿼리를 실행합니다. 여기서는 `postgres` 소유로 고정합니다.
- `SET search_path = pg_catalog, public`: 호출자 세션의 위험한 객체 탐색 경로를 사용하지 않게 합니다. 애플리케이션 객체는 가능한 한 `public.`으로 스키마를 명시합니다.
- `REVOKE ... FROM PUBLIC, anon, authenticated`: 먼저 기본 실행 권한을 모두 제거합니다.
- `GRANT EXECUTE ... TO anon, authenticated`: 필요한 API 역할에 함수 호출 권한만 다시 허용합니다.
- View 직접 SELECT는 별도로 막아 둡니다. 함수 반환 상한을 우회해 원본 선수 관점 행 전체를 조회하지 못하게 하기 위함입니다.
- 서비스 롤 키는 브라우저에 넣지 않습니다.

## 8. 기존 계산과의 전체 표본 대조

페이지 API로 `total_count=172` 전체를 빠짐없이 읽었고 172개 고유 경기 ID를 확인했습니다. 이어 기존 JavaScript 대시보드 계산과 Supabase RPC 응답을 비교했습니다.

| 항목 | 비교 결과 |
|---|---|
| 경기 수/플레이어 수/최근 24시간(변경 전 기준) | 당시 계산과 모두 일치 |
| 조합 경기 수/승리 수/승률 | 일치 |
| KST 30일 활동과 급상승 기간별 수치 | 일치 |
| 캐릭터 픽 횟수와 승률 | 값은 일치. 동률 캐릭터 ID 6·62의 표시 순서만 다름 |
| 캐릭터 ID | NULL 0건, 등록되지 않은 ID 0건. 명시적 ID 0은 기존 규칙대로 폴 캐릭터 |
| 맵 ID | 미등록 ID 0건. NULL 108건이며 기존 계산과 SQL 모두 맵 집계에서 제외 |
| 경기 시각 | 누락 또는 파싱할 수 없는 시각 0건 |

날짜 표준은 사이트 공통 `Asia/Seoul`로 확정했습니다. 이전 JavaScript는 방문자 브라우저의 로컬 시간대를 사용했으므로, KST 외 지역 방문자는 달력 날짜 경계 결과가 예전과 달라질 수 있습니다. 공통 시간대를 사용하는 것이 사이트 전체에서 같은 경기를 같은 날짜로 보여주는 기준입니다.

이 검증에서 172는 “표본을 제한해도 충분하다”는 뜻이 아닙니다. 당시 DB에 있는 전체 경기 172건을 페이지 API의 `total_count`에 따라 마지막 페이지까지 실제로 가져와 대조한 결과입니다. 예전 1,000건 경로로는 문제가 드러나지 않을 작은 표본이었기 때문에, 이 비교는 기존 계산과 새 집계의 의미가 일치하는지 확인하는 회귀 검증으로 사용했습니다. 1,001건 이상에서 상한 잘림이 생기는 문제는 이 데이터 표본만으로 실증한 것이 아니라, 기존 상한 동작에서 직접 따라오는 구조적 결함입니다.

## 9. 교체 작업은 어떤 순서로 진행됐나요?

이번 작업은 limit 숫자만 바꾸는 수정이 아니라 데이터 경로를 나누고 결과를 교차 확인하는 작업이었습니다.

1. **기존 데이터 경로를 조사:** 통계와 기록 화면이 상한이 있는 경기 목록을 사용해 계산/렌더링할 수 있는 지점을 찾아냈습니다.
2. **통계의 DB 기준을 설계:** 원본 경기 한 건을 P1/P2 관점으로 표현하는 `public.v_player_match_rows`를 기준으로 정하고, KPI·순위·프로필·이름 검색에 필요한 RPC를 나눴습니다.
3. **계산 규칙을 보존:** 이름 정규화, 승리 판정, 캐릭터 조합 정렬, 시간대, NULL 처리, 분모, 최소 경기 수, 응답 배열 상한을 기존 계산과 맞췄습니다. 시간대 기준은 사이트 공통 KST로 정리했습니다.
4. **실제 기록 목록을 페이지화:** 전체 및 플레이어별 목록을 각각 별도 페이지 RPC 경로로 바꿨습니다. `page`, `page_size`, 정확한 `total_count`, 개인 기록 정렬, 시간순 `match_number`를 계약에 포함했습니다.
5. **서버/API 경계에서 검증:** 입력을 제한하고 명시된 RPC만 호출하며, DB JSON 구조·수치·행·페이지 크기를 파싱해 오류를 빈 성공값으로 숨기지 않게 했습니다.
6. **권한을 확인:** 통계 View 직접 조회를 차단하고, `SECURITY DEFINER` 함수 소유자·`search_path`·anon/authenticated 실행 권한을 점검했습니다.
7. **표본 전체를 끝까지 대조:** 목록 페이지로 172행 전부와 고유 ID 172개를 확인한 뒤 기존 JavaScript 집계와 DB 응답을 비교했습니다.
8. **화면과 성능을 확인:** 대시보드·순위·프로필·검색 흐름을 확인하고, 로컬 API 왕복과 SQL Editor DB 실행 시간을 각각 기록했습니다.

각 계층과 확인의 의미는 [02. 데이터 흐름](./02-data-flow.md), 기록 목록의 구체적 동작은 [04. 전체·개인 경기 기록 페이지 조회](./04-match-history-pagination.md)를 함께 참고하세요.

## 10. API 왕복 시간과 올바른 해석

2026-09-30 production build의 로컬 Next.js API를 한 번씩 순차 호출한 시간은 **앱+네트워크 포함** 관측치입니다. DB 단독 실행 시간과 구별합니다.

| API | 시간 | 의미 |
|---|---:|---|
| dashboard | 2515ms | 로컬 앱 경로를 포함한 1회 왕복 |
| rankings | 70ms | 로컬 앱 경로를 포함한 1회 왕복 |
| profile | 73ms | 로컬 앱 경로를 포함한 1회 왕복 |
| search | 54ms | 로컬 앱 경로를 포함한 1회 왕복 |

이 값은 로컬 앱, API 처리, 네트워크를 포함한 관측치이며 DB 단독 실행 시간이 아닙니다. 대시보드 2515ms는 단 한 번의 요청에서 측정했으므로 반복 평균이나 대표 성능으로 해석하면 안 됩니다. DB에서 직접 측정한 시간은 다음 절에서 따로 다룹니다.

## 11. DB 실행 시간과 한계

2026-10-01 Supabase SQL Editor에서 사용자가 네 RPC를 `EXPLAIN (ANALYZE, BUFFERS, TIMING ON)`으로 각각 한 번씩 실행해 다음 결과를 제공했습니다.

| RPC | Planning Time | Execution Time | Shared buffer hit |
|---|---:|---:|---:|
| 대시보드 | 0.047ms | 18.977ms | 1227 |
| 순위 | 0.045ms | 4.040ms | 835 |
| 프로필 | 0.089ms | 5.382ms | 1040 |
| 이름 검색 | 0.044ms | 3.405ms | 607 |

`Execution Time`은 EXPLAIN에 전달한 바깥 SQL 문장의 실행 시간입니다. 제공된 계획에는 바깥 `Result` 노드만 표시되어 함수 내부 각 SQL 구문의 실행 계획은 펼쳐져 있지 않습니다. 수치는 당시 172경기 표본, 개별 1회 실행 결과입니다. 반복 평균, 동시 사용자 부하, 더 큰 데이터 규모에서의 성능은 확인하지 않았습니다.

현재 통계 화면 연결, Supabase 적용, 응답 검증과 표본 대조는 완료됐습니다. 남아 있는 성능 작업은 데이터가 충분히 증가한 운영 규모에서 쿼리 계획과 실행 시간을 다시 측정하는 일입니다. 부하 테스트는 하지 않았습니다.

추후 화면/API를 바꾸는 사람은:

1. 집계 의미와 NULL 처리/분모/시간 구간을 먼저 확인합니다.
2. DB에서 계산하고 반환 배열 상한을 SQL에서 강제하며 응답 형식을 서버에서도 검증합니다.
3. 관련 SQL 파일(05~08)의 주석과 검증 쿼리를 함께 갱신합니다.
4. 전체 경기 표본 또는 경계 사례 테스트로 기존 의미와 비교합니다.
5. API 시간과 DB 실행 시간을 혼동하지 않도록 측정 방법을 기록합니다.

현재 기록된 172경기·단일 호출 수치는 이 교체가 해당 표본에서 정확하고 빠르게 동작했다는 근거이지, 수만 건에서 성능이 이미 입증됐다는 의미는 아닙니다. 대규모 성능 검증은 별도로 남아 있는 작업입니다.
