# 화면 체감 속도 최적화 완료 보고서

## 1. 배경과 목표

기존에는 최대 1,000건의 경기 데이터를 받아 브라우저에서 통계를 계산했습니다. 이 방식은 당시 화면에서 빠르게 느껴질 수 있었지만, 전체 경기 수가 상한을 넘으면 통계에서 기록이 빠져 정확하지 않을 수 있었습니다. 현재 구조는 정확성을 위해 DB RPC에서 통계를 계산하고 경기 기록은 필요한 페이지만 조회합니다.

DB 기준으로 바꾸며 화면에서 필요한 요청을 기다리는 시간이 더 체감될 수 있습니다. 이 계획은 정확성을 다시 희생하거나 전체 경기 행을 브라우저로 가져오는 대신, 재사용할 수 있는 응답을 캐시하고 필요한 요청을 미리 시작해 **화면이 기다리는 시간을 줄이는 것**을 목표로 합니다.

이 문서는 구현 전 합의한 동작, 구현 내용, 검증 결과와 확인된 한계를 함께 기록합니다. 속도 비교는 현재 저장소 데이터와 기존 빌드로 수행한 참고 측정이며, 대규모 부하 시험이나 운영 환경의 성능 보증을 뜻하지 않습니다.

## 2. 확정된 결정

| 항목 | 결정 |
|---|---|
| DB 통계의 정확성 | DB RPC와 페이지 조회 구조를 유지합니다. 전체 경기 행을 통계 계산 목적으로 브라우저에 보내지 않습니다. |
| 초기 데이터 준비 | 대시보드, TOP 10, 전체 대전 기록 1페이지를 준비합니다. |
| 독립 API 요청 | 초기 준비 요청은 서로 의존하지 않으므로 병렬로 시작합니다. |
| 현재 화면 우선순위 | 현재 열린 화면의 데이터가 준비되면 먼저 표시하고, 다른 데이터는 백그라운드에서 캐시에 채웁니다. |
| 지속 캐시 | 브라우저의 IndexedDB를 사용합니다. 브라우저/기기 간 공유는 요구하지 않습니다. |
| 저장 범위 | 앱이 실제로 받아온 응답은 저장합니다. 사용자가 아직 열지 않은 모든 프로필/경기 페이지를 미리 가져오지는 않습니다. 별도로 정한 첫 진입 3종 데이터와 선택 상대 1명의 선조회는 예외적으로 준비합니다. |
| 보존 | 앱은 캐시를 자동 만료하거나 삭제하지 않습니다. 브라우저에 저장 공간 보존을 요청하고, 요청이 거부/미지원이어도 네트워크 조회로 정상 동작합니다. |
| 캐시가 있을 때 | 저장 데이터를 먼저 표시하고, 새 데이터는 화면을 비우지 않은 채 백그라운드에서 받아 별도 갱신 표시 없이 조용히 교체합니다. |
| 오래된 캐시 | 5초와 5분은 서로 다른 기준으로 사용합니다. 오래된 데이터를 지우고 빈 화면을 만드는 대신 표시 가능한 값으로 유지하며 갱신합니다. |
| 이름 자동완성 | 250ms 디바운스를 제거하고, 비어 있지 않은 검색어가 바뀌면 즉시 검색을 시작합니다. |
| 자동완성 캐시 | 검색어별 결과를 IndexedDB에 저장하고, 앱에서 자동 만료·삭제하지 않습니다. 캐시 결과는 임시 제안으로 먼저 보여주고, 사용자가 즉시 선택할 수 있게 하며, 최신 서버 검색은 동시에 계속합니다. |
| 선택 상대 전적 | 자동완성에서 특정 닉네임을 선택하는 순간 그 한 명의 전적 조회를 시작합니다. 다른 후보 전적은 미리 조회하지 않습니다. |
| 제출 | 돋보기 버튼/Enter는 조회 시작 신호가 아니라 선택 상대 결과를 화면에 적용하는 동작입니다. 이미 시작한 요청이 있으면 이를 재사용하고 중복 요청하지 않습니다. |
| 작은 시점 차이 | 각 API 결과의 데이터 시점이 조금 다를 수 있는 것은 허용합니다. 모든 카드의 결과가 하나의 DB 스냅샷이어야 한다는 요구는 없습니다. |
| 성능 측정 | 구현 당시 비교 측정은 보류하고 기능 검증을 먼저 합니다. 구현 완료 후 사용자가 별도로 요청하면 전후 버전의 동일 화면을 비교합니다. |

## 3. 초기 진입과 캐시 동작

### 캐시가 없는 경우

아래 세 요청은 독립적이므로 순차 대기하지 않고 병렬로 시작합니다.

```text
대시보드 통계 API ─┐
TOP 10 API         ├─ 병렬 시작
대전 기록 1페이지 API ┘
```

화면은 현재 경로에 필요한 응답이 도착하면 그 화면부터 렌더링합니다. 다른 요청이 느리다고 현재 화면까지 기다리게 하지 않습니다. 나머지 응답은 도착하는 대로 IndexedDB에 저장해 이후 화면 이동에서 재사용합니다.

구현 시 현재 화면 요청과 선취 요청이 같은 키로 겹칠 수 있으므로, 요청 중복 제거를 해야 합니다. 동일 데이터 키에 이미 네트워크 요청이 진행 중이면 새 요청을 만들지 않고 진행 중인 Promise/결과를 공유합니다.

### IndexedDB에 데이터가 있는 경우

1. 화면 진입 시 IndexedDB에서 키에 맞는 데이터를 읽습니다.
2. 유효한 저장 데이터가 있으면 서버 응답을 기다리지 않고 먼저 화면에 제공합니다.
3. 갱신 기준을 넘겼다면 기존 화면을 유지한 채 서버 요청을 시작합니다. 갱신 중이라는 별도 표시 없이 기존 화면을 유지합니다.
4. 성공한 새 응답을 화면과 IndexedDB에 함께 반영합니다.
5. 갱신에 실패하면 기존 데이터는 유지하고 오류를 별도로 알립니다. 오류를 빈 성공값으로 바꾸지 않습니다.

브라우저가 IndexedDB를 비우거나 읽기/쓰기 오류가 발생해도 네트워크 요청으로 기능을 계속 사용할 수 있어야 합니다. 캐시는 성능 보조 수단이지 앱 데이터의 유일한 원천이 아닙니다.

### 저장 용량과 보존 요청

- `navigator.storage.persist()`를 지원하는 브라우저에서는 사이트 저장소 보존을 요청합니다. 허용 여부는 브라우저가 결정하며, 저장 공간을 예약하거나 부족한 공간을 확보하는 기능은 아닙니다.
- `navigator.storage.persist()`를 지원하지 않거나 요청이 거부돼도 앱 동작을 막지 않습니다.
- IndexedDB 쓰기가 quota/storage 오류로 실패해도 다른 사이트, 브라우저 데이터, 앱 데이터를 강제로 지우지 않습니다. 앱도 기존 캐시를 자동 삭제해 공간을 만들지 않습니다.
- 캐시 저장이 실패하면 오류를 기록하고, 이번 세션은 메모리에 받은 응답을 사용하며 API/서버 조회는 계속합니다. 다음 방문 때 해당 응답의 로컬 캐시가 없을 수 있습니다.
- 브라우저의 저장량 추정은 참고값일 뿐이며, 미리 계산해 저장 공간을 보장하지 않습니다.

## 4. 5초와 5분의 의미

기준은 주기적 폴링 간격이 아닙니다.

- **5초 신선도 기준:** 저장 데이터가 5초 이내라면 화면 진입 때 재검증 요청 없이 캐시를 사용합니다. 5초보다 오래된 값을 화면에서 사용하게 되는 경우 백그라운드 갱신을 한 번 시작합니다.
- **5분 재검증 기준:** 5분 이내 데이터는 통상 신선한 캐시로 취급합니다. 5분을 넘긴 데이터는 더 오래된 값으로 취급해 사용 시 즉시 재검증하되, 새 응답 전에 캐시를 삭제하거나 화면을 비우지는 않습니다.
- **재검증은 이벤트 기반:** 화면 진입/데이터 사용 시 나이 기준을 검사합니다. 5초마다 반복 요청하는 폴링은 하지 않습니다.

5초와 5분은 일반 화면 데이터를 언제 다시 서버에서 확인할지 판단하는 기준이며, 저장소에서 데이터를 삭제하는 만료시간(TTL)이 아닙니다. 5초가 지나면 백그라운드 갱신 대상이고, 5분이 지나면 더 오래된 데이터로 표시/재검증합니다. 갱신 성공 시 `updatedAt`을 갱신합니다. 갱신 중에는 별도 표시 없이 기존 화면을 유지하고, 갱신 실패 시에는 오류를 알려 최신 여부를 숨기지 않습니다.

이 5초·5분 정책은 대시보드, 순위, 프로필 통계, 대전 기록 등 화면 데이터 캐시를 위한 것입니다. 검색어별 자동완성 캐시는 별도 동작을 사용하며 이 신선도 간격을 적용하지 않습니다.

## 5. IndexedDB 캐시 계약

### 저장 키

서로 다른 조회 결과가 섞이지 않도록 요청 의미 전체를 키에 포함합니다.

| 데이터 | 캐시 키 예시 |
|---|---|
| 대시보드 | `dashboard` |
| TOP 10 | `rankings` |
| 전체 대전 기록 | `matches:page:1` |
| 개인 대전 기록 | `player-matches:{정규화된 이름}:{페이지}:{정렬}` |
| 프로필 통계 | `profile:{정규화된 이름}:{상대 이름 또는 none}` |
| 이름 제안 | `player-name-suggestions:{정확한 검색어}:{제외할 이름}`. 검색어별로 저장하되 아래 자동완성 정책에 따라 매번 서버에서 재검증합니다. |

실제 키 형식은 구현 시 한 곳에서 정의합니다. 대소문자 정규화는 DB 조회 의미와 기존 API 계약을 확인해 결정하고, 서로 다른 표시 이름을 임의로 같은 프로필로 합치지 않습니다.

### 저장 레코드와 검증

캐시 항목은 최소한 다음 정보를 가져야 합니다.

- 캐시 키
- 데이터 스키마 버전
- 저장/갱신 시각(`updatedAt`)
- 기존 API가 반환한 응답 데이터

IndexedDB에서 읽은 값도 신뢰할 수 없는 입력으로 취급해 기존 응답 파서를 통과시킵니다. 스키마 버전이 다르거나 파싱에 실패한 항목은 정상 데이터로 렌더링하지 않고 네트워크에서 다시 받습니다. 이 경우에도 앱이 기존 캐시를 자동 정리 목적으로 삭제하지 않습니다. 데이터에 사용자 인증 정보나 비밀 키를 저장하지 않습니다.

쓰기 실패나 저장소 사용 불가가 API 성공을 실패로 바꾸어서는 안 됩니다. 단, 저장 오류는 개발/운영 진단이 가능하도록 기록하고 사용자 데이터가 저장된 것처럼 조용히 처리하지 않습니다.

## 6. 닉네임 자동완성: 검색어별 캐시와 즉시 서버 검색

250ms debounce를 제거합니다. 입력이 비어 있지 않고 새 검색어가 되면 해당 검색어의 캐시를 확인하는 동시에 `search_player_names`를 즉시 요청합니다. 캐시에 값이 있으면 서버 응답을 기다리는 동안 임시로 보여주고, 서버 응답이 도착하면 교체·저장합니다. 100자 제한, prefix 검색, 최대 10개 결과 등 기존 서버 계약은 그대로 유지합니다.

자동완성 캐시는 결과의 원본이 아니며 서버 검색을 생략하는 근거로 사용할 수 없습니다. 캐시 후보는 서버 검색이 끝나기 전에도 즉시 선택할 수 있고, 사용자가 선택한 뒤에도 해당 검색어의 서버 검색은 계속 진행합니다. 입력할 때마다 캐시 조회와 함께 서버 검색을 시작합니다. 따라서:

- 캐시가 비어 있거나 캐시 결과가 빈 배열이어도 서버 검색을 매번 실행합니다. 캐시에 없는 신규 플레이어가 검색되지 않는 상황을 막습니다.
- 캐시 후보를 보여주는 동안 “검색 결과 없음”을 확정하지 않습니다. 서버 검색이 성공한 뒤에만 현재 검색어에 대한 결과 없음 상태를 표시합니다.
- 캐시가 있는 상태에서 서버 요청이 실패하면 오래된 후보와 최신 조회 실패를 구분해 알립니다. 오래된 후보만으로 최신 결과인 것처럼 표시하지 않습니다.
- 검색어가 다른 항목의 캐시 결과를 현재 검색어의 결과로 사용하지 않습니다. 오직 정확히 같은 검색어/제외 이름 키만 임시 표시합니다.
- 서버 응답은 성공 시 현재 제안 목록의 기준이 되고 캐시를 덮어씁니다. 앱은 자동 만료나 용량 확보를 위한 자동 삭제를 하지 않습니다. 브라우저가 사이트 데이터를 지우거나 저장 공간을 회수할 수 있으므로 실제 영구 보존은 보장되지 않습니다.

빠른 타이핑 중에는 입력 글자마다 네트워크/API 요청이 생길 수 있습니다. 새 입력은 이전 브라우저 요청을 abort하고 오래된 응답이 현재 검색어의 제안 목록을 덮지 않도록 검색어 키를 확인합니다. AbortController는 브라우저의 요청 처리를 취소하지만 이미 Supabase DB에서 실행 중인 작업 취소를 보장하지 않습니다. 따라서 사용량을 검증할 때 프론트 요청 수와 Supabase 실제 DB 호출 수를 구분합니다.

이 Hook은 다음 세 UI에서 공유됩니다.

1. 상단 플레이어 검색창
2. 프로필의 상대 전적 검색창
3. PWA의 저장 프로필 추가 검색창

검색어가 한 글자일 때 요청을 막거나 최소 글자 수를 추가하는 결정은 아직 없습니다. 기존 API가 허용하는 비어 있지 않은 검색어를 기준으로 동작시키며, 다른 제한이 필요해지면 별도 결정 후 서버 계약과 함께 변경합니다.

## 7. 선택한 상대 전적 선조회

### 의도한 흐름

```text
자동완성에서 상대 이름 선택
  → 선택 이름으로 get_player_statistics 요청 시작
  → 사용자는 버튼/Enter를 누를 수 있음
  → 요청 중이면 같은 요청을 기다리고, 완료됐으면 캐시 결과 사용
  → 제출 시 선택 상대 결과를 화면에 반영
```

후보가 제안 목록에 보인다는 이유만으로 모든 후보를 요청하지 않습니다. 오직 사용자가 실제로 선택한 한 명만 선조회합니다.

### 정확성 및 중복 방지

- 미리 읽은 결과 키는 프로필과 상대 이름을 모두 포함합니다.
- 자동완성 후보 선택은 입력/선택 상태와 미리 조회를 시작하되, 제출 전까지 기존 화면의 적용 상대 결과를 새 상대 결과로 바꾸지 않습니다.
- 버튼/Enter 제출은 같은 키의 진행 중 요청을 찾아 재사용합니다.
- 다른 상대를 선택하면 이전 상대의 요청 응답이 현재 선택 결과를 덮지 않도록 요청 키를 비교합니다. 불필요한 브라우저 요청은 취소할 수 있지만 DB 취소를 보장하지 않습니다.
- 선조회 실패는 오류 상태로 기록합니다. 제출 전에는 기존 프로필 정보를 유지하고, 제출 시 기존 오류 UI를 통해 실패를 알립니다. 오류를 “전적 없음”으로 표시하지 않습니다.
- API 응답은 현재 `parseProfileStatistics` 검증을 통과해야 캐시에 넣거나 화면에 적용합니다.

현재 `get_player_statistics`는 상대 전적뿐 아니라 기본 프로필 통계도 함께 반환합니다. 따라서 구현에서는 기존 응답 계약과 파서를 재사용하며, 새 RPC를 추가하거나 후보 전체의 데이터를 모으는 방식으로 확장하지 않습니다.

## 8. 화면 표시와 오류 규칙

- 캐시가 없는 첫 진입에는 현재의 명시적 최초 로딩 상태를 보여줍니다.
- 캐시가 있는 갱신 중에는 전체 화면을 비우거나 페이지 로딩 화면으로 바꾸지 않습니다.
- 새 응답은 해당 화면의 데이터를 교체합니다. 캐시가 실제로 갱신된 경우에만 해당 데이터 영역에 짧고 절제된 시각 강조를 적용하며, 화면 전체를 다시 등장시키지 않습니다. 최초 로드와 갱신 실패에는 갱신 효과가 없습니다.
- 백그라운드 갱신 실패 시 유효한 기존 데이터는 계속 보여주고, 오류를 사용자가 알 수 있는 기존 오류 UI/알림 패턴으로 표시합니다.
- 캐시가 없고 요청도 실패했으면 현재 API 오류 처리를 그대로 사용합니다.
- 오래된 상대 결과를 선택한 새 상대의 결과처럼 렌더링하지 않습니다.
- 각 API 요청은 독립적이므로 캐시의 `updatedAt`을 개별적으로 관리합니다. 서로 다른 응답이 동시에 같은 DB 시점의 스냅샷이라고 가정하지 않습니다.

## 9. 구현 내용과 완료 상태

아래 작업은 합의된 정책에 따라 구현했습니다.

1. **IndexedDB 및 캐시 API 계층:** 버전이 지정된 응답 저장소, 파서 재검증, 키별 중복 요청 공유, 캐시 우선 로드와 백그라운드 재검증을 구현했습니다.
2. **저장소 fallback:** 저장소 보존 요청, IndexedDB 미지원/오류 시 네트워크 fallback, 쓰기 실패 진단을 연결했습니다. 앱은 자체 캐시 만료나 삭제를 하지 않습니다.
3. **화면 데이터 연결:** 대시보드, 순위, 프로필 통계, 경기 페이지 데이터를 공통 캐시 계층에 연결했습니다.
4. **초기 데이터 및 상대 선조회:** 대시보드·TOP 10·경기 첫 페이지 요청을 병렬 준비하고, 사용자가 선택한 상대의 통계만 선조회해 제출 시 재사용합니다.
5. **자동완성:** 디바운스를 제거하고 캐시 결과 표시와 최신 서버 검색을 병행합니다. 캐시가 비어 있어도 서버 검색을 수행하며, 빠른 입력에서 이전 응답이 새 검색 결과를 덮지 않도록 합니다.
6. **오류 동작:** 백그라운드 갱신 실패 때 기존 유효 데이터를 유지하면서 오류를 표시합니다.
7. **갱신 모션:** 오래된 캐시를 새 응답이 대체할 때 데이터 콘텐츠 바깥에 약 1초간 은은한 청록색 빛 테두리를 표시합니다. 대시보드와 순위, 프로필의 통계 숫자는 약 0.65초간 카운트업/다운합니다. 승률 원형 게이지의 중앙 값도 갱신 시 카운트업/다운하며, 숫자와 퍼센트 기호를 한 줄로 중앙에 표시합니다. 대전 기록은 새 응답에 추가된 경기 ID의 카드만 위에서 제자리로 들어오며 청록색 테두리·빛을 약 1.2초간 표시하고, 기존 카드는 새 행 삽입에 맞춰 부드럽게 이동합니다. 최초 로드, 페이지 이동, 기존 경기의 갱신에는 새 카드 효과를 적용하지 않습니다. 막대/도넛/승률 차트는 기존 차트 전환 애니메이션을 유지합니다. 운영체제의 모션 감소 설정과 관계없이 갱신 효과를 재생합니다.
8. **문서 및 자동화 검증:** 구현 흐름은 [통계 데이터 흐름 문서](../statistics/02-data-flow.md)에 반영했습니다. 전체 테스트 36개, ESLint, TypeScript 검사와 프로덕션 빌드를 통과했습니다.

핵심 구현은 `src/lib/client-cache.ts`, `src/lib/cached-api.ts`, `src/lib/client-data-requests.ts`, `src/hooks/useCachedApi.ts`, `src/hooks/usePlayerNameSuggestions.ts`, `src/components/ui/StatusBlock.tsx`에 있습니다.

- 실제 앱에서 오래된 캐시를 새 API 응답으로 교체할 때 데이터 영역 강조를 확인했습니다. 숫자 카운터는 별도 미리보기에서 중간값을 거쳐 증가하는 동작과 모션 감소 설정에서도 재생되는 것을 확인했습니다. 대전 카드 효과는 기존 캐시와 새 응답의 경기 ID 차이를 사용하며, 최초 로드·페이지 이동·기존 경기만 바뀐 응답에서는 새 카드 강조를 하지 않습니다. 390px 모바일 뷰와 standalone 모드의 프로필 경기 목록 렌더링 및 가로 넘침이 없는 것을 확인했습니다. 실제 새 경기 응답을 주입한 카드 모션의 end-to-end 시각 확인은 별도 검증이 필요합니다.
- 브라우저에서 별도의 시각적 회귀 전수 검사는 하지 않았습니다.

## 11. 전후 비교 측정 결과

사용자 요청으로 최적화 전 폴더 `C:\1\ttt2_web_v2_pre2`와 현재 폴더의 기존 프로덕션 빌드를 각각 별도 포트에서 실행했습니다. 동일한 브라우저, 동일한 `.env.local`, 동일한 로컬 데이터 원본을 사용했습니다. 화면에 예상 경기 수가 실제 표시될 때까지를 측정했고, 브라우저 리소스 타이밍에서 API 응답 시간을 확인했습니다. 최적화 후 첫 방문 측정에서는 IndexedDB 데이터를 지웠고, 브라우저 HTTP 캐시를 비활성화했습니다. 재방문에서는 앱 캐시 동작을 유지했습니다.

현재 DB에서 확인된 데이터는 대전 172건, 플레이어 38명입니다.

| 화면/조건 | 최적화 전 | 최적화 후 | 관찰 |
|---|---:|---:|---|
| 홈, 캐시 없는 새로고침 | 5회: 361, 379, 404, 409, 411ms (중앙값 404ms) | 4회: 389, 389, 426, 956ms (중앙값 407.5ms) | 첫 표시 시간은 사실상 비슷했습니다. 최적화 후 첫 실행 956ms는 초기 서버 요청 지연의 영향을 받은 값입니다. |
| 홈 API 응답 크기 | 경기 API 약 58.8KB | 대시보드·순위·경기 첫 페이지 합계 약 6.2KB | 통계 전용 결과를 받아 응답량은 줄었습니다. |
| 프로필 통계가 있는 직접 방문 | 273~1,822ms 범위의 관측값 | 캐시 없는 방문 590ms 관측 | 실행 순서/초기화에 따라 편차가 커 반복 가능한 대표 성능값으로 간주하지 않습니다. |
| 프로필 재방문 | 기존 버전은 재방문 때도 API 요청 관찰 | 신선한 IndexedDB 캐시로 재방문 시 334ms, API 요청 0회 관찰 | 서버 응답 대기 없이 캐시 데이터를 재사용할 수 있음을 확인했습니다. |
| 프로필 API 응답량 | 전체 경기 API와 플레이어 경기 응답 합계 약 89.8KB | 대시보드·순위·경기 첫 페이지·프로필·플레이어 경기 응답 합계 약 11.2KB | 첫 방문 요청은 3종 초기 데이터 준비를 포함하므로 이전 버전과 요청 구성은 다릅니다. |

**해석:** 현재 데이터 크기에서는 초기 화면 표시 시간이 눈에 띄게 줄었다고 확인되지 않았습니다. 반면 통계 응답량 감소와 신선한 캐시 재방문 때 API 요청 생략은 관찰됐습니다. 따라서 이 측정은 네트워크 데이터 전송량과 재방문 동작 개선을 뒷받침하지만, 모든 상황에서의 체감 속도 향상을 입증하지는 않습니다.

### 측정의 한계

- 현재 데이터가 172경기이므로 이전 방식의 최대 1,000건 제한이 초과된 경우를 재현하지 못했습니다. 통계 완전성의 전후 비교는 이 측정 범위에 포함되지 않습니다.
- 기존 `.next` 빌드 산출물을 실행했습니다. 기존 빌드 생성 시점은 최적화 전 폴더가 2026-09-30, 현재 폴더가 2026-10-02였습니다. 두 `BUILD_ID`가 다르며, 비교 전 폴더에는 `ProfileView.tsx`, `useProfileStatistics.ts`의 미커밋 변경도 있었습니다.
- 초기 로딩, DB/로컬 API 응답, 브라우저 렌더링, 개발자 도구 상태가 측정값에 영향을 줄 수 있습니다. 반복 횟수도 제한적이고 양쪽 횟수가 같지 않아 엄밀한 통제 실험이 아닙니다.
- 로컬 프로덕션 빌드 측정이므로 실제 운영 서버·사용자 기기·네트워크에서의 성능을 보장하지 않습니다.
- 부하 테스트, 대규모 데이터 테스트, 장시간 캐시 유지 테스트는 수행하지 않았습니다.

### 최신성 리스크와 완화

IndexedDB에 저장된 모든 API 응답은 저장 후 DB가 바뀌면 오래된 값이 될 수 있습니다. 자동완성에만 생기는 문제가 아니라, 사용자가 추가한 기록/경기 때문에 다음 값이 잠시 최신 상태와 다를 수 있습니다.

| 데이터 | 캐시가 오래됐을 때 가능한 현상 | 완화 |
|---|---|---|
| 자동완성 | 새 플레이어가 캐시 제안에 없거나, 최근 삭제/이름 변경된 이름이 남을 수 있음 | 캐시로 결과 없음을 확정하지 않고 매번 서버 검색. 성공 응답으로 교체. 서버 오류 시 오래된 임시 결과임을 표시 |
| 대시보드·TOP 10 | 새 경기로 합계나 순위가 바뀌었는데 캐시가 먼저 표시될 수 있음 | 표시 가능한 캐시는 유지하되 stale 상태를 구분하고 백그라운드 재검증. 온라인 조회 실패를 최신 데이터인 것처럼 감추지 않음 |
| 프로필/상대 전적 | 새 경기가 추가되어 승률·상대 결과가 바뀌었어도 캐시가 잠시 이전 값일 수 있음 | 요청 키별로 보관하고 stale-while-revalidate. 선택한 상대 키와 다른 상대 결과를 섞지 않음 |
| 페이지별 경기 목록 | 새 경기 추가로 최신순 페이지 경계가 이동할 수 있음. 서로 다른 시점에 저장된 페이지를 이어 보면 중복/누락처럼 보일 수 있음 | 현재 요청 페이지를 재검증하고 페이지 키/시점을 구분. 페이지 간 일관성이 필요한 이동에서는 관련 페이지를 무효화/재검증하는 정책을 구현 시 확정 |

캐시만 사용해 서버를 영구히 조회하지 않으면 새 정보가 빠지는 상태가 계속될 수 있습니다. 이 계획은 캐시를 첫 표시용으로 사용하고 정해진 네트워크 재검증을 수행해 이 위험을 줄입니다. 그러나 오프라인, API 오류, 백그라운드 갱신 실패 중에는 캐시가 최신이라고 보장할 수 없습니다. 갱신 중 별도 표시는 하지 않되 실패는 사용자에게 알리고, 캐시를 DB 원본이나 동기화 저장소로 설명하면 안 됩니다.

## 12. 범위 밖/미확정

- 브라우저 간/기기 간 캐시 동기화: IndexedDB는 각 브라우저의 로컬 저장소이며 동기화하지 않습니다.
- Service Worker의 API 캐시: 이번 계획은 IndexedDB 앱 캐시를 대상으로 하며, 별도 HTTP 캐시 정책을 추가하지 않습니다.
- 앱은 IndexedDB 캐시를 자동 만료·삭제하지 않으며, 다른 사이트/앱의 저장 데이터를 삭제해 용량을 확보하지 않습니다. 브라우저에 저장 공간 보존을 요청하지만 허용 여부나 실제 보존은 보장되지 않습니다. 이 보관 선호와 검색 결과의 신선도는 별개이며, 자동완성은 검색할 때마다 서버에서 재검증합니다.
- 자동완성 최소 검색 글자 수: 미확정이며 이번 결정은 기존 비어 있지 않은 검색어의 즉시 조회입니다.
- 화면 갱신 모션은 새 서버 응답이 기존 캐시 데이터를 실제로 대체할 때만 재생합니다. 캐시 없는 최초 로드, 내용이 바뀌지 않은 신선 캐시 재사용, 갱신 실패에는 표시하지 않습니다. 대전 목록에서는 이때 새로 추가된 경기 카드만 강조·등장 모션을 재생하고, 숫자는 카운트하지 않습니다. 사용자가 별도로 요청해 운영체제의 모션 감소 설정과 관계없이 짧은 효과를 재생합니다.
- 새 통계 RPC 추가, 집계 규칙 변경, 전체 경기 행 브라우저 전송: 범위에 포함하지 않습니다.
