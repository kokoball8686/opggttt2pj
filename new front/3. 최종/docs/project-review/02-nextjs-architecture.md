# Next.js 아키텍처 관점 리뷰

## 1. 핵심 문제

이 프로젝트는 Next.js App Router를 사용하고 있는 듯 보이지만, 실제로는 클라이언트 중심 SPA에 가깝게 동작한다. 대부분 페이지가 `"use client"` 를 사용하고 있고, 데이터 패칭도 클라이언트 훅에서 수행되면서 서버/클라이언트 경계가 흐려졌다.

## 2. 가장 큰 구조 문제: 거의 모든 페이지가 클라이언트 컴포넌트

주요 파일들:

- [src/app/page.tsx](../../src/app/page.tsx)
- [src/app/matches/page.tsx](../../src/app/matches/page.tsx)
- [src/app/players/page.tsx](../../src/app/players/page.tsx)
- [src/app/profile/[name]/page.tsx](../../src/app/profile/[name]/page.tsx)
- [src/app/download/page.tsx](../../src/app/download/page.tsx)

이런 페이지들은 대부분 `"use client"` 로 선언된다. 이는 Next.js에서 클라이언트 컴포넌트를 의미하며, 서버 컴포넌트의 장점을 대부분 포기하는 선택이다.

### 서버 컴포넌트의 장점

- 서버에서 데이터를 직접 가져올 수 있다.
- HTML이 빠르게 초기 렌더링된다.
- SEO와 초기 로딩 성능이 좋아진다.
- 클라이언트 쪽 번들 부담을 줄일 수 있다.
- 캐시와 데이터 재사용을 설계할 수 있다.

### 현재 프로젝트에서의 문제

- 데이터 로딩이 기본적으로 클라이언트에서 발생한다.
- 초기 HTML이 거의 의미가 없다.
- 로딩 상태가 브라우저에서 생성되므로 화면 점프가 많다.
- 서버 기반 성능 최적화를 제대로 활용하지 못한다.

즉, 프로젝트는 "Next.js 앱처럼 보이지만, 실제로는 브라우저 SPA에 가깝다." 는 평가를 받기 쉽다.

## 3. 라우트 파일과 UI 파일이 기능적으로 섞여 있다

예를 들어 [src/app/page.tsx](../../src/app/page.tsx) 는 단순 페이지 컴포넌트가 아니라 대시보드 전체 구조를 담당한다.

그 안에는 다음이 모두 섞여 있다.

- 데이터 조회
- 상태 관리
- 계산 로직
- 차트 조립
- 최근 대전 표시
- 페이지형 레이아웃 전체

이건 페이지 컴포넌트가 너무 많은 책임을 맡고 있다는 의미다.

### 기준

현업 기준으로는 보통 이런 식이다.

- page.tsx: 레이아웃 조립만
- DashboardSection.tsx: 홈 대시보드 조립
- useDashboardData.ts: 데이터 fetching 로직
- stats.ts: 계산 로직

현재 구조는 이 분리가 약하다.

## 4. 데이터 fetch 경계가 흐려진다

[src/hooks/useMatches.ts](../../src/hooks/useMatches.ts) 는 클라이언트에서 fetch를 수행하고, API route도 별도로 존재한다. 이 구조는 기능적으로는 동작하지만 Next.js 설계로는 약하다.

### 문제

- 서버 API와 클라이언트 렌더링 경계가 불명확하다.
- 서버 컴포넌트와 클라이언트 컴포넌트의 역할이 섞여 있다.
- 변경 시 서버 데이터 입출력과 UI가 동시에 영향받는다.

### 면접용 지적 포인트

> “이 앱은 Next.js를 쓰고 있지만, 서버 vs 클라이언트 책임 분리가 아직 약합니다. 결과적으로 App Router의 장점을 충분히 살리지 못하고 있습니다.”

## 5. 서버 컴포넌트로 나아갈 수 있는 부분이 많이 남아 있다

현재 코드는 다음 부분을 서버 컴포넌트로 옮길 수 있다.

- 정적 데이터 계산
- 서버 데이터 fetch
- 기본 메타 데이터 렌더링
- 조회 결과 기반의 서버사이드 계산
- 일부 사용자 인터랙션을 제외한 화면 구조

대신 거의 대부분을 client 컴포넌트로 두고 있으니, 실제 Next.js의 장점이 사라졌다.

## 6. 수동 fetch의 문제

`fetch`를 클라이언트에서 직접 반복하는 구조는 기능적으로는 가능하지만, 다음 문제가 있다.

- 캐시 전략을 설계하기 어렵다.
- 로딩 상태 관리가 중복된다.
- 사용자 경험이 불안정해진다.
- route segment에 대한 구조 설계가 약하다.

## 7. 면접에서 가장 많이 지적될 문장

다음 표현이 정확히 맞다.

> “이 프로젝트는 Next.js 프로젝트처럼 보이지만, 사실상 클라이언트 중심의 SPA 구조를 유지하고 있습니다. 서버 컴포넌트와 클라이언트 컴포넌트의 역할 분리가 약하고, App Router의 이점을 충분히 활용하지 못하고 있습니다.”

## 8. 개선 포인트

다음이 우선이다.

1. 정적 페이지/메인 화면을 서버 컴포넌트로 전환
2. 데이터 fetch 로직을 서버 또는 route layer로 이동
3. page.tsx는 조립용으로만 유지
4. client component는 상호작용이 필요한 최소 영역으로 제한
5. 화면 단위로 컴포넌트 분리

---

## 9. 결론

이 프로젝트는 Next.js라기보다, 클라이언트 중심 웹앱 구조를 갖고 있다. 기능은 동작하지만, Next.js의 설계 사고가 약한 상태다.

이건 심각한 실수라기보다, 구조적 이해와 스타일 설계가 아직 정리되지 않은 상태로 보인다. 특히 Tailwind는 원래 의도했던 표준 스타일 스택이었으므로, 앞으로는 이를 중심으로 구조와 전역 CSS를 정리해야 한다.
