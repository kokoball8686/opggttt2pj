# 유지보수 규칙: 구조를 깨지 않는 작업 원칙

## 1. 목적

이 문서는 프로젝트가 다시 "모놀리식 구조"로 돌아가는 것을 막기 위한 실전 규칙을 정리한 문서다.

핵심 원칙은 간단하다.

- 페이지는 얇게 유지한다.
- UI는 컴포넌트로 분리한다.
- 데이터 로직은 hook / lib로 분리한다.
- 스타일은 Tailwind 우선으로 처리한다.
- 전역 CSS는 최소한만 사용한다.
- 한 번에 너무 많은 책임을 한 파일에 넣지 않는다.

---

## 2. 기본 원칙

### 2.1 Route 파일은 얇게 유지

Route 파일은 그 페이지의 조립만 담당해야 한다.

좋은 예:

- [src/app/page.tsx](../../src/app/page.tsx)
- [src/components/dashboard/DashboardHome.tsx](../../src/components/dashboard/DashboardHome.tsx)

기본 규칙:

- 데이터 fetch 로직을 route 안에 직접 넣지 않는다.
- 계산 로직을 route 안에 직접 넣지 않는다.
- UI 섹션을 한 파일 안에 모두 몰아넣지 않는다.

금지 패턴:

- route 파일 안에 차트, 리스트, 상태 관리, 계산 로직이 모두 섞여 있는 것
- page.tsx 안에서 레이아웃 + 데이터 + 스타일 + 차트가 모두 처리되는 것

---

### 2.2 UI는 반드시 컴포넌트 단위로 분리

다음처럼 역할별로 나눈다.

- 레이아웃: [src/components/layout/AppShell.tsx](../../src/components/layout/AppShell.tsx)
- 네비게이션: [src/components/layout/SidebarNav.tsx](../../src/components/layout/SidebarNav.tsx)
- 상단 바: [src/components/layout/TopBar.tsx](../../src/components/layout/TopBar.tsx)
- 대시보드: [src/components/dashboard/DashboardHome.tsx](../../src/components/dashboard/DashboardHome.tsx)
- 차트: [src/components/charts/Charts.tsx](../../src/components/charts/Charts.tsx)
- 매치 리스트: [src/components/matches/MatchList.tsx](../../src/components/matches/MatchList.tsx)

규칙:

- 한 컴포넌트는 하나의 책임만 가진다.
- 페이지 전체를 하나의 컴포넌트로 합치지 않는다.
- 중복 UI는 공용 컴포넌트로 추출한다.

---

### 2.3 데이터 로직은 hook / lib로 분리

데이터 확인, 캐싱, 정제, 집계 로직은 UI와 분리해야 한다.

예시:

- [src/hooks/useMatches.ts](../../src/hooks/useMatches.ts)
- [src/lib/stats.ts](../../src/lib/stats.ts)

규칙:

- UI 컴포넌트 안에 fetch, cache, aggregation 코드가 섞이지 않도록 한다.
- 계산 로직은 lib에 두고, UI는 결과만 소비한다.
- API 응답 처리와 비즈니스 로직을 route와 섞지 않는다.

---

### 2.4 스타일은 Tailwind 우선

이 프로젝트는 Tailwind를 기본 스타일 전략으로 정했다.

원칙:

- 기본 UI는 Tailwind utility로 작성한다.
- 전역 CSS는 reset, token, base 스타일만 남긴다.
- 각 컴포넌트의 세부 스타일은 해당 컴포넌트에 가깝게 작성한다.

기본 파일:

- [src/app/globals.css](../../src/app/globals.css)

여기서 허용되는 것은 다음 정도다.

- CSS reset
- 전역 배경
- 기본 폰트 설정
- 일부 공통 토큰
- 정말 전역적으로 필요한 스타일

다음은 금지다.

- 레이아웃 전체를 globals.css에 몰아넣기
- 컴포넌트별 스타일을 한 파일에 잔뜩 쌓기
- "이런건 그냥 globals.css에 추가하면 되지"라는 사고

---

## 3. 금지 패턴

다음 패턴은 구조를 다시 무너뜨리는 대표적 행동이다.

### 3.1 전역 CSS 덩어리화

예시 문제:

- 페이지를 수정할 때 globals.css를 열어 수백 줄 추가
- 하나의 클래스가 서로 다른 화면을 모두 제어함
- 특정 페이지의 UI가 전역 스타일에 종속됨

해결법:

- 해당 컴포넌트로 스타일 이동
- Tailwind utility 로 대체
- 필요한 경우 작은 공용 컴포넌트로 분리

---

### 3.2 route 파일이 뚱뚱해짐

예시 문제:

- page.tsx 안에서 데이터 계산, 차트 생성, modal 제어, 데이터 fetch까지 모두 함

해결법:

- 로딩/에러 상태는 공용 컴포넌트로
- 차트는 별도 파일로
- 계산 로직은 lib로
- modal은 별도 컴포넌트로

---

### 3.3 UI와 데이터 로직이 섞임

예시 문제:

- 컴포넌트 안에 API 호출과 계산 함수가 섞여 있음
- props 의존성이 늘어나고 테스트가 어려워짐

해결법:

- hook으로 데이터 로직 분리
- 컴포넌트는 렌더링만 담당
- 필요시 util 함수로 계산 로직 분리

---

## 4. 수정 시 작업 규칙

### 4.1 작업 전 확인

수정 전에 반드시 다음을 확인한다.

- 이 기능은 route 파일을 건드려야 하는가?
- 아니면 컴포넌트만 수정하면 되는가?
- 계산 로직을 추가해야 하는가?
- 전역 스타일이 필요한가?

---

### 4.2 수정 범위 원칙

권장 원칙: 한 작업 당 영향 범위가 작아야 한다.

예시:

- 버튼 스타일 수정 → 해당 컴포넌트 파일만 변경
- 대시보드 데이터 변경 → hook/lib + dashboard 컴포넌트 고려
- 전역 배경 보정 → globals.css로 최소한만

기본 규칙:

- 2개 이상의 페이지 파일을 동시에 수정하는 것은 신중하게 판단한다.
- 공용 스타일을 고치기 전에, 해당 공용 스타일이 정말 전역이어야 하는지 검토한다.

---

### 4.3 확인 절차

각 수정 후에는 다음을 확인한다.

1. 테스트 실행
2. 빌드 실행
3. 구조 유지 여부 점검
4. 전역 CSS 남용 여부 점검
5. 다시 모놀리식으로 돌아가는지 점검

---

## 5. AI 작업용 체크리스트

다음 체크리스트를 통과해야만 수정이 안전하다고 판단한다.

- [ ] Route 파일이 너무 두꺼워지지 않았는가?
- [ ] 컴포넌트 책임이 분리되어 있는가?
- [ ] 전역 CSS를 과하게 늘리지 않았는가?
- [ ] Tailwind를 우선적으로 활용했는가?
- [ ] logic과 UI가 섞이지 않았는가?
- [ ] 수정 범위가 작고 명확한가?
- [ ] 기존 구조를 유지했는가?

하나라도 부족하면 작업을 중단하고 구조를 다시 설계해야 한다.

---

## 6. 현업 기준의 판단 기준

이 프로젝트가 실서비스에 적합하게 유지되려면 다음을 만족해야 한다.

- 라우트 파일이 빠르게 늘어나지 않는다.
- 전역 스타일이 과거처럼 커지지 않는다.
- 컴포넌트가 재사용 가능한 단위로 나뉜다.
- 데이터를 다루는 로직과 화면 로직이 분리된다.
- 구조적 수정이 빠르고 안정적으로 가능하다.

이 조건이 만족되면, 이 프로젝트는 리팩터링 이후에도 유지보수 가능한 상태로 남는다.

---

## 7. 결론

리팩터링은 단순히 "코드가 보기 좋다"가 아니라,
"다음 사람이 안전하게 수정할 수 있는 구조를 남기는 것"이다.

즉, 이 문서의 핵심 규칙은 다음 한 줄이다.

> 구조를 깨지 않는 수정만 한다.

이 원칙만 지켜도 프로젝트는 다시 모놀리식으로 돌아가지 않는다.
