# 데이터 흐름과 라우팅 설계 리뷰

## 1. 전체 구조의 핵심

현재 프로젝트의 구조는 다음과 같이 이해할 수 있다.

- 루트 페이지와 각 라우트에서 데이터를 가져온다.
- 커스텀 Hook이 데이터 로딩을 담당한다.
- Route Handler가 Supabase와 통신한다.
- lib/stats에서 계산 로직을 처리한다.
- UI 컴포넌트들이 결과를 렌더링한다.

이 구조 자체는 괜찮다. 문제는 이 흐름이 실제로 "명확한 Next.js 계층 구조"를 유지하고 있느냐는 점이다.

## 2. 데이터 fetch가 클라이언트 중심으로 몰려 있다

주요 파일:

- [src/hooks/useMatches.ts](../../src/hooks/useMatches.ts)
- [src/hooks/useMatches.ts](../../src/hooks/useMatches.ts)
- [src/app/api/matches/route.ts](../../src/app/api/matches/route.ts)
- [src/app/api/matches/player/route.ts](../../src/app/api/matches/player/route.ts)

이 구조는 동작은 한다. 정석적인 클라이언트 fetch 훅처럼 잘 보이기도 한다.

하지만 Next.js의 장점을 제대로 살리려면 다음과 같은 흐름이 맞다.

- 서버 컴포넌트가 page에서 데이터를 가져온다.
- 클라이언트는 상호작용이 필요한 컴포넌트에만 제한된다.
- Route Handler는 서버 사이드 인프라로만 사용된다.

현재 코드에서는 client component가 많은 비중을 차지하면서, 이 흐름이 무너지기 쉽다.

## 3. API route는 존재하지만, 페이지 데이터 구조와 일관되지 않다

Route Handler가 있어도, UI가 대부분 client component이면 그 API의 의미가 약해진다.

### 현재 구조의 문제

- API route는 서버의 데이터 access layer 역할을 하고 있으나
- 실제 페이지는 그걸 클라이언트에서 다시 불러오는 구조로 보임
- 서버 우선 설계와 클라이언트 우선 설계가 섞여 있음

이건 구조적으로 분리 부족을 의미한다.

## 4. 데이터 로딩 상태 관리가 반복적으로 보인다

Hook 파일을 보면 로딩, 에러, 캐시 상태가 반복된다.

문제는 반복 구조 자체가 아니라, 그것이 페이지마다 비슷하게 구현되어 있다는 점이다.

### 즉,

- useMatches
- usePlayerMatches
- ProfilePage 내부 로직
- other page local state

이렇게 여러 곳에 비슷한 데이터 흐름이 흩어져 있다.

이 구조는 작은 프로젝트에서는 빠르게 만들 수 있지만, 확장성 측면에서 약하다.

## 5. 로딩과 에러 처리의 기준이 불명확하다

예:

- [src/components/ui/StatusBlock.tsx](../../src/components/ui/StatusBlock.tsx)

이 컴포넌트는 로딩과 에러 상태를 핸들링하는 용도로 보이지만, 각 페이지마다 조금씩 다른 방식으로 사용되고 있다.

### 문제

- 에러 처리 기준이 페이지마다 다르다.
- 공통 에러 boundary가 없다.
- 데이터 fetch 실패 시 어떤 UI를 보여줘야 하는지 책임이 모호하다.

면접에서 많이 듣는 질문:

> “에러 상태와 로딩 상태를 어디서 표준화해야 하나?”

현재는 일부 표준화가 있지만, 전체적으로는 약하다.

## 6. 라우팅은 App Router 기반이지만, 실제로는 페이지 단위 SPA처럼 동작한다

이 프로젝트는 실제 URL이 `/players`, `/matches`, `/profile/[name]` 구성으로 되어 있다. 이런 라우트 구조는 정상적이다.

하지만 내부 데이터 흐름이 client side 중심이라면, 전체 앱은 실제로는 path 전환이 아니라 state 전환이 많이 섞인 UI처럼 보일 수 있다.

### 결과

- URL은 App Router처럼 보이지만, 실제 동작은 SPA에 가까움
- 상태 재사용이 약함
- 경계가 모호함

이건 마이크로 아키텍처의 문제로 이어진다.

## 7. 서버와 클라이언트 책임이 불명확한 이유

가장 큰 이유는 다름 아닌 사용자 상호작용과 데이터 로딩이 모두 클라이언트에 집중되어 있기 때문이다.

### 이런 구조는 다음을 만든다.

- 페이지의 상태 로직이 비대해짐
- 데이터 fetch와 렌더 로직이 뒤섞임
- 서버 이점을 살리지 못함
- cache layer 설계가 어려워짐

## 8. 개선 포인트

다음이 가장 현실적인 개선 방향이다.

1. 서버에서 데이터를 가져오는 페이지 컴포넌트 우선 설계
2. 클라이언트 컴포넌트는 필요한 상호작용만 남기기
3. Hook을 단순화해 데이터 fetch 구현을 통일
4. 공통 loading/error boundary 구성
5. 라우트별 데이터 책임을 명확하게 분리

## 9. 결론

이 프로젝트는 데이터 흐름의 기본형은 갖추고 있지만, Next.js의 서버/클라이언트 경계를 명확하게 설계하지 못했다. 기능적으로는 동작하지만, 구조적으로는 전반적으로 클라이언트 중심으로 쏠려 있는 상태다.

이 부분은 면접에서 구조적 문제로 자주 떠오르는 지점이며, 동시에 Tailwind 역시 원래 의도했던 표준 스택이었음에도 실행에서 빠르게 누락된 점이 함께 드러난다. 앞으로는 서버/클라이언트 경계 정리와 Tailwind 표준화가 동시에 필요한 작업이다.
