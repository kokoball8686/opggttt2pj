# 컴포넌트 구조와 CSS 설계 리뷰

## 1. 컴포넌트 분리 상태는 부분적이다

이 프로젝트는 이미 여러 컴포넌트 파일들이 있다. 예를 들어:

- [src/components/layout/AppShell.tsx](../../src/components/layout/AppShell.tsx)
- [src/components/charts/Charts.tsx](../../src/components/charts/Charts.tsx)
- [src/components/matches/MatchList.tsx](../../src/components/matches/MatchList.tsx)
- [src/components/search/PlayerSearch.tsx](../../src/components/search/PlayerSearch.tsx)
- [src/components/pwa/PwaControls.tsx](../../src/components/pwa/PwaControls.tsx)

이것 자체는 좋은 신호다. 단순히 페이지 안에 모든 UI가 박혀 있지는 않다.

하지만 문제는 그 컴포넌트들이 "완전히 역할별로 잘 분리되었는가"이다.

## 2. 페이지 컴포넌트가 너무 많은 책임을 가지는 문제

예:

- [src/app/page.tsx](../../src/app/page.tsx)

이 페이지는 다음을 동시에 수행한다.

- 데이터 조회
- 상태 값 선언
- 계산 처리
- 차트 조립
- 리스트 렌더링
- 페이지 제목/설명 구성
- 맵 모달 제어
- 최근 경기 섹션 조립

이런 식으로 한 페이지 파일이 여러 책임을 맡으면, 재사용성과 유지보수성이 떨어진다.

### 면접에서 보이는 문제

> “이 파일이 페이지인지, 페이지 내부 로직 모듈인지 애매합니다.”

이 문장은 매우 자연스럽다.

## 3. 공용 스타일이 전역으로 과도하게 몰려 있다

대표 파일:

- [src/app/globals.css](../../src/app/globals.css)

이 파일에는 거의 모든 클래스가 모여 있다.

### 포함되는 내용

- 전체 레이아웃
- 헤더와 사이드바
- 검색 UI
- 네비게이션
- 카드
- 차트
- 대전 리스트
- 프로필 UI
- 반응형 쿼리
- PWA 설치 안내
- 모달

이런 구조는 한 번에 모든 스타일을 관리하기 편하다는 장점이 있지만, 동시에 많은 문제를 유발한다.

### 문제점

- 스타일 간 충돌 가능성이 높다.
- 특정 컴포넌트 수정 시 전역 영향이 크다.
- CSS가 재사용이 아니라 덩어리로 남아 있다.
- 클래스명이 의미적으로 일관되지 않을 수 있다.
- 다른 컴포넌트와의 스타일 의존성이 커진다.

## 4. Tailwind는 원래 계획이었고, 지금은 반드시 정착시켜야 한다

설정 파일 중에는 Tailwind가 있다.

- [package.json](../../package.json)
- [postcss.config.mjs](../../postcss.config.mjs)

중요한 점은, 이 프로젝트는 Tailwind를 아예 안 쓰는 방향으로 설계된 것이 아니라, 구현 과정에서 빠르게 넘어가면서 실제로는 전부 custom CSS 기반이 되었다는 점이다.

즉, 이는 "의도된 기술 스택이었지만 실행 누락이 있었다"는 뜻이며, 지금은 이를 바로잡아야 한다.

### 왜 문제인가

Tailwind가 빠져 있으면 다음 문제가 발생한다.

- 스타일 규칙이 전역화되기 쉽다.
- 컴포넌트 재사용이 어려워진다.
- 일관된 디자인 토큰을 관리하기 어렵다.
- 반응형 스타일이 중복될 가능성이 높다.

결과적으로, 프로젝트는 "디자인 시스템이 없다"는 인상을 준다.

### 앞으로의 기준

이제는 Tailwind를 선택지가 아니라 표준으로 받아들여야 한다.

- 전역 CSS는 reset, 토큰, 기본 스타일 중심으로 축소
- 컴포넌트 스타일은 Tailwind utility 기반으로 정리
- page와 globals.css에서 직접적인 스타일 덩어리 구성은 최소화
- 디자인 시스템과 spacing, color, typography를 Tailwind 기준으로 통일

이렇게 해야 구조와 일관성이 동시에 유지된다.

## 5. 스타일 구조가 비효율적이다

현업 수준에서 style은 보통 다음 단계로 나뉜다.

- 전역 reset/토큰
- 공용 레이아웃 스타일
- 컴포넌트별 스타일
- 페이지별 스타일

하지만 현재는 전역 스타일이 너무 큰 비중을 차지하고 있다. 즉, 디자인 시스템이 아니라, "모든 스타일을 한 군데 몰아놓은 상태"다.

## 6. 컴포넌트가 잘 분리되어 있지 않은 이유

여기서 핵심은 단순히 파일 수가 많은 것이 아니라, 파일의 책임이 명확한가 여부다.

### 현재 상태의 약점

- 많은 컴포넌트가 이미 있으나, page와 globals에 계속 연결되는 구조
- 특정 UI가 페이지와 공유 CSS에 의존하게 됨
- 실제 재사용 단위가 약함

이 말은, "분리 자체는 있었지만, 실질적인 모듈화는 부족했다"는 뜻이다.

## 7. 면접에서 보이는 질문

면접관은 보통 이런 질문을 한다.

- 이 프로젝트가 Tailwind를 왜 쓰지 않는가?
- 공용 스타일이 전역이 아니라면 어디까지가 공용인지 설명 가능하나?
- 페이지 컴포넌트가 너무 크지 않은가?
- 재사용 가능한 작은 컴포넌트로 나누려면 어디를 쪼개야 하는가?
- CSS 충돌 방지 전략이 있는가?

이런 질문에 대한 설명이 약하면, 구조적 신뢰도가 급격히 낮아진다.

## 8. 개선 방향

권장 사항은 다음과 같다.

1. globals.css를 "토큰 + reset + base" 수준으로 축소
2. 공용 레이아웃/컴포넌트별 스타일을 컴포넌트 파일 수준으로 분리
3. 페이지별 스타일은 해당 페이지로 국한
4. Tailwind 도입 여부를 명확히 결정
5. 페이지 내부 섹션을 작은 컴포넌트로 분해

## 9. 결론

이 프로젝트는 이미 여러 컴포넌트를 나누었지만, 전역 CSS와 페이지 조립 방식 때문에 결국 큰 구조를 유지하고 있다. 즉, "분리된 컴포넌트가 많다"는 사실 자체보다, "그 컴포넌트가 실제로 재사용 가능한 구조인지"가 더 중요하다.

현재는 그 부분이 약하다.
