# TAG2.GG 프론트엔드 발전 상세 자료

> 이 문서는 TAG2.GG 프론트엔드의 1단계부터 5단계까지를 상세히 설명하는 내부 작성 자료다. 인쇄용 최종본이 아니라, 이후 최종 문서를 만들 때 활용할 수 있도록 배경, 설계 의도, 실제 코드에서 확인한 구조, 데이터 계약, 검증 결과와 한계를 가능한 한 구체적으로 모아 둔다.
>
> 단계 번호는 프로젝트 소유자가 정한 역사 구분을 따른다. 폴더명의 `v2` 같은 문자열은 단계 번호를 뜻하지 않는다.

## 1. 이 문서가 설명하는 프로젝트와 범위

TAG2.GG는 RPCS3에서 실행되는 *Tekken Tag Tournament 2*의 경기 결과를 웹에서 확인할 수 있게 하는 서비스다. 게임에서 직접 데이터를 수집하는 트래커와 경기 기록을 저장하는 데이터베이스가 있고, 이 문서는 그중 사용자가 대전 기록·통계·플레이어 정보를 보는 프론트엔드의 발전을 기록한다.

프론트엔드의 다섯 단계는 다음과 같이 구분한다.

1. **1단계 — 바닐라 웹:** HTML, CSS, JavaScript로 만든 초기 웹앱.
2. **2단계 — 초기 Next.js:** Next.js로 옮겼지만 실제 구현에서는 모놀리식 구조와 데이터 범위 문제가 이어진 웹앱.
3. **3단계 — Next.js 구조 리팩터링:** 2단계의 구조적 실패를 반복하지 않도록 라우팅, 컴포넌트, 데이터 코드와 스타일링을 다시 정리한 버전.
4. **4단계 — 통계 데이터 보완:** 기록이 크게 늘어도 통계가 조회 상한에 잘리지 않도록 통계 집계와 경기 목록 조회의 데이터 경로를 재설계한 버전.
5. **5단계 — 캐시 중심 최종 결과:** 4단계의 데이터 정확성 구조를 유지하면서 캐시와 요청 재사용을 통해 일부 화면의 재방문·갱신 대기를 줄인 현재 결과물.

이 구분은 기능을 한 번에 전부 새로 만든다는 의미가 아니다. 앞 단계에서 만들어 둔 기능을 이어받기도 하고, 다른 단계에서 구조만 다시 만들거나 데이터 처리의 특정 문제를 따로 해결하기도 했다. 특히 다음 두 축은 서로 구분해야 한다.

- **구조 품질 축:** 모놀리식 코드에서 책임별 모듈·라우팅·스타일 구조로 이동한 일.
- **데이터 정확성 및 성능 축:** 전체 대상 통계를 빠짐없이 계산하는 일과, API 응답을 캐시해 다시 쓰는 일.

Next.js를 도입한 것만으로 데이터가 완전해지는 것은 아니고, DB에서 정확한 통계를 계산한다고 해서 클라이언트 재방문이 자동으로 빨라지는 것도 아니다. 이 프로젝트는 그 문제들을 각기 다른 단계에서 다뤘다.

## 3. 서비스 데이터의 기본 흐름

프론트엔드의 각 단계가 다루는 경계는 다음 구조로 이해할 수 있다.

```text
RPCS3에서 경기 발생
  → 별도 Tracker가 경기 결과를 감지
  → 경기 정보를 Supabase PostgreSQL에 저장
  → TAG2.GG 프론트엔드가 REST/RPC 경로로 조회
  → 경기 목록 또는 통계 UI에 표시
```

프론트엔드는 트래커가 게임 메모리를 읽는 과정의 소유자가 아니다. 이 문서에서 다루는 주요 프론트엔드 책임은 저장된 기록을 읽고, 플레이어/경기/캐릭터/맵을 올바르게 해석해 화면에 제공하는 것이다.

Supabase의 `matches` 레코드에는 일반적으로 경기 ID, 두 플레이어 이름과 점수, 양 플레이어의 메인·서브 캐릭터 ID, 맵 ID, 승자, 시작·종료 시각, 등록 시각 등이 포함된다. 실제 데이터에는 과거 기록의 `map_id = NULL` 같은 값이 존재할 수 있으므로, `0`을 무조건 결측치로 처리하거나 NULL을 임의의 유효 값으로 바꾸면 안 된다. 프론트엔드는 ID를 캐릭터·맵 이름 및 이미지에 연결하지만, 통계 단계에서는 분모·NULL 처리·시간대 같은 도메인 규칙을 별도로 유지해야 한다.

## 4. 1단계 — HTML·CSS·JavaScript 바닐라 웹

### 4.1 구현 형태

초기 버전은 Next.js나 React 없이 HTML, CSS, 브라우저 JavaScript로 만든 정적 웹앱이었다. 실제로 확인한 폴더는 `C:\1\yyy\1. html+css 바닐라 버전`이며, 중요한 파일 크기와 형태는 다음과 같다.

| 항목 | 확인한 내용 |
|---|---|
| `index.html` | 약 58 KB, 929줄 |
| `css/main.css` | 약 36 KB |
| `css/components.css` | 약 5 KB |
| `manifest.json` | PWA 메타데이터 파일 |
| `sw.js` | Service Worker 파일 |
| 정적 이미지 자산 | `assets` 폴더 내 캐릭터·아이콘 등의 자산 |

따라서 “CSS 파일이 문자 그대로 하나뿐이었다”는 뜻이 아니라, **대부분의 화면 스타일을 큰 CSS 파일에 모으고 HTML/JavaScript도 큰 진입 파일에 집중시킨 모놀리식 성격의 구현**으로 이해하는 것이 정확하다. 당시 파일을 빠르게 수정하기는 단순했지만, 기능이 늘어날수록 화면 구조·데이터 처리·상태 전환이 서로 강하게 엮였다.

### 4.2 화면과 주요 기능

초기 웹앱에서 확인된 주요 사용자 기능은 다음과 같다.

- 홈 대시보드에서 전체 경기와 플레이어 현황, 픽률·조합 등 통계 표시.
- TOP 10 플레이어 랭킹.
- 플레이어 닉네임 검색과 추천.
- 플레이어 프로필 요약과 대전 기록.
- 상대 전적 검색.
- 전체 대전 기록과 개인 경기 기록.
- 결과·점수·두 플레이어·캐릭터·맵·시각 정보 표시.
- 결과 정렬과 페이지 이동.
- Tracker 다운로드 경로.
- PWA manifest와 Service Worker를 통한 설치 가능 웹앱 구성.

화면 이동은 URL의 `#home`, `#players`, `#matches`, `#profile/...` 같은 해시 값에 의존했다. 브라우저는 같은 정적 페이지를 유지하고 스크립트가 해당 화면을 표시하는 구조였다.

### 4.3 데이터 요청과 통계 계산

`index.html` 내부 JavaScript는 Supabase REST 요청을 직접 실행했다. 예를 들어 대시보드 기록 요청은 경기 컬럼을 지정하고 `created_at.desc`로 정렬한 뒤 `limit=1000`을 사용했다. 브라우저에서 이 응답을 받아 플레이어별 수치, 랭킹, 캐릭터 분포 등의 계산과 화면 렌더링에 활용했다.

이 구조에서 조회 요청의 결과 배열은 “Supabase의 모든 경기”가 아니라 “해당 요청에서 반환된 최대 1,000행”이다. 통계가 그 배열을 전체 데이터로 취급하면 실제 기록이 더 많아지는 순간 뒤쪽 기록이 계산에서 빠질 수 있다. 이 위험은 1단계부터 데이터 경로의 특성으로 존재했으며, 2단계에서도 계속 확인된다.

초기 HTML은 Supabase URL과 공개 조회용 키를 사용해 브라우저에서 직접 API를 호출하는 방식이었다. 공개 키는 비밀 서비스 권한 키와 동일하지 않으며, 권한은 DB 정책에 의존한다. Next.js 전환 계획에서는 키를 환경변수로 다루는 방법을 구분해 설명했으며, 현재 배포 안내는 URL과 공개 anon/publishable 키를 Netlify 환경변수로 등록하는 방식이다. 서비스 롤 키를 프론트엔드에 포함하는 방식은 사용하지 않는다.

### 4.4 1단계에서 다음 단계로 이동한 배경

바닐라 웹은 이미 사용 가능한 기능을 제공하고 있었지만, 그 기능을 계속 키우고 변경하기 위한 구조에는 한계가 있었다. 화면 마크업과 데이터 로직이 한 파일에 모이고, 스타일도 큰 파일에 집중되어 있어 수정의 경계가 명확하지 않았다. 사용자는 지인으로부터 Next.js를 시도해 보라는 권유를 받고 AI IDE 도구를 이용해 프레임워크 전환을 시작했다.

1→2단계에서 기대한 것은 단순히 파일 확장자를 HTML에서 TSX로 바꾸는 것이 아니었다. 새로운 프레임워크로 기능을 가져가고 이후 개선을 이어가는 것이 목표였지만, AI 도구가 계획된 구조를 충분히 따르지 않아 결과는 기대와 달라졌다. 이 문제는 2단계의 경험으로 이어진다.

## 5. 1→2단계 — 바닐라 웹에서 Next.js로 옮기려던 목표

### 5.1 전환 전 계획이 다루던 것

`C:\1\Documents\plans\2. 바닐라 웹에서 넥스트js 버전으로 전환 계획안.md`는 기존 정적 웹에서 Next.js로 옮길 때 새 작업자가 파악해야 할 서비스와 기능을 정리한 인수인계 자료다. 문서의 중요한 목적은 기존 동작을 빠뜨리지 않고 옮기고, DB·트래커에 대한 불필요한 변경을 막는 것이었다.

계획과 인수인계 자료가 명시한 원칙에는 다음이 포함됐다.

- 기존 웹 기능을 목록화하고 누락 없이 옮긴다.
- 트래커나 운영 DB 스키마를 프론트 전환과 무관하게 전면 변경하지 않는다.
- 경기 기록 수정·삭제 기능을 임의로 만들지 않는다.
- 닉네임과 DB 값은 신뢰할 수 없는 입력으로 다룬다.
- 기존 HTML 문자열 조립보다 React 요소와 텍스트 렌더링을 우선한다.
- Supabase 연결 오류, 로딩, 빈 결과를 서로 구분한다.
- 공개 anon 키와 비밀 service-role 키를 혼동하지 않는다.
- PC·모바일·설치 PWA의 동작 정책을 의식적으로 결정한다.
- 디자인·기능·데이터 연결·배포를 검증한 뒤 기존 서비스 교체를 검토한다.

자료에는 Next.js App Router, TypeScript, Tailwind CSS, Recharts, Framer Motion, 환경변수 및 Netlify 구성의 목표가 등장한다. 프로젝트가 처음 Next.js로 전환할 때 지향하던 방향은 새 도구를 도입하는 것뿐 아니라, 기능·데이터·배포에 관한 기존 조건을 보존하는 것이었다.

### 5.2 계획의 UI와 PWA 결정

전환 당시 문서는 홈, TOP 10, 검색, 프로필, 대전 기록, 다운로드, 맵·캐릭터 표시, 로딩·오류 상태 등 기존 기능을 조사해 목록화했다. 또한 Next.js 프로젝트를 만들기 전에 디자인 시안을 준비하고, 실제 데이터 계층과 공통 컴포넌트를 연결한 뒤 검증한다는 단계형 작업 순서를 제안했다.

당시 계획 문서의 모바일 정책은 일반 모바일 브라우저와 설치된 PWA를 다르게 취급하는 안을 포함했다. 일반 모바일 브라우저에는 설치 안내를 표시하고, 설치된 앱에서는 모바일 UI를 제공한다는 내용이었다. 이후 리팩터링 계획에서는 PC·모바일 브라우저·PWA 모두에서 동작하도록 범위를 명시했으므로, 이는 프로젝트의 요구사항이 단계에 따라 조정된 사례로 읽어야 한다. 과거 계획을 현재 정책으로 그대로 가져오면 안 된다.

### 5.3 계획과 구현은 동일한 것이 아니다

계획안에 App Router, Tailwind, 분리된 컴포넌트 같은 문구가 있다고 해서 실제 구현이 그 목표를 달성했다고 볼 수는 없다. 다음 절의 2단계 코드를 직접 확인하면, 계획된 기술과 실제 구조 사이에 큰 간격이 있었다. 이 구분은 1→2단계의 중요한 결과다.

## 6. 2단계 — Next.js로 옮겼으나 모놀리식 구현이 반복된 버전

### 6.1 코드 스냅샷에서 확인되는 구성

`C:\1\yyy\2. 넥스트js 이긴하나 모놀리식 개판 버전`의 실제 소스 스냅샷을 확인했다. 파일 크기와 형태는 다음과 같다.

| `src/app/page.tsx` | 약 44 KB, 500줄 |
| `src/app/globals.css` | 약 90 KB, 1,464줄 |
| `src/app/api/matches/route.ts` | Supabase 경기 목록 REST 요청 |
| `src/lib/matches.ts` | 경기 관련 타입·정규화 코드 일부 |
| `src/app/PwaControls.tsx` | PWA 제어 UI 일부 |

코드가 Next.js `src/app` 경로에 있다는 점에서 Next.js 프로젝트였지만, 앱 페이지 파일 하나에 상태와 동작이 집중되고 전역 CSS가 거대하게 유지됐다. 프레임워크 채택과 코드 구조의 개선이 자동으로 같이 발생하지 않았다는 뜻이다.

### 6.2 페이지 파일의 책임 집중

`page.tsx`에서는 다음과 같은 책임이 한 파일에 함께 들어 있었다.

- 경기 데이터 배열, 로딩 상태와 오류 처리.
- 데이터 API 호출 및 취소 제어.
- 해시를 읽어 화면 섹션과 프로필을 결정하는 라우팅 유사 상태.
- 화면 검색어·상대 검색·메뉴·페이지 번호·정렬·맵 선택 상태.
- 선수별 게임·승리 수와 승률을 계산하는 로직.
- TOP 10의 20전 필터, 승률/경기 수 정렬, 대표 조합 산출.
- 캐릭터 픽 통계를 계산하는 로직.
- 화면 카드·차트·리스트와 모달 렌더링.

예를 들어 페이지는 `hash` 상태를 두고 `window.location.hash`를 감시하며, 내부 링크와 `history.pushState`로 해시 경로를 바꾸고 있었다. 그러므로 코드가 Next.js App Router 디렉터리에 존재하는 것과 실제 사용자 화면이 `/players`, `/profile/name` 같은 경로별 App Router 페이지로 분리되어 있는 것은 다른 문제다. 이 스냅샷에서는 내부 화면 전환이 해시 상태와 한 페이지 컴포넌트에 크게 의존했다.

### 6.3 전역 CSS의 책임 집중

`globals.css`는 약 90 KB였고, 레이아웃·내비게이션·카드·대시보드·차트·목록·모달·모바일 대응 등 여러 UI의 스타일이 한 파일에 들어 있었다. Tailwind 관련 설정/의존성이 존재한다고 해서 실제 화면 스타일이 Tailwind 유틸리티 중심으로 작성된 것은 아니었다. CSS 설계의 중심은 여전히 광범위한 전역 규칙이었다.

이는 스타일이 화면 컴포넌트 소유자 가까이에 놓이지 않아 변경 영향 범위를 좁히기 어렵고, 공통 클래스나 미디어 쿼리가 다른 영역에 영향을 주기 쉬운 상태였다. 사용자의 “다 한 파일에 때려박았다”는 표현은 특정 확장자 파일이 딱 하나였다는 문자적 설명이 아니라, 역할 분리 없이 대규모 파일에 내용이 집중됐다는 구조적 평가다.

### 6.4 데이터 상한 문제의 지속

2단계의 `src/app/api/matches/route.ts`는 Supabase REST API를 호출하면서 `order=created_at.desc&limit=1000`을 지정했다. 응답을 `normalizeMatch`로 정리해도 그 정규화는 **받아온 행의 형태**를 일관되게 할 뿐, API 요청에서 반환되지 않은 기록을 복원하지 않는다.

따라서 2단계에는 서로 다른 두 문제가 같이 있었다.

1. **구조 문제:** 페이지와 CSS에 책임이 집중되고 화면 상태/계산이 뒤섞임.
2. **데이터 범위 문제:** 통계가 최대 1,000행 요청 결과에 의존할 수 있음.

두 문제는 같은 문제의 다른 이름이 아니다. 2→3단계는 주로 첫 번째 문제를 해결하기 위한 구조 리팩터링이며, 두 번째 데이터 완전성 문제는 3→4단계에서 해결했다.

### 6.5 2단계가 남긴 핵심 교훈

사용자는 Next.js 전환을 위해 AI IDE 도구를 적극 사용했지만, AI가 목표 문서를 스스로 지키고 아키텍처 원칙을 자동으로 일관되게 적용해 주지는 않았다. 기대했던 App Router·모듈화·Tailwind 등의 방향이 있었음에도 실제 산출물이 한 페이지·전역 CSS 중심으로 남았다.

따라서 2단계의 실패는 “Next.js가 나쁜 선택”이었다는 결론이 아니다. 기술을 바꾸었어도 작업 지시와 검증이 구현 구조를 보장하지 않으면 이전 모놀리식 방식이 새 프레임워크에 그대로 재현될 수 있다는 학습이었다. 이 경험을 바탕으로 3단계에서는 기능을 추가하기 전에 구조 목표와 유지보수 규칙을 자세히 정리했다.

### 6.6 2단계 종료 시점에 작성된 구조 진단

2단계 코드를 살핀 당시의 구조 진단은 “기능이 동작하는가”와 “Next.js의 기능·경계를 활용하는가”를 별도 질문으로 다뤘다. 이 진단은 2단계 구현을 평가하고 다음 리팩터링 방향을 정하기 위한 것이지, 이후 3~5단계 코드에 대한 현재 상태 평가가 아니다.

#### 긍정적으로 확인된 부분

- App Router 경로의 기초가 생겨 있었다.
- API Route Handler와 `lib`를 분리하려는 흔적이 있었다.
- 화면의 일부가 이미 별도 컴포넌트 파일로 나뉘어 있었다.
- 데이터 로딩 일부가 Hook으로 추출되어 있었다.
- Recharts와 Framer Motion을 사용하려는 구현이 있었다.
- 사용자가 필요한 대시보드와 프로필 기능 자체는 작동하는 구현을 만들고 있었다.

따라서 진단은 프로젝트가 “완전히 무너진 코드”라고 한 것이 아니다. 기능을 빠르게 구현하고 일부 분리도 시작했지만, 컴포넌트가 존재한다는 사실만으로 책임 경계까지 잘 분리된 것은 아니라고 판단했다.

진단 당시 일부 UI·기능은 `AppShell`, `Charts`, `MatchList`, `PlayerSearch`, `PwaControls` 같은 파일로 이미 분리되어 있었다. 이 사실은 “컴포넌트가 전혀 없었다”는 말과 다르다. 문제 제기는 그러한 분리에도 페이지 파일과 전역 CSS가 광범위한 책임을 유지하고 있어, 파일 분리만으로 재사용성·독립성을 확보했다고 보기 어렵다는 것이었다.

#### Next.js 서버·클라이언트 경계에 대한 당시 우려

당시 주요 화면 파일들이 `"use client"`를 선언하고 클라이언트 Hook에서 데이터를 요청했다. 이 선택은 인터랙션에 필요할 수 있지만, 거의 모든 페이지가 같은 방식이면 서버 렌더링·데이터 전달·클라이언트 상호작용의 경계가 약해진다. 초기 HTML이 화면 내용을 충분히 제공하지 못하고, 로딩 상태가 브라우저에서 뒤늦게 만들어져 화면 점프가 생길 수 있다는 우려가 있었다. 서버 렌더가 가능한 화면까지 클라이언트 번들에 들어가면 번들 크기와 초기 렌더 관점의 이점도 놓칠 수 있다고 평가했다.

서버 컴포넌트의 이점으로 당시 검토한 것은 서버에서 직접 데이터를 취득할 수 있는 점, 초기 HTML을 더 일찍 제공할 수 있는 점, SEO와 초기 로딩 개선 가능성, 클라이언트 번들 부담 감소, 데이터·캐시 재사용을 서버 경계에서 설계할 수 있다는 점이었다. 제안된 후보는 정적 페이지 구조, 기본 메타데이터, 조회 결과를 바탕으로 한 서버 측 데이터 취득·계산처럼 사용자 상호작용이 꼭 필요하지 않은 부분이었다. 반대로 검색 입력, 차트 상호작용, 모달처럼 브라우저 이벤트가 필요한 범위는 클라이언트에 남긴다는 구상이었다. 이는 이후 실제 모든 화면이 서버 컴포넌트로 바뀌었다는 사실을 뜻하지 않는다. 현재 프로젝트는 캐시 우선 표시, 브라우저 IndexedDB, focus/visibility 기반 재검증 등 클라이언트 실행이 필요한 기능도 갖고 있으므로, 당시 목표와 현재 채택된 동작을 구분해야 한다.

데이터 Hook에서도 `useMatches`, `usePlayerMatches`, 프로필 내부 상태와 각 페이지 로컬 로직 사이에 비슷한 로딩·오류·캐시 처리가 반복될 수 있다는 지적이 있었다. 상태 관리가 Hook으로 일부 추출됐다는 긍정적 관찰과, 페이지마다 처리가 다르게 복제된다는 문제는 동시에 성립한다. 공통 `StatusBlock` 같은 구성요소가 존재해도 오류 상태 표현과 실패 시 동작이 전체 화면에서 표준화된 것은 아니라고 보았다. 따라서 당시 제안은 데이터 취득 수명과 UI의 상태 표시를 구분하고, 공통 로딩/오류 처리를 정하되 실제 오류가 빈 데이터 성공으로 오해되지 않게 하는 것이었다.

#### Route Handler와 클라이언트 데이터 취득의 관계

API Route Handler가 존재한다고 해서 화면 데이터가 서버 우선 구조가 되는 것은 아니다. 당시 흐름은 클라이언트 컴포넌트가 Hook을 통해 애플리케이션 API를 다시 요청하고, Route Handler가 Supabase에 접근하는 형태였다. 이 경로에는 명확한 이점도 있다. 브라우저에서 직접 DB 연결 세부사항을 다루지 않고, 서버가 입력·응답 계약을 관리할 수 있다. 다만 데이터 취득 책임이 화면·Hook·Route Handler 중 어디에 놓이는지 분명히 정하지 않으면, 서버와 클라이언트 양쪽에 중복 처리와 불필요한 왕복이 남는다.

당시 권고는 페이지 단위 서버 데이터 취득을 우선 검토하고, Route Handler는 API 경계가 실제로 필요한 경우에 쓰며, 클라이언트 컴포넌트는 상호작용 중심으로 제한하는 것이었다. 이후 4단계에서 DB RPC, Next.js Route Handler, 클라이언트 Hook이라는 경로가 정착한 사실은 별도의 데이터 정확성·API 계약 결정이다. 그것을 서버 컴포넌트 전환이 완료되었다는 의미로 바꾸어 읽으면 안 된다.

클라이언트에서 수동 `fetch`를 각 화면이 제각각 반복하면 캐시 정책을 공유하기 어렵고, 로딩 상태 구현이 중복되며, 실패 시 UX가 화면별로 달라지고, App Router의 route segment와 데이터 경계를 일관되게 설계하기 어려워진다는 우려도 있었다. 권고는 모든 Route Handler를 없애자는 것이 아니라, 페이지에서 서버가 맡을 데이터와 API 경계가 맡을 일, Hook이 관리할 상호작용 상태를 명시적으로 정하자는 것이었다.

#### 페이지·컴포넌트·스타일 진단

진단은 `/src/app/page.tsx`에서 데이터 조회, 상태 선언, 통계 계산, 차트 조립, 경기 목록, 제목·레이아웃, 맵 모달 제어가 한데 모이는 점을 책임 집중으로 보았다. 기존 컴포넌트 파일이 이미 일부 있어도 페이지와 공유 스타일 의존이 계속된다면 실질적인 재사용·독립성이 약하다고 구분했다.

약 1,464줄인 `globals.css`에는 전역 레이아웃부터 헤더·사이드바·검색·카드·차트·경기 목록·프로필·모달·반응형 규칙까지 폭넓게 쌓여 있었다. 이 때문에 특정 컴포넌트의 스타일 변경이 다른 화면에 영향을 줄 수 있고, 한 클래스의 의미와 소유자를 찾기 어려웠다. 문제는 단순히 CSS 파일의 줄 수가 많다는 것만이 아니라 전역 범위와 변경 책임이 화면 경계에 맞지 않는 것이었다.

Tailwind는 원래 의도된 스타일 기술이었지만, 2단계 구현에서 실제 기본 작성 방식으로 정착하지 못한 것으로 진단됐다. 따라서 이를 Tailwind가 설계에서 제외된 선택이라고 표현하는 것은 부정확하다. 당시 평가는 설치된 도구와 의도된 규칙이 실제 구현에서 빠르게 지나가며 생긴 실행 누락·기술 부채에 가까웠다.

#### 당시 평가의 의미

평가 자료는 기능 구현력을 “보통 이상”, 구조 설계를 “중하”, Next.js 이해도를 “보통”, 유지보수성을 “낮음”, 면접용 완성도를 “보통 이하”로 표현했다. 이 등급은 자동화된 품질 측정치나 현재 프로젝트의 점수가 아니라, 2단계 소스에 대한 당시의 정성 평가다. 당시 상태를 기능은 동작하지만 실무형 아키텍처로 보기에는 미완성인 프로토타입에 가깝다고 설명했다. 면접/코드 리뷰에서 나올 수 있는 질문도 이런 진단을 설명하기 위한 예시였다.

- 서버와 클라이언트의 책임을 어떻게 나눴는가?
- 각 페이지는 데이터 취득과 화면 조립 중 무엇을 소유하는가?
- 공통 UI와 컴포넌트별 UI를 어떤 기준으로 재사용하는가?
- 스타일이 전역으로 퍼지지 않도록 무엇을 기준으로 관리하는가?
- 데이터 계산과 UI 렌더링을 어떻게 분리하고 검증하는가?

이 질문들의 핵심은 “Next.js를 썼다”는 사실이 아니라, 프레임워크가 제공하는 경계를 왜 선택했고 각 책임이 어느 파일에 있는지 설명할 수 있는가였다.

## 7. 2→3단계 — Next.js 구조 리팩터링

### 7.1 목표의 중심은 구조였다

2→3단계는 1,000행 통계 문제를 해결하는 단계가 아니었다. 주된 목적은 2단계 구현의 구조적 실패를 반복하지 않도록 프론트엔드를 다시 나누고, 의도한 Next.js 프로젝트 형태를 적용하는 것이었다.

리팩터링에서 집중한 방향은 다음과 같다.

- 파일시스템 기반 **App Router**를 실제 화면 경로의 기준으로 사용한다.
- `page.tsx`를 전체 앱 UI·로직을 다 가진 파일로 만들지 않고 라우트 엔트리로 사용한다.
- UI를 레이아웃·대시보드·차트·검색·경기·프로필 등 책임별 컴포넌트로 나눈다.
- 데이터 요청 상태와 업무 흐름은 Hooks에, 데이터 타입·정규화·순수 계산은 lib에 둔다.
- Tailwind 유틸리티를 기본 컴포넌트 스타일 작성 방법으로 사용한다.
- Recharts와 Framer Motion을 단지 의존성으로 설치해 두는 것이 아니라 실제 차트와 절제된 UI 모션에 사용한다.
- 로딩, 오류, 빈 결과와 정상 데이터를 구분한다.
- 모바일 브라우저와 설치 PWA를 포함해 기기 범위를 좁히지 않는다.

이 지침의 목적은 다음 작업에서 AI 도구가 대형 페이지와 CSS를 다시 만들어 내지 않도록, 작업 전 파일 책임·구조·검증을 명시하는 것이었다. 기존 계획서에는 route, component, hook, lib, API, 공용 레이아웃과 페이지 흐름 등 구체적인 목표 구조가 적혔다.

### 7.2 실제 기능 범위의 기준

3단계는 화면을 비우고 새 앱을 만드는 것보다 기존 기능과 다음 Next.js 디자인 기준을 기능 단위로 이식하는 작업이었다. 중요한 기능 범위는 다음과 같이 정리되어 있었다.

- 홈: 전체 대전, 플레이어 수, 최근 24시간 수, 캐릭터 픽률, 태그 조합, 급상승 플레이어, 최근 30일 활동 및 최근 대전.
- TOP 10: 최소 경기 기준, 승률 우선 정렬, 대표 팀과 캐릭터 표현.
- 검색: 상단 플레이어 검색과 닉네임 자동완성.
- 프로필: 경기/승패/승률, 플레이 시간, 조합, 맵, 상대 전적, 개인 경기 기록.
- 전체 경기: 결과, 점수, 플레이어/캐릭터, 맵/시각, 페이지 이동과 맵 미리보기.
- Tracker 다운로드와 기존 에셋/아이콘 매핑.
- 일반 화면 외에도 모바일 웹과 설치 PWA에서 사용할 UI.

이식 시에는 기존 기능을 제거하기보다 기준 화면과 기존 서비스 데이터를 대조해 동작을 보존하는 것을 우선했다. 그래프 성격이 있는 패널은 Recharts, UI의 등장·상태 전환은 Framer Motion으로 다루고, 일반 숫자 카드나 테이블을 억지로 차트로 만들지 않는 방향이었다.

### 7.3 현재 코드에서 확인되는 구조의 결과

현재 `C:\1\ttt2_web_v2` 코드베이스에서 구조가 나뉜 예는 다음과 같다.

| 책임 | 예시 경로 |
|---|---|
| App Router 화면 경로 | `src/app/page.tsx`, `src/app/players/page.tsx`, `src/app/matches/page.tsx`, `src/app/profile/[name]/page.tsx` |
| 공용 레이아웃 | `src/components/layout/AppShell.tsx`, `TopBar.tsx`, `SidebarNav.tsx` |
| 각 화면 UI | `src/components/dashboard/DashboardHome.tsx`, `src/components/matches/MatchesDirectory.tsx`, `src/components/profile/ProfileView.tsx` |
| 차트 | `src/components/charts/Charts.tsx` |
| 데이터 흐름 Hook | `src/hooks/useDashboardStatistics.ts`, `useMatches.ts`, `useProfileStatistics.ts` 등 |
| API 응답·도메인 검증 | `src/lib/dashboard-statistics.ts`, `profile-statistics.ts`, `match-pages.ts` 등 |
| 서버 RPC 경계 | `src/lib/server/supabase-rpc.ts`, `match-pages.ts` 등 |

현재 루트 `src/app/page.tsx`는 화면 전체를 담지 않는 얇은 엔트리이며, 홈 UI는 dashboard 컴포넌트에 둔다. 현재 전역 CSS는 약 134줄로 reset, 토큰과 기반 스타일 등을 포함하고, 화면별 디자인의 다수는 TSX의 Tailwind utility에서 관리된다. 이는 2단계의 500줄 페이지·1,464줄 전역 CSS 스냅샷과 대조되는 구조 변화다.

“모든 코드가 완벽하게 분리됐다”는 뜻은 아니다. 예를 들어 `ProfileView.tsx`와 `Charts.tsx`는 여전히 상당한 UI를 갖는다. 중요한 변화는 앱 전체가 단일 route/CSS 덩어리에 종속되지 않고, 라우트와 주요 기능 소유자가 구분되는 방향으로 이동했다는 점이다.

### 7.4 3단계가 해결하지 않은 것

App Router, Tailwind, 컴포넌트 구조와 데이터 모듈화를 적용해도, 통계가 어떤 행을 입력으로 받는지는 별도 문제다. 요청이 여전히 전체 기록 중 일부만 반환하고 브라우저가 받은 행을 전체 표본처럼 계산한다면 구조가 좋아져도 값은 계속 부정확할 수 있다.

즉 3단계의 완료 기준은 통계 쿼리의 대용량 정확성을 해결하는 것이 아니었다. 통계의 계산 범위와 화면 목록 범위를 재설계하는 일은 3→4단계에서 별도로 진행했다.

이를 보여 주는 구체적인 계획상 계약이 있다. 대시보드용 `/api/matches`는 `limit=1000`을 사용하는 안으로 적혀 있었고, 개인 프로필만 `/api/matches/player?name=`으로 별도 조회해 전체 최근 경기 덤프에 의존하지 않게 하려 했다. 이는 프로필 조회 부담을 분리하는 개선이지만, 대시보드의 전체 통계를 1,000행 밖까지 계산한다는 보장은 아니다. 리팩터 단계에서 프로필 API를 분리한 것과 전체 데이터 범위 문제를 해결한 것을 동일한 성과로 합쳐 쓰면 안 된다.

### 7.5 3단계 설계안의 출발점과 기준 프로젝트

3단계는 기존 구현을 그대로 확장하는 대신 새 폴더 `ttt2_web_v2`에서 구조를 다시 짜는 그린필드 방식으로 계획됐다. 기능과 UI를 판단할 기준은 당시 존재하던 `ttt2_web_next` 디자인·기능 샘플이었다. 그 샘플은 실서비스가 아니라 미배포 레퍼런스였으며, 실제 Supabase 데이터 대신 임시 하드코딩 데이터를 사용했다. 그러므로 샘플을 “실제 동작이 검증된 최종 앱”으로 보거나, 배포된 구형 정적 `ttt2_web`을 새 UI의 기준으로 삼는 계획은 아니었다.

당시 기준 선택은 다음과 같았다.

- `ttt2_web_next`: 홈·프로필·맵 미리보기·화면 배치·에셋의 기본 레퍼런스.
- 구형 정적 웹: 기본 UI 기준으로 삼지 않고, 프로필 전체 조회와 동일 캐릭터 솔로 태그 표현 등 명시한 예외만 참조.
- `ttt2_web_v2`: 새 App Router 프로젝트, 기능 동등성 확보 후 배포 후보.
- 이전 레퍼런스 폴더는 새 구조가 기능 동등성에 도달하기 전까지 보존하고 덮어쓰지 않는다.

이 구분은 “기존 것을 아무것도 보지 않는다”는 말이 아니다. 어느 구현을 기능·UI의 기준으로 삼고, 어떤 구형 기능만 예외적으로 가져올지 명확히 하여 AI 도구가 오래된 화면을 임의의 소스 오브 트루스로 사용하는 것을 막는 결정이었다.

### 7.6 프레임워크·라우트·모듈 계획의 세부

리팩터 계획은 Next.js 16 계열과 React 19를 유지하고, 리팩터링과 프레임워크 메이저 업그레이드 위험을 동시에 섞지 않는 방침을 두었다. 계획 당시 레퍼런스 앱의 구체 버전은 Next.js 16.3.6, React 19.2.8이었으며, Recharts와 Framer Motion도 실제 UI에서 활용할 대상으로 남겼다. 해당 번호는 계획 문서 시점의 값이지 현재 설치 버전을 보증하는 정보로 사용하면 안 된다.

해시 화면 이동(`#profile/name`) 대신 실제 URL 경로를 사용해 직접 링크·북마크·브라우저 탐색을 명확히 하는 것이 App Router 선택의 이유였다.

| 경로 | 목적 |
|---|---|
| `/` | 홈 대시보드 |
| `/players` | 기존 사이드바의 TOP 10 |
| `/matches` | 최근 전체 대전 기록 |
| `/download` | Tracker 다운로드 |
| `/profile/[name]` | 플레이어 프로필 |
| `/api/matches` | 대시보드/목록의 경기 데이터 API |
| `/api/matches/player` | 플레이어 전용 기록 API |

계획된 파일 책임은 대략 다음과 같았다.

- `app/layout.tsx`: 공용 셸과 페이지 공통 메타 구조.
- `app/*/page.tsx`: 해당 경로 엔트리, 페이지 조립.
- `components/layout`: 앱 셸, 사이드바, 데스크톱 헤더, 필요 시 모바일 내비게이션.
- `components/dashboard`, `matches`, `profile`, `charts`: 기능별 화면.
- `hooks`: 클라이언트 상호작용이 필요한 데이터 수명과 화면 상태.
- `lib`: 경기 타입/정규화, 맵·캐릭터 매핑, 계산 함수.
- `app/api`: 입력 검증과 서버 측 Supabase 데이터 접근.
- `public`: 캐릭터·맵 이미지, 앱 아이콘 및 PWA 자산.

`page.tsx`를 “모든 것을 넣는 컴포넌트”가 아니라 레이아웃·기능 컴포넌트를 조립하는 경계로 축소하려고 했다. 차트 계산은 순수 데이터 계산과 시각화 컴포넌트의 역할을 구분하고, API 응답 파싱과 화면 표시도 하나의 컴포넌트에 합치지 않는 것이 의도였다.

라우트 차원의 보완 목표로 `loading.tsx`와 `error.tsx` 또는 동등한 오류 UI, 서비스 목적에 맞는 `metadata`, create-next-app 기본 템플릿을 그대로 둔 README 대신 프로젝트 목적·기술 스택·실행 방법·환경변수·배포·폴더 구조·공개키와 RLS 설명을 담은 README를 준비하는 안도 있었다. 이는 구조뿐 아니라 새 작업자가 프로젝트를 실행하고 데이터 권한 모델을 이해할 수 있게 하려는 문서화 요구였다.

### 7.7 기능 동등성 체크리스트

계획은 기존 기능을 막연히 “이전”하지 않고, 레퍼런스 화면과 비교할 수 있는 기능 단위로 나눴다.

#### 홈 대시보드

- 전체 경기, 등록 플레이어, 최근 24시간 경기 수.
- 캐릭터 픽률과 고승률 태그 조합.
- 최근 7일과 직전 7일을 비교하는 급상승 플레이어.
- 오늘을 기준으로 한 30일 일별 경기 그래프.
- 최근 경기 3개를 포함한 최근 경기 요약.

#### TOP 10

- 등록된 모든 플레이어 중 경기 수와 승리 수 집계.
- 최소 20전 기준 적용.
- 승률을 우선으로 정렬하고 승률 동률이면 더 많은 경기 수를 우선.
- 최대 10명 표시.
- 대표 태그 조합과 캐릭터 이미지.
- 항목에서 해당 플레이어 프로필로 이동.

#### 검색 및 프로필

- 플레이어 닉네임 검색과 자동완성.
- 입력 일부와 `startsWith`/prefix 규칙에 따른 추천.
- 추천 이름을 선택하면 프로필로 이동.
- 프로필의 총 경기, 승·패, 승률, 총 플레이 시간, 마지막 경기 시간.
- 주력 태그 조합 및 맵별 승률.
- 상대 전적 및 원하는 상대 이름 검색.
- 최근 경기 목록, 결과 기준 정렬과 페이지 이동.
- 프로필의 경기 수는 대시보드에서 받은 임의의 전체 경기 샘플에 종속시키지 않고 별도 API로 취득.
- 태그 양쪽이 같은 솔로 태그는 중복된 두 캐릭터 슬롯처럼 보이지 않게 한 캐릭터로 표현하는 예외.

#### 전체 경기 및 기타 UI

- 경기 번호, WIN/LOSS, 라운드 스코어, 두 플레이어 이름.
- 양쪽 캐릭터의 이미지와 이름, 맵 이름, 경기 소요 시간, 시작/종료 시각.
- 전체 최신 경기, 페이지네이션, 맵 미리보기.
- Tracker 다운로드와 다운로드 파일 링크.
- 로딩, 오류, 데이터 없음의 구분.
- 검색 자동완성과 공통 메뉴·레이아웃.
- 화면을 꾸미기 전에 기존 기능 누락을 먼저 검사.

기능 동등성은 데이터 소스가 완전히 같은지와 화면 기능이 같은지를 구별해야 한다. 이후 4단계에서 일부 데이터 API 자체가 정확성 문제 때문에 바뀌었으므로, 레퍼런스의 당시 계산 결과를 정답으로 고정하지 않고 화면·사용자 기능과 통계 의미를 각각 대조해야 한다.

### 7.8 차트·모션·스타일·접근성 목표

Recharts는 설치만 하고 사용하지 않는 의존성으로 남기지 않고, 의미 있는 데이터 패널에 실제로 적용할 계획이었다. 후보로 구분했던 여섯 시각화 영역은 다음과 같다.

1. 홈의 캐릭터 픽률.
2. 홈의 고승률 태그 조합.
3. 최근 7일과 직전 7일 비교 급상승 지표.
4. 홈의 최근 30일 대전량.
5. 프로필의 주력 태그 조합 승률.
6. 프로필의 맵별 승률.

반면 상단 KPI 숫자, 경기 목록, TOP 10 표, 상대 전적 목록, 다운로드 버튼은 차트로 만들 범위가 아니었다. 차트는 실제 데이터를 연결하고, 읽기 어려우며 의미가 약한 도식은 제거할 수 있다는 조건도 있었다.

Framer Motion은 카드나 패널의 진입, 페이지/탭 전환, 모달 또는 목록 갱신처럼 상태 변화를 이해하기 쉬운 범위에 절제해 사용한다. 장식 목적으로 모든 요소를 움직이지 않으며, 계획에서는 `prefers-reduced-motion` 설정을 존중하도록 요구했다.

스타일 측면에서는 레퍼런스의 다크 테마 분위기는 이어가되 누적된 중복 미디어 쿼리 더미를 복사하지 않으며, 전역 CSS를 새로 키우지 않고 컴포넌트 단위로 필요한 스타일을 구성하려 했다. 데스크톱, 좁은 모바일 뷰포트, 설치 PWA의 standalone 레이아웃을 검증 대상으로 뒀다.

접근성 기본 항목으로는 차트 라벨, 모달 Escape 종료, 장식 이미지를 스크린리더에서 불필요하게 읽지 않도록 하는 빈 `alt` 값 등을 계획했다. 차트가 시각적으로만 의미를 전달하지 않게 하고 키보드 사용도 고려한다는 취지였다.

계획 당시 레퍼런스 디자인 샘플에는 `Dark esports`, `SaaS analytics`, `Mobile arcade` 세 테마가 비교용으로 존재했으나, 그 시점에는 최종 테마가 정해지지 않은 샘플 상태였다. 이후 리팩터 방향은 다크 테마 한 가지를 기준으로 삼고 세 테마 선택 UI는 범위에서 제외했다. 세 샘플을 세 가지 완성된 제품 테마 또는 최종 기능으로 서술하지 않는다.

### 7.9 데이터 계약·보안·운영 경계의 계획

#### `select=*`와 응답 정규화

계획은 Supabase REST의 모든 컬럼을 나열하는 방식보다 `select=*`를 허용하고, `normalizeMatch`와 TypeScript 타입 경계에서 응답을 정규화하는 쪽을 선택했다. 트래커에 계급 ID 같은 새 컬럼이 추가될 가능성이 있어, 컬럼 목록을 여러 요청에 반복해 고정하는 유지비를 피하려는 결정이었다. 새 필드를 선택적으로 타입에 추가하고 필요한 UI에서 명시적으로 소비하되, 데이터를 무검증 상태로 UI에 넘기자는 뜻은 아니었다. “응답 컬럼을 유연하게 읽음”과 “응답 형식 검증·정규화”는 별개의 책임이다.

#### 키와 배포

- 로컬 개발은 `.env.local`에서 Supabase URL과 공개 anon 키를 주입한다.
- 저장소에는 실제 키가 아닌 자리표시자만 든 `.env.example`을 둘 계획이었다.
- `.env.local`은 Git에서 제외하고 `.env.example`은 추적 가능하게 한다.
- Netlify에서는 프로젝트 빌드 설정과 콘솔 환경변수를 각각 준비한다.
- 공개 `NEXT_PUBLIC_*` 키는 브라우저에 노출되는 공개 키이며 service-role 키와 다르다.
- 운영 권한은 Supabase RLS 정책으로 제한하고 관리자 키를 프론트엔드에 두지 않는다.
- 구형 사이트의 하드코딩된 브라우저 키와 새 Next 앱 환경변수 방식의 배포 절차가 같지 않음을 문서화한다.

#### 배포·레퍼런스·범위 통제

리팩터 계획 시점에는 구형 정적 사이트만 Netlify 실서비스였고, 기능 기준이 되는 Next 디자인 샘플은 미배포였다. 새 프로젝트는 테스트용 Netlify 사이트/도메인에서 실제 DB 연결·기능·모바일·PWA를 검증한 뒤, 문제가 없을 때 구형 도메인 교체를 검토하는 순서였다. 계획을 기록한 사실만으로 실제 테스트 배포나 도메인 교체가 완료됐다고 말할 수 없다.

이번 구조 작업에서는 Django 같은 별도 백엔드를 단지 기술 스택을 늘리기 위해 도입하지 않으며, Supabase MCP를 연결해 운영 DB를 자동 수정하지 않고, DB 스키마나 Tracker를 임의로 바꾸지 않는 경계를 두었다. 경기 수정·삭제 관리 기능도 만들지 않는 범위였다. 별도 서버는 관리자 검수·신고 처리·계정/권한·비정상 기록 탐지 등 실제 요구가 생길 때 다시 검토할 대상으로 남았다.

당시 제외 범위는 3종 테마, 모바일 콘텐츠 강제 차단, 패치노트 신규 구현, 복잡한 CI 매트릭스와 무관한 Django 추가였다. 이는 초기 전환안에 있었던 미설치 모바일 브라우저용 게이트 구상에서 **PC·모바일 브라우저·PWA 전체를 지원하는 방향으로 계획이 바뀐 것**을 보여 준다. “모바일 브라우저를 막는다”는 정책을 이후 단계까지 지속된 요구사항으로 서술하면 안 된다.

### 7.10 검증 전략

3단계 계획에서 요구한 자동·수동 검증은 서로 다른 것을 확인한다.

| 확인 영역 | 계획한 확인 방법 | 확인하려는 것 |
|---|---|---|
| 정적 품질 | `npm run lint` | 정적 규칙과 일반적인 코드 오류 |
| 패키징 | `npm run build` | 프로덕션 번들 및 Next 빌드 성공 |
| 순수 계산 | 통계 유닛 테스트 | 고정 입력의 집계 규칙과 경계값 |
| 기능 동등성 | 레퍼런스와 나란히 홈·TOP 10·프로필·매치·검색·다운로드 비교 | 기존 사용자 흐름 누락 여부 |
| 뷰포트 | 데스크톱과 좁은 화면 | 레이아웃 및 콘텐츠 사용성 |
| PWA | 가능한 경우 standalone 실행 | 설치 앱 실행 시 공통 셸과 내비게이션 |
| 실제 데이터 | Supabase 데이터와 기존 화면 비교 | 데이터 매핑·표시·실패 상태 |
| 프로필 상한 | 전용 조회 결과와 기존 조회 결과 비교 | 프로필이 최근 1,000행 전체 샘플의 우연에 묶이지 않는지 |

초기 통계 비교 검증은 3단계 시점에 만들었던 클라이언트 계산 및 데이터 응답에 대한 확인이며, 대규모 데이터에서도 상한이 없는 집계를 보장했다는 뜻은 아니다. 이 한계는 뒤 단계에서 데이터 경로를 따로 설계한 이유와 연결된다.

### 7.11 다음 리팩터링이 되돌아가지 않도록 둔 유지보수 기준

3단계 설계의 산출물은 파일을 나누는 일회성 지시뿐 아니라, 이후 변경에서 다시 모놀리식 구조가 생기지 않게 하는 작업 기준도 포함했다.

#### 파일 소유권

- Route 파일은 페이지 경로와 화면 조립을 담당한다. 그 안에 API 요청, 통계 계산, 차트·모달·리스트 구현을 다시 모두 넣지 않는다.
- 공용 셸·내비게이션·대시보드·차트·검색·경기 행·프로필 UI는 기능 책임에 맞는 컴포넌트로 둔다.
- 한 컴포넌트가 명확한 한 가지 책임을 맡고, 중복 UI는 공용화하되 단지 파일 수를 늘리는 분리는 피한다.
- 데이터 로딩·요청 취소·상태는 Hook 또는 서버 데이터 계층에, 순수한 정규화와 계산은 `lib`에 둔다.
- API 응답 계약과 도메인 계산을 Route Handler 또는 화면 컴포넌트 한 곳에 뒤섞지 않는다.

#### CSS 소유권

- Tailwind utility를 기본 UI 스타일링 방식으로 사용한다.
- 전역 CSS에는 reset, 디자인 토큰, 전역 배경·폰트, 실제 공통 기반 스타일만 둔다.
- 특정 화면·컴포넌트만 쓰는 클래스와 반응형 규칙을 무심코 전역 CSS에 누적하지 않는다.
- 전역 클래스를 추가하기 전, 그 스타일이 정말 전역인지와 영향을 받는 화면을 먼저 확인한다.

#### 수정 전후 체크리스트

| 점검 질문 | 기대하는 안전한 상태 |
|---|---|
| 이 변경은 route, component, hook, lib 중 어디에 속하는가? | 동작의 소유 모듈을 찾아 그 경계에서 수정 |
| route가 데이터 취득·계산·레이아웃·차트까지 떠안는가? | 해당 책임을 기존 모듈 또는 새로 적절히 분리된 소유자에 둠 |
| UI와 fetch/cache/집계가 같은 컴포넌트에 섞였는가? | UI는 검증된 결과를 소비하고 데이터 동작은 별도 계층에서 처리 |
| globals.css에 컴포넌트 규칙을 추가하는가? | 필요한 경우에만 전역 변경하고 아니면 Tailwind/소유 컴포넌트를 사용 |
| 변경 범위가 여러 페이지에 불필요하게 퍼지는가? | 한 기능 소유자 중심으로 작게 유지하고 공용 변경은 호출 화면을 확인 |
| 기존 모바일·PWA·데스크톱 동작에 영향이 있는가? | 의도된 범위만 바뀌는지 각 관련 환경을 확인 |
| 검증으로 구조 회귀를 발견할 수 있는가? | 가장 가까운 테스트·린트·빌드와 필요한 화면 확인을 실행 |

원래 작업 규칙은 항목 하나라도 충분히 만족하지 못하면 코드를 곧바로 추가하지 말고 구조를 다시 검토하는 기준을 제시했다. 핵심은 이 체크리스트가 테스트 하나로 대체되는 것이 아니라는 점이다. 린트와 빌드는 문법·타입·패키징을 확인할 수 있지만, 한 파일에 책임이 다시 몰렸는지 또는 공통 스타일 영향 범위를 잘못 잡았는지는 설계 관점에서 검토해야 한다.

#### 우선순위와 현실적인 적용 순서

당시 개선안의 최우선 세 가지는 클라이언트 페이지 비중과 서버/클라이언트 경계, 전역 CSS의 범위, 페이지 책임 분리였다. 실행할 때는 페이지와 컴포넌트 구조를 먼저 정리하고, 그 뒤 사용자 이벤트가 필요한 클라이언트 영역과 서버에서 처리 가능한 영역을 구분하며, 스타일을 Tailwind 중심으로 일관화한 후 lint/build와 주요 라우트 동작을 확인하는 순서를 제안했다. 기대 효과는 특정 성능 수치를 약속하는 것이 아니라 변경 범위·테스트 가능성·디버깅·코드 리뷰의 용이성을 높이는 것이었다.

이는 “모든 페이지를 반드시 서버 컴포넌트로 바꿔야 한다”는 절대 규칙으로 요약할 수 없다. 기존 진단은 당시 클라이언트 편중을 줄이기 위한 방향을 제안한 것이며, 캐시와 상호작용 구조가 추가된 뒤에는 각 경계가 실제 기능 요구와 맞는지 다시 판단해야 한다.

그 당시 면접용 설명의 중심 문장은 “기능을 빠르게 구현했지만 서버/클라이언트 경계와 스타일 시스템 정리가 아직 필요하며, 특히 계획했던 Tailwind가 실제 구현에 정착하지 못해 다음 단계에서 구조와 스타일을 표준화하려 한다”는 취지였다. 이는 약점을 숨기기보다 어떤 문제가 있었고 왜 다음 리팩터링이 필요했는지 설명하기 위한 표현이었다.

## 8. 3→4단계 — 전체 통계와 대전 목록 데이터 경로 보완

### 8.1 문제가 왜 중요한가

초기 웹과 2단계의 데이터 경로에는 `limit=1000`처럼 최대 행 수가 제한된 경기 조회가 있었다. 사용자가 이를 “최대 1,000건”이라고 부른 것은 설명 편의를 위한 표현이다. 서비스 기록이 1,000건 이하인 동안에는 제한이 표면화되지 않을 수 있지만, 전체 기록이 그 범위를 넘으면 요청이 반환하지 않은 경기를 브라우저 통계가 볼 수 없다.

이 문제는 단순히 오래된 경기 목록 일부를 못 보는 데 그치지 않는다. 제한된 경기 표본으로 전체처럼 보이는 결과를 계산하면 다음 값이 달라질 수 있다.

- 전체 경기 수와 플레이어별 경기 수.
- 플레이어 승·패와 승률.
- 캐릭터별 픽 횟수와 비율.
- 태그 조합 사용 횟수와 승률.
- 맵별 경기 및 승률.
- 플레이어 랭킹의 자격·정렬.
- 최근 기간 통계나 날짜별 집계.

기록이 수만 건으로 성장하면 더 큰 제한을 택하는 것만으로도 근본 해결이 되지 않는다. 결국 새 제한 뒤에서 똑같은 현상이 다시 나타나며, 브라우저 전송량·메모리·계산 작업도 계속 커진다. 4단계의 목적은 현재 기록이 이미 제한을 초과했음을 보여 주는 것이 아니라, **미래에 기록이 크게 늘어날 때도 전체 통계의 계산 범위를 보존하는 것**이었다.

### 8.2 통계 계산과 경기 행 표시를 분리

4단계에서는 필요한 데이터의 성격에 따라 두 계약을 만들었다.

| 요구 | DB가 수행할 일 | 브라우저가 받는 것 |
|---|---|---|
| 통계 숫자·랭킹·상위 목록 | 해당 지표 조건을 만족하는 전체 대상 기록을 집계 | 숫자, 상한이 있는 집계 결과만 |
| 실제 경기 카드/행 | 요청한 정렬·페이지의 기록 조회 및 전체 건수 산출 | 현재 페이지 경기 행과 `total_count` |

통계는 DB에서 집계하고 요약 JSON을 반환한다. “전체 기록을 대상으로 집계한다”는 것은 전체 경기 행을 브라우저에 보내라는 뜻이 아니다. 반대로 경기 기록 화면은 플레이어·점수·맵 같은 개별 행이 필요하므로 페이지 조회가 알맞다.

이 분리는 정확성과 응답 크기 양쪽을 위해 필요하다. 통계가 전송된 소수 행의 전체성을 오해하지 않고, 목록도 처음부터 전체 행을 브라우저에 쌓지 않는다.

### 8.3 공통 선수 관점 View

DB의 원본 경기는 두 플레이어가 한 경기에 참여한다. 여러 플레이어별 지표를 쉽게 계산하기 위해 `public.v_player_match_rows` View는 원본 경기 한 건을 최대 두 개의 선수 관점 행으로 표현한다.

- 첫 행은 P1을 `player_name`, P2를 `opponent_name`으로 보고 P1의 캐릭터와 승리 여부를 기록한다.
- 둘째 행은 P2를 `player_name`, P1을 `opponent_name`으로 보고 P2의 캐릭터와 승리 여부를 기록한다.
- 두 행은 동일한 원본 경기 ID·맵·시간을 공유한다.
- `UNION ALL`을 써서 두 관점 행을 보존한다.
- 승자 값의 NULL은 임의로 패배로 바꾸지 않고 판정 결과의 불확실성을 보존한다.
- `played_at`은 `end_time`이 있으면 그 시간을, 없으면 `created_at`을 사용한다.

View는 결과를 별도 물리 테이블에 복제하는 캐시가 아니라 조회 모양을 재사용하는 SQL 정의다. 공개 역할에 View 전체 직접 조회 권한을 주지 않고, 필요 범위의 집계만 반환하는 함수로 접근하도록 구성했다.

### 8.4 네 통계 RPC의 역할과 반환 상한

현재 통계 설계 문서에는 네 가지 주요 RPC가 정리돼 있다.

| RPC | 용도 | 브라우저 반환 계약 |
|---|---|---|
| `get_dashboard_statistics()` | 전역 KPI, 캐릭터 픽, 조합, 급상승, 활동 그래프 | 30일 활동, 캐릭터 최대 6, 조합 최대 6, 급상승 0~1. 경기 전체 행은 반환하지 않음 |
| `get_player_rankings()` | 전체 플레이어 전적과 대표 조합 기준 순위 | 최대 10명, 각 플레이어 20전 이상 |
| `get_player_statistics(name, opponent)` | 단일 플레이어 프로필·조합·맵·상대 통계 | 조합 최대 5, 맵 최대 50, 최근 상대 최대 5, 선택 상대 결과 0~1 |
| `search_player_names(query, exclude)` | 자동완성용 이름 검색 | prefix 결과 최대 10개, 빈 검색은 빈 배열 |

이 상한은 전체 DB를 6개나 10개만 검사한다는 뜻이 아니다. **DB가 입력 조건에 맞는 전체 표본을 계산한 뒤, 화면에 필요한 결과 목록만 제한해 반환**한다는 뜻이다. 검색이나 프로필 파라미터에는 길이와 빈 값 검사를 적용한다.

### 8.5 통계 계산 규칙의 구체적 의미

아래 규칙은 계산값의 분모·시간·결측 처리 등 결과 의미를 보존하기 위해 문서화된 내용이다.

#### 대시보드

- 전체 경기 수는 선수 관점 View에서 경기 ID로 다시 묶어 원본 경기 수를 계산한다.
- 플레이어 수는 양끝 공백을 제거한 이름의 고유 수로 계산한다. 문서에 기록된 그룹 의미는 대소문자 구분이다.
- 오늘 대전 수는 한국 시간(KST) 자정부터 통계 조회 시각까지의 경기 수다. 자정 직전 경기는 제외하고 미래 시각으로 기록된 경기도 제외한다.
- 캐릭터 픽 분모는 경기 수 × 4이며 양 선수의 메인/서브 네 칸을 기준으로 한다.
- 팀 순서만 다른 동일한 조합은 캐릭터 ID를 정렬해 동일 조합으로 합친다.
- 대시보드 조합은 10전 이상 후보 가운데 승률 상위 6개를 반환한다.
- 급상승은 KST 오늘 포함 최근 7일과 그 직전 7일을 비교하고, 양 구간 모두 10전 이상인 플레이어 중 승률 상승폭을 선택한다. 후보가 없으면 JSON `null`이다.
- 일별 그래프는 KST 기준 오늘 포함 30일을 반환하며 경기 없는 날도 0으로 만든다.

#### 순위

- 한 원본 경기는 각 플레이어의 관점에서 한 경기다.
- 플레이어마다 20전 이상을 대상으로 한다.
- 정렬은 승률 내림차순, 경기 수 내림차순, 마지막 동률은 일관된 이름 정렬 기준을 둔다.
- 대표 조합은 사용 횟수가 많은 조합이며 사용 수가 같으면 캐릭터 ID 정렬 기준으로 결정한다.

#### 프로필 및 검색

- 프로필 요약은 지정 플레이어가 참여한 경기의 해당 플레이어 관점에서 계산한다.
- 플레이 시간은 시작·종료 시간이 모두 있고 종료가 시작보다 이르지 않은 경기만 초 단위 합계에 포함한다.
- 맵 통계는 `map_id IS NOT NULL`인 기록만 대상으로 한다.
- 최근 상대는 소문자 정규화 키로 상대를 합치고 가장 최근 순서로 상위 5명을 반환한다.
- 이름 자동완성은 검색어로 시작하는 prefix 일치이며, 일부 문자열 포함 검색이 아니다.
- 표시할 이름은 검색 규칙에 맞는 최근 기록에서 선택한다.

이 규칙은 UI 장식이 아니라 데이터 계약이다. 시간대를 브라우저 로컬 시간대로 두면 방문자의 위치에 따라 같은 경기가 다른 날짜에 속할 수 있으므로, 사이트 기준은 `Asia/Seoul`(KST)로 정리됐다. KST 외 방문자에게 과거 로컬 계산과 다르게 보일 수 있다는 점도 설계 변경의 의미다.

### 8.6 실제 경기 목록 페이지 RPC

전체 경기 목록과 개인별 목록은 통계 JSON과 분리된 두 페이지 함수로 조회한다.

```text
전체 기록:
MatchesDirectory
  → useMatchPage(page)
  → GET /api/matches?page=N
  → get_all_matches_by_page(page, page_size=10)
  → 행 + total_count

개인 기록:
ProfileView
  → usePlayerMatchPage(name, page, sort)
  → GET /api/matches/player?name=...&page=N&sort=...
  → get_player_matches_by_page(name, page, 10, sort)
  → 행 + total_count + match_number
```

- 페이지는 1부터 시작하고 크기는 서버가 10으로 고정한다.
- 전체 기록과 개인 기록은 조건·필터·정렬 계약이 다르다.
- 개인 기록의 정렬 옵션은 `time`, `wins`, `losses`이며 이름·페이지·정렬값을 검증한다.
- `total_count`는 페이지 수와 이동 UI를 만들기 위한 전체 건수다. 한 페이지에서 모든 행을 반환하는 값이 아니다.
- 개인 경기에는 시간순 `match_number`가 포함되어 다른 정렬을 선택해도 번호의 의미가 유지된다.
- 클라이언트는 HTTP 상태와 응답 JSON을 확인하며, 잘못된 행·ID·건수·페이지 메타데이터를 성공 데이터처럼 받아들이지 않는다.
- 로딩 실패를 빈 성공 배열로 바꾸지 않고 오류로 표시한다.

페이지네이션도 DB 비용을 무료로 만들지는 않는다. 정확한 총건수를 계산하고 OFFSET으로 먼 페이지를 조회하는 방식은 데이터가 커졌을 때 다시 성능 측정이 필요하다. 그렇지만 처음 화면을 띄우기 위해 모든 경기 행을 전송할 필요는 없다.

### 8.7 보안과 응답 검증

데이터베이스 함수는 제한된 결과를 반환하도록 하고, View 직접 SELECT를 차단하는 설정을 적용했다. 각 SQL은 함수 소유자, `SECURITY DEFINER`, 고정 `search_path`, 실행 권한을 확인하는 절차를 포함한다. 공개 anon/authenticated 역할은 허용된 RPC 실행 권한으로 접근하고, 서버에서 Supabase 공개 anon 키로 호출한다. service-role 키를 브라우저로 보내지 않는다.

검증은 여러 계층에 나뉜다.

1. Route Handler가 입력과 필수 파라미터를 확인한다.
2. 서버 RPC 호출부가 정해진 함수와 인자만 사용한다.
3. DB가 계산 및 결과 상한을 적용한다.
4. 서버 응답 파서가 JSON 필드·숫자 범위·배열 크기를 점검한다.
5. 캐시에서 읽은 데이터도 원래 API 파서를 다시 통과한다.
6. 화면은 검증된 결과만 렌더링한다.

따라서 오류, 잘못된 JSON, 미설정 환경변수, DB 오류는 0건 또는 0%인 정상 결과처럼 숨기지 않는다. 실패는 명시적인 API 상태와 UI 오류로 구분한다.

### 8.8 4단계에서 실행한 검증과 수치의 의미

2026-10-01 시점 DB 표본은 172경기였다. 페이지 API에서 `total_count=172`를 기준으로 마지막 페이지까지 전부 요청했고, 응답 행 172개와 고유 ID 172개를 확인했다. View는 172경기에서 선수 관점 행 344개를 만들었다.

기존 JavaScript 통계와 DB RPC 결과를 해당 표본 전체에서 비교한 결과:

- 경기 수, 플레이어 수, 최근 24시간 수가 일치했다.
- 조합의 경기 수·승리 수·승률이 일치했다.
- KST 활동 날짜와 급상승 기간별 수치가 일치했다.
- 캐릭터 픽 횟수와 승률이 일치했다. 동률 ID 6과 62의 표시 순서만 tie-break 차이가 있었다.
- 캐릭터 ID NULL 및 미등록 ID는 표본에서 발견되지 않았다.
- 맵 미등록 ID는 0건이었고 `map_id=NULL` 108건은 양 계산에서 제외됐다.
- 누락/파싱 불가 경기 시각은 표본에서 0건이었다.
- View 직접 SELECT는 anon/authenticated에서 거부됐다.
- Trakeas 프로필 표본은 30전 17승 13패였고, 계산 합계가 일치했다.
- `Fei` prefix 검색은 `Feira_Practice`를 반환했고, 제외 조건이 적용된 검색 결과 없음도 확인했다.

이 검증이 증명하는 것은 172건 표본의 페이지 완전성과 당시 기존 계산과 새 결과의 의미 대조다. 172건은 문제를 일으킬 데이터 규모가 아니라는 점을 숨기지 않는다. 이 수치는 미래 대규모 데이터 부하 테스트가 아니다. 1,000행 조회 상한이 더 큰 표본에서 자르면 누락이 생길 수 있다는 위험은 조회 계약의 구조에서 도출되며, 당시 실제 1,001건 초과 DB를 만들어 재현한 결과라고 표현하지 않는다.

성능 수치도 시점을 구분한다.

| 측정 | 당시 결과 | 해석 범위 |
|---|---:|---|
| 로컬 API 1회 대시보드 호출 | 2,515 ms | 앱과 네트워크를 포함한 단일 관측 |
| 로컬 API 1회 랭킹 호출 | 70 ms | 앱과 네트워크를 포함한 단일 관측 |
| 로컬 API 1회 프로필 호출 | 73 ms | 앱과 네트워크를 포함한 단일 관측 |
| 로컬 API 1회 이름 검색 | 54 ms | 앱과 네트워크를 포함한 단일 관측 |
| SQL Editor DB 함수 실행 | 대시보드 18.977ms, 랭킹 4.040ms, 프로필 5.382ms, 검색 3.405ms | 172경기 표본에서 각각 한 번 실행한 EXPLAIN 결과 |

API 왕복과 DB SQL 실행 시간은 같은 지표가 아니다. API에는 로컬 앱 처리와 네트워크가 들어가며, EXPLAIN 출력은 바깥 함수 호출 문장의 관측이다. 반복 평균, 동시 사용자 부하, 수만 건 이상의 쿼리 계획은 이 기록으로 입증하지 않았다.

## 9. 4→5단계 — 캐시 중심 최종 결과

### 9.1 왜 데이터 정확성을 높인 다음 캐시가 필요했나

4단계에서 통계 계산과 목록 조회를 DB의 명시적인 계약으로 옮기면 브라우저가 전체 경기 배열을 받아 계산하지 않아도 된다. 대신 화면에서 필요한 통계 API, 페이지 RPC, 프로필 데이터 등을 요청한다. 새 구조는 정확성을 개선하지만, 네트워크·서버 응답이 화면에 도착하기를 기다리는 모든 상황을 없애지는 않는다.

따라서 5단계의 목표는 4단계의 집계 기준을 다시 클라이언트 계산으로 되돌리는 것이 아니었다. **검증된 API 응답을 기기 안에 저장하고 재사용하며, 필요한 시점에는 새 응답으로 확인해 정확성 흐름을 보존하면서 대기를 줄이는 것**이었다.

사용자가 직접 전후 사용을 시험한 결과, 모든 조건에서 빨라진 것은 아니지만 캐시를 재사용하는 일부 상황에서는 개선을 확인했고 이에 만족했다. 문서에서는 이 사용자 체감 평가와 제한된 계측 결과를 구분한다.

### 9.2 캐시 계층 구성

현재 캐시 관련 구현은 다음 역할로 나뉜다.

| 구성요소 | 책임 |
|---|---|
| `src/lib/client-cache.ts` | IndexedDB 열기, 레코드 읽기/쓰기, 스키마 버전과 캐시 레코드 검증, freshness 분류, 저장소 보존 요청 |
| `src/lib/cached-api.ts` | 메모리 캐시, IndexedDB 캐시 읽기, API 요청, 키별 in-flight 중복 요청 공유, 캐시 우선 로드와 네트워크 재검증 |
| `src/lib/client-data-requests.ts` | 각 데이터 종류의 URL·검증 parser·오류 메시지·키를 정의하고 초기 및 선택 상대 데이터 준비 |
| `src/hooks/useCachedApi.ts` | 화면 Hook이 로딩·오류·기존 데이터 유지·새 응답 반영·갱신 버전을 사용할 수 있게 연결 |
| 각 데이터 Hook | Dashboard/Ranking/Profile/Match 화면과 공통 캐시 계약을 연결 |

캐시 레코드는 최소한 키, 스키마 버전, `updatedAt`, API 응답 JSON을 가진다. API 응답을 보관할 뿐 서비스의 원본 DB가 되는 것은 아니다. IndexedDB 데이터는 신뢰할 수 없는 입력처럼 다루며, 화면에 쓰기 전에 기존 데이터 파서를 다시 통과시킨다.

### 9.3 요청 키와 데이터 격리

다른 의미의 조회가 한 저장값을 공유하지 않게 각 요청 의미를 키에 포함한다. 구현 예는 다음과 같다.

| 데이터 유형 | 요청 키의 구성 예 |
|---|---|
| 대시보드 | `dashboard` |
| 순위 | `rankings` |
| 전체 경기 페이지 | API와 페이지 번호 |
| 개인 경기 페이지 | 프로필 이름, 페이지, 정렬 |
| 프로필 통계 | 프로필 이름, 선택된 상대 또는 none |
| 이름 제안 | 정확한 검색어와 제외할 이름 |

특히 프로필과 상대 전적은 “선택한 상대가 다른데 이전 상대의 통계를 새 요청 결과처럼 보여 주는 것”을 피하도록 두 입력을 구분한다. 페이지 목록도 이름·페이지·정렬 조건을 분리한다.

동일한 캐시 키에 진행 중인 네트워크 요청이 있으면 별도의 중복 fetch를 만들지 않고 Promise와 결과를 공유한다. 여러 UI가 같은 초기 요청을 시작하거나 Hook과 선조회가 겹쳐도 같은 데이터라면 한 요청을 나눠 쓸 수 있다. 요청 구독자가 모두 취소되면 내부 AbortController로 아직 진행 중인 fetch를 중단할 수 있지만, 브라우저 취소가 이미 DB에서 시작된 처리를 취소한다고 보장하지는 않는다.

### 9.4 캐시 우선 표시 및 재검증 흐름

일반 화면 응답은 화면 진입 때 캐시를 먼저 확인한다.

```text
요청 키로 캐시 조회
  ├─ 검증 가능한 캐시가 없음
  │    → API 요청
  │    → 응답 parser 검증
  │    → 메모리 사용 + IndexedDB 저장 시도
  │    → 화면 적용
  │
  └─ 캐시가 있음
       → 기존 값을 먼저 화면에 적용
       → 신선도에 따라 API 재검증 여부 판단
       → 새 응답을 받으면 검증 후 화면/캐시 교체
       → 갱신 실패 시 기존 데이터 유지 + 오류 표시
```

일반 화면 캐시의 freshness 구간은 구현 상수로 관리한다.

- `updatedAt` 기준 **5초 이내**: fresh. 일반 화면에서는 API를 다시 요청하지 않고 캐시를 사용할 수 있다.
- **5초 초과부터 5분 이내**: stale. 캐시를 표시하면서 사용 시 서버에서 재검증한다.
- **5분 초과**: old. 캐시를 표시 가능한 값으로 유지하되 사용 시 서버 재검증 대상이다.

이 시간들은 주기적 polling 간격도 아니고 저장 레코드를 자동 삭제하는 TTL도 아니다. 화면이 데이터를 사용할 때, 화면이 다시 활성화될 때 freshness를 보고 재검증한다. 일반 화면에서 5초마다 또는 5분마다 타이머 polling을 계속 돌리는 구조는 아니다. 5분 이상 된 값도 저장소에서 자동 삭제하지 않는다.

새 네트워크 응답이 캐시보다 최신이면 새 결과가 기존 결과를 대체한다. 실제 갱신일 때는 데이터 영역의 짧은 강조와 통계 숫자 변화 표현 등을 통해 교체를 알릴 수 있다. 이 문서가 설명하는 핵심은 캐시 교체 조건과 기존값 보존이다.

### 9.5 초기 데이터 준비와 화면 우선

첫 화면에서 서로 독립적인 데이터 요청은 병렬로 미리 시작한다.

```text
대시보드 통계 ─┐
TOP 10 순위   ├─ Promise.all로 병렬 준비
전체 경기 1p  ┘
```

현재 코드의 `prefetchInitialClientData()`는 이 세 요청을 병렬 실행하며 `AppShell`에서 첫 진입 준비를 시작한다. 사용 중인 화면의 Hook도 같은 요청을 시작하면 캐시 계층에서 동일 키 요청을 공유한다. 사용자가 현재 보는 화면은 자신에게 필요한 데이터가 준비되는 즉시 표시하고, 다른 초기 준비 요청을 기다리느라 해당 화면의 렌더링을 묶지 않는다.

모든 프로필·모든 경기 페이지를 미리 가져오는 방식은 아니다. 실제로 앱이 받아온 데이터와 정한 초기 일부 데이터만 보관하고, 프로필 통계는 사용자가 연 프로필 또는 직접 선택한 상대 등 요청된 조건에 한정한다.

### 9.6 검색 캐시는 일반 화면 캐시와 다르게 최신 검색을 보장

닉네임 자동완성은 사용자가 입력할 때마다 결과가 바뀔 수 있고, 신규 플레이어도 나타날 수 있다. 그래서 검색 캐시는 응답을 빠르게 미리 보여주는 용도일 뿐 서버 요청을 생략하는 기준이 아니다.

- 비어 있지 않은 새 검색어가 입력되면 debounce 없이 검색을 시작한다.
- 정확히 같은 검색어와 제외 이름에 해당하는 캐시만 임시 제안으로 표시한다.
- 동시에 최신 서버 검색을 항상 수행한다. 캐시가 비어 있거나 빈 배열이어도 서버를 조회한다.
- 서버 성공 응답은 제안을 교체하고 캐시를 갱신한다.
- 서버 오류 때 캐시 후보를 최신 검색 결과인 것처럼 단정하지 않고 실패를 알린다.
- 빠른 입력으로 검색어가 바뀌면 이전 브라우저 요청을 취소하고 이전 응답이 현재 검색어 결과를 덮지 않도록 키를 확인한다.
- 서버 검색 결과 최대 10개, prefix 매칭, 이름 길이와 제외 값 같은 기존 API 계약을 유지한다.

선택된 상대의 프로필 조회는 자동완성 결과 전체를 미리 요청하지 않는다. 사용자가 실제로 한 상대를 선택했을 때 그 상대 통계만 시작하고, 제출 때 진행 중이거나 캐시된 같은 키를 재사용한다.

### 9.7 저장 보존과 실패 대응

IndexedDB는 브라우저와 기기별 로컬 저장소다.

- 앱은 `navigator.storage.persist()`를 지원하는 브라우저에서 보존 요청을 시도한다.
- 브라우저는 허용 여부를 결정하며 요청 성공이 영구 저장이나 저장 공간 예약을 보장하지 않는다.
- IndexedDB 미지원, open/read/write 실패가 나더라도 API 네트워크 경로를 사용할 수 있어야 한다.
- 쓰기가 실패하면 오류를 기록하고 현재 받은 응답은 메모리에서 사용 가능하게 둔다.
- 앱은 저장 용량을 확보하려고 자기 캐시를 자동 삭제하거나 다른 사이트 데이터를 삭제하지 않는다.
- 브라우저 자체의 정리나 사용자의 사이트 데이터 삭제는 가능하므로 다음 방문까지 값이 남는다고 보장하지 않는다.
- 캐시 저장값의 스키마 버전이 맞지 않거나 API parser가 거부하면 정상 UI 데이터로 사용하지 않고 네트워크를 통해 다시 받는다. 자동 정리 목적으로 기존 레코드를 삭제하지 않는다.

즉 캐시는 성능 보조 수단이지 단일 진실 원천이 아니다. DB/API 오류와 저장 오류는 다른 의미다. IndexedDB 쓰기가 실패해도 새 API 응답 자체가 실패한 것은 아니며, 서버 요청이 실패했다고 해서 이전 캐시가 최신이라고 보장되는 것도 아니다.

### 9.8 캐시가 오래될 수 있는 위험

DB에 새 기록이 생기면 브라우저에 저장된 통계와 경기 페이지는 한동안 이전 값일 수 있다.

| 캐시 대상 | 가능한 최신성 차이 | 처리 원칙 |
|---|---|---|
| 대시보드·TOP 10 | 새 경기로 집계와 순위가 바뀜 | 캐시를 먼저 보여주고 재검증, 갱신 실패는 최신이라고 숨기지 않음 |
| 프로필·상대 통계 | 새 경기로 승률/상대 전적 변동 | 키에 플레이어와 상대를 포함하고 이전 조건 데이터를 섞지 않음 |
| 경기 페이지 | 새 경기로 최신순 페이지 경계가 이동 | 페이지별 키를 구분하고 현재 페이지를 재검증 |
| 이름 제안 | 신규 이름이 없거나 변경된 이름이 남음 | 캐시만으로 결과 없음 확정 금지, 매 검색 때 서버 재검증 |

서로 다른 API 응답은 조회 시점이 조금 다를 수 있다. 모든 카드가 같은 DB 스냅샷에서 계산됐다고 가정하지 않는다. 응답 캐시를 사용해도 API 간 시점 차이는 남을 수 있으며, 캐시 재검증은 온라인 연결과 API 성공에 의존한다.

### 9.9 실제 4→5단계 전후 비교

속도 비교 보고서의 관측은 2026-10-02 시점 로컬 프로덕션 빌드와 당시 172경기·38명의 데이터를 사용했다. 같은 브라우저와 환경 변수, 로컬 데이터 원본을 활용하려 했으며 첫 방문은 IndexedDB를 지우고 브라우저 HTTP 캐시를 끄는 방식, 재방문은 앱 캐시를 유지하는 방식으로 측정했다.

| 화면·조건 | 4단계(최적화 전) | 5단계(캐시 적용 후) | 관찰 내용 |
|---|---:|---:|---|
| 홈, 캐시 없는 새로고침 | 5회: 361, 379, 404, 409, 411ms (중앙값 404ms) | 4회: 389, 389, 426, 956ms (중앙값 407.5ms) | 첫 화면 중앙값은 사실상 비슷함. 956ms는 초기 서버 지연 영향을 받은 관측 |
| 홈 API 응답량 | 경기 API 약 58.8KB | 대시보드·순위·경기 1페이지 합계 약 6.2KB | 통계 전용 결과와 첫 페이지 구성이어서 전송량 감소 |
| 프로필 직접 방문 | 당시 273~1,822ms 관측 | 캐시 없는 590ms 관측 | 표본 횟수·실행 초기화가 일정하지 않아 대표 속도 수치 아님 |
| 프로필 재방문 | 기존 버전은 재방문에도 API 요청 관찰 | 신선한 IndexedDB 캐시에서 334ms, API 요청 0회 관찰 | 캐시를 재사용해 서버 요청을 생략한 사례 |
| 프로필 관련 API 응답량 | 경기 API와 플레이어 경기 합계 약 89.8KB | 대시보드·순위·경기 1페이지·프로필·플레이어 경기 합계 약 11.2KB | 요청 구성 자체가 완전히 같은 실험은 아님 |

이 결과를 “모든 화면의 로딩 속도가 항상 빨라졌다”고 일반화하면 안 된다. 캐시 없는 홈 최초 표시의 중앙값은 사실상 비슷했다. 반면 API 데이터량은 크게 줄었고, 프로필 재방문에서 API를 요청하지 않은 사례가 관찰됐다. 사용자가 실제로 시험한 경험에서도 일부 상황이 4단계보다 빨라졌으며 그 개선에 만족했다. 따라서 결론은 **캐시가 재방문과 일부 데이터 요청 대기를 줄이는 데 유효했고, 모든 최초 방문·모든 화면에서 속도 향상을 입증한 것은 아니다**이다.

### 9.10 성능 측정과 기능 검증의 한계

속도 보고서가 명시한 한계는 다음과 같다.

- 양쪽 측정 횟수가 다르고 적어 엄밀한 통제 실험이 아니다.
- 측정은 실제 운영 서버가 아니라 로컬 프로덕션 빌드에서 수행했다.
- 실행 순서, 브라우저 상태, DB/API 초기 응답, 렌더링, 개발자 도구 상태가 값에 영향을 줄 수 있다.
- 비교 대상 `.next` 산출물의 빌드 생성 시점이 다르고, 최적화 전 폴더에 미커밋 프로필 파일 변경이 있었다.
- 당시 172경기였으므로 1,000행 초과 규모의 정확성/성능 비교는 재현하지 않았다.
- 수만 건 데이터 부하 테스트, 동시 사용자 테스트, 장시간 캐시 보존 테스트를 하지 않았다.
- 실제 새 경기 응답을 앱에 주입한 경기 카드 등장의 완전한 end-to-end 시각 확인은 별도 한계로 기록됐다.
- 프로필 경기 목록 390px 모바일과 standalone PWA 화면은 렌더링과 가로 넘침 여부를 확인했지만 모든 화면에 대한 시각 회귀 검사는 아니었다.

자동 검증 기록에는 당시 전체 테스트 36개 통과, ESLint, TypeScript `--noEmit`, Next.js 프로덕션 빌드 통과가 포함된다. 확인된 테스트 범위는 캐시 freshness 경계, IndexedDB 오류 fallback, 동일 키 요청 공유와 구독 취소, stale 캐시에서 실패, 초기 요청 준비, 요청 키 검증 등을 포함했다.

### 9.11 각 화면에서 API까지의 실제 호출 경로

통계 자료는 함수 목록만 기록한 것이 아니라 화면이 어떤 컴포넌트·Hook·Route Handler·DB RPC를 통과하는지도 구체적으로 추적했다. 이 정보는 원래 담당 모듈을 찾거나 화면 동작을 수정할 때 필요하다.

| 기능 | 화면 | Hook/요청 | Next.js API | DB 호출 | 응답을 확인하는 코드 |
|---|---|---|---|---|---|
| 홈 통계 | `DashboardHome` | `useDashboardStatistics` | `/api/statistics/dashboard` | `get_dashboard_statistics()` | `dashboard-statistics.ts` |
| 플레이어 랭킹 | `PlayersRanking` | `usePlayerRankings` | `/api/statistics/rankings` | `get_player_rankings()` | `player-rankings.ts` |
| 프로필 통계 | `ProfileView` | `useProfileStatistics` | `/api/statistics/profile` | `get_player_statistics(p_player_name, p_opponent_name)` | `profile-statistics.ts` |
| 이름 제안 | 상단 검색·상대 검색·PWA 저장 프로필 검색 | `usePlayerNameSuggestions` | `/api/statistics/search` | `search_player_names(p_query, p_exclude_name)` | `profile-statistics.ts`의 이름 parser |
| 전체 경기 페이지 | `MatchesDirectory` | `useMatchPage(page)` | `/api/matches?page=N` | `get_all_matches_by_page(...)` | `match-pages.ts` |
| 개인 경기 페이지 | `ProfileView` | `usePlayerMatchPage(name, page, sort)` | `/api/matches/player` | `get_player_matches_by_page(...)` | `match-pages.ts`와 필수 번호 검증 |

Route Handler는 HTTP 입력을 확인하고 서버에서 Supabase RPC를 호출한다. 서버 RPC 경계는 허용된 함수·인자 형태를 제한하고, 응답 parser는 DB JSON을 검증된 앱 타입으로 정규화한다. Hook은 데이터 로드/취소·캐시와 화면 상태를 연결한다. 같은 `ProfileView`가 통계와 경기 목록을 모두 보여도 통계 RPC의 JSON 안에 모든 경기 행을 함께 실어 보내지는 않는다.

오류 경계도 상태에 따라 나뉜다. 쿼리 입력 오류는 HTTP 400, 서버 Supabase 설정이 없으면 503, Supabase RPC 실패나 계약에 맞지 않는 결과면 502를 사용한다. Route가 `Cache-Control: no-store`를 지정하는 경우에도 브라우저 앱 캐시로 응답을 재사용할 수 있다. HTTP 캐시와 IndexedDB 응답 캐시는 서로 다른 캐시 계층이다. 클라이언트 API 오류는 응답의 `warning`이 있으면 화면 오류로 사용하고, 그렇지 않으면 해당 요청의 표준 오류 메시지를 쓴다.

### 9.12 이름 자동완성의 화면별 동작과 비용 경계

이름 제안 Hook은 상단 플레이어 검색, 프로필 상대 검색, PWA 저장 프로필 추가 검색에서 공유한다. 한 글자 이상 입력하면 250ms debounce 없이 즉시 서버 검색을 시작하고, 정확히 같은 검색어와 제외 이름 조합의 로컬 캐시가 있으면 먼저 임시 후보로 보여준다. 빈 검색어는 전체 플레이어 디렉터리를 뜻하지 않으며 서버도 빈 배열을 반환한다. 클라이언트는 검색 결과를 최대 10개까지 받고, 상대 검색 화면은 그중 최대 5개를 보여준다.

캐시 후보가 없는 경우에도 서버 요청을 생략하지 않는다. 검색 결과 없음은 서버 성공 뒤에만 확정하며, 오래된 후보를 보여주던 중 서버 오류가 나면 최신 검색 실패를 함께 표시한다. 신규 플레이어가 과거 캐시 때문에 검색 불가가 되지 않게 하는 정책이다. 빠른 타이핑은 글자별 네트워크 요청을 만들 수 있다. 새 검색어는 이전 브라우저 fetch를 중단하고 응답 키를 비교해 오래된 후보가 현재 입력을 덮지 않게 하지만, 브라우저의 abort가 이미 실행 중인 PostgreSQL 함수까지 취소한다고 보장하지 않는다. 따라서 브라우저 fetch 횟수와 Supabase DB 함수 호출 횟수를 같은 수로 단정하지 않는다.

제안 선택과 검색 제출도 구분한다. 상단 검색과 PWA는 선택한 이름으로 이동/저장을 진행한다. 프로필 상대 검색은 선택 순간 그 한 명의 프로필 통계를 미리 요청하지만, 버튼이나 Enter로 제출하기 전까지 현재 적용 상대 결과를 바꾸지 않는다. 제출 때는 같은 키의 진행 중 Promise 또는 캐시 결과를 재사용한다. 선택하지 않은 모든 제안 상대의 전적을 미리 불러오지 않는다. 자동완성에는 최소 입력 글자 수 정책을 추가하지 않았으며, 향후 변경 시 DB 검색 계약과 함께 검토해야 한다.

### 9.13 상대 전적 검색에서 발견한 프로필 본문 깜빡임

상대 이름을 바꾸어 제출할 때 프로필 통계의 캐시 키는 `플레이어 이름 + 상대 이름`으로 달라진다. 이전 Hook 구현은 새 키 데이터가 도착하기 전 반환할 `data`가 없어졌고, 프로필 UI가 `profileStatistics` 존재 여부를 기준으로 요약·태그 조합·맵 통계를 렌더링했기 때문에 본문 전체가 잠시 사라졌다가 재등장했다. 브라우저 페이지 전환이나 전체 새로고침이 아니라, React 상태에서 기존 데이터가 제거된 현상이었다.

수정 후에는 새 상대 요청이 진행되는 동안 직전의 성공한 프로필 통계를 Hook 결과에 유지한다. 상대 전적 영역은 로딩 상태를 별도로 표시하고, 새 상대 조회 성공 후 결과를 교체한다. 조회 성공 결과가 비어 있으면 전적 없음 상태를 표시하며, 요청 실패는 기존 프로필 내용을 남긴 채 오류로 나타낸다. 이전 상대의 전적을 새 상대의 결과인 것처럼 표시하지 않는다. 입력을 지우면 적용 상대를 해제하지만, 다른 이름을 입력 중일 때는 기존 적용 상대를 유지하고 제출 시 새 선택을 적용한다. 첫 프로필 진입 전 성공 데이터가 전혀 없을 때는 최초 로딩 화면을 그대로 사용한다.

이 내용은 데이터 요청 키, Hook의 이전 데이터 유지, 화면의 각 영역 조건부 렌더링이 함께 원인이었던 결함과 수정이다. 단지 “캐시로 깜빡임을 해결했다”라고 요약하면 어느 데이터가 남고 어느 데이터가 교체되는지 중요한 UX 규칙이 사라지므로 이 동작 계약을 보존한다.

### 9.14 캐시 단계에서 고정한 경계와 미실시 범위

- IndexedDB는 브라우저/기기 간 동기화 수단이 아니다.
- Service Worker의 API 응답 캐시나 HTTP cache 정책은 추가하지 않았다. 여기서 다루는 지속 캐시는 IndexedDB 기반 앱 캐시다.
- 자동 만료·용량 회수용 삭제·타 사이트 데이터 삭제는 구현하지 않는다.
- 자동완성 최소 글자 수와 미확정된 페이지 간 일관성/무효화 정책을 임의로 추가하지 않는다.
- 캐시된 여러 API 응답은 각각 다른 시점에 생성될 수 있으며 하나의 DB snapshot으로 취급하지 않는다.
- 새 RPC를 만들거나 집계를 브라우저로 되돌리거나 모든 경기 행을 한 번에 내려받는 것은 캐시 개선 범위가 아니다.
- 자동화 기능 테스트 36개, lint, TypeScript `--noEmit`, 프로덕션 build는 기록되어 있으나 실제 서비스 운영 부하·다수 동시 사용자·대규모 DB 시험은 이 결과에 포함되지 않는다.

## 10. 5단계에서 캐시와 화면 갱신 표시의 관계

새 데이터가 기존 캐시를 실제로 대체하는 경우와 첫 로드·신선 캐시 재사용은 다르다. 화면 갱신 효과는 새 서버 응답이 기존 캐시를 대체했다는 사용자 피드백으로 제한한다.

- 캐시가 전혀 없는 최초 로드에는 갱신 효과를 주지 않는다.
- 값이 같은 신선 캐시를 그대로 표시한 경우에도 새 데이터 갱신 효과로 취급하지 않는다.
- 서버 갱신 실패는 데이터 갱신 성공 효과로 표시하지 않는다.
- 새 경기 기록은 이전/새 페이지의 경기 ID를 비교해 실제로 추가된 카드만 식별한다.
- 숫자 통계의 카운트 애니메이션은 캐시 대체 시 새 값과 이전 값의 차이를 보여주는 UI 피드백이다.

## 11. 단계 사이에서 반복된 설계 원칙

### 11.1 계획과 구현을 구분한다

전환 계획서에 App Router, Tailwind, 모듈화를 적어 두어도 실제 코드를 확인하지 않으면 달성 여부를 알 수 없다. 2단계는 이 점을 직접 보여 준다. 계획 목표는 다음 단계의 구현·검증 기준으로 연결되어야 한다.

### 11.2 기능 구조, 데이터 계산, 속도 최적화는 각각 다른 층이다

- 컴포넌트 분리는 파일 책임과 변경 범위를 다룬다.
- DB 집계는 통계 계산의 데이터 범위와 분모 의미를 다룬다.
- 페이지 RPC는 실제 경기 행을 요청 단위로 제공한다.
- 캐시는 유효한 응답을 다시 사용해 네트워크 대기를 줄인다.

한 층의 개선으로 다른 층 문제가 자동 해결되지 않는다. 예를 들어 캐시를 넣어도 잘못 계산된 통계가 정확해지는 것은 아니며, 정확한 RPC를 만들어도 응답을 매번 기다리는 문제는 별개로 남을 수 있다.

### 11.3 성공 응답처럼 보이는 잘못된 값으로 오류를 감추지 않는다

요청 실패, 잘못된 API JSON, 캐시 형식 오류, 빈 결과는 의미가 다르다. 특히 잘못된 데이터를 빈 배열이나 0으로 조용히 바꾸면 사용자는 “기록이 없음”과 “조회 실패”를 구별할 수 없다. 현재 구조는 파서와 오류 상태를 통해 이 차이를 드러내고, 기존 유효 캐시를 사용할 때도 갱신 실패를 알리는 것을 원칙으로 한다.

### 11.4 전체 집계와 제한된 결과 배열은 양립한다

화면에 상위 6개만 보인다고 DB가 6행만 집계하는 것은 아니다. 전체 대상 표본에서 계산한 뒤 최대 6개만 응답할 수 있다. 반대로 1,000행을 받아 그 배열에서 계산한 통계는 응답 배열 자체가 잘린 표본일 수 있다. “DB 결과를 제한했다”와 “집계 범위를 제한했다”는 서로 다른 개념이다.

### 11.5 캐시 데이터는 최신 데이터라는 보장이 아니다

캐시는 응답을 다시 쓸 수 있게 하지만, DB가 갱신된 이후에는 값이 잠시 오래됐을 수 있다. 온라인 재검증, 오류 표시, 요청 키 격리가 함께 필요하다. 브라우저 저장소는 공간 보존 및 영구성을 보장하지 않으므로, 네트워크 요청을 대체하는 영구 DB로 설명하면 안 된다.

## 13. 최종 요약

TAG2.GG 프론트엔드는 단순히 HTML에서 Next.js로 한 번 갈아탄 프로젝트가 아니다.

1. 바닐라 웹에서는 기능을 빠르게 구현했지만 화면·스타일·데이터 로직이 큰 파일들에 집중됐다.
2. Next.js 전환에서는 계획한 아키텍처가 실제 구현에 충분히 반영되지 않아 큰 페이지·전역 CSS·해시 상태·제한된 데이터 요청이 남았다.
3. 구조 리팩터링 단계에서 이 문제를 다시 설계하고 App Router, 책임별 모듈, Tailwind와 차트/모션 도구를 프로젝트 구조에 맞게 연결했다.
4. 통계 보완 단계에서는 전체 통계를 DB에서 집계하고, 개별 경기 화면은 현재 페이지의 실제 행만 조회해 정확성·전송 계약을 분리했다.
5. 캐시 개선 단계에서는 그 데이터 계약을 유지하면서 IndexedDB·메모리 캐시, 초기 병렬 준비, 요청 공유와 백그라운드 재검증을 추가해 일부 재방문·요청 상황을 개선했다.

마지막 단계의 핵심 성과는 “항상 모든 화면이 더 빨라졌다”가 아니다. **정확성을 희생하지 않는 구조를 유지하면서 응답을 재사용할 수 있게 했고, 실제 측정에서 전송량 감소와 캐시 재방문 API 생략을 확인했으며, 사용자는 일부 상황의 개선을 체감했다**는 것이다. 동시에 최초 로딩 중앙값이 비슷했던 점과 대규모 부하 검증이 없다는 점도 함께 기억해야 한다.

## 14. 삭제 예정 기술 자료에서 보존해야 할 실행 원문

이 발전 자료는 결과를 설명하는 요약만으로 충분하지 않다. DB 함수나 데이터 계약을 나중에 검토·복구해야 하는 경우를 위해, 아래에 당시 기록한 SQL을 실행 가능한 텍스트 형태로 함께 보존한다. SQL 주석과 검증 쿼리도 코드의 일부로 포함한다. 임의로 재구성하거나 요약한 의사 코드가 아니다.

> **실행 주의:** 이 부록은 변경 당시 기록의 보존본이지, 지금 임의로 운영 DB에 재실행하라는 지시가 아니다. 통계 SQL에는 `CREATE OR REPLACE FUNCTION`, 소유권 및 권한 변경이 들어 있고 페이지 함수는 기존 데이터 접근 계약을 바꾼다. 재적용 전에는 현재 DB의 함수 정의, View, 권한, RLS, PostgREST schema cache와 애플리케이션의 parser/API 계약을 대조해야 한다. SQL 원문과 실제 운영 DB 상태는 자동 동기화되지 않는다.

### 14.1 선수 관점 View 정의와 직접 조회 차단

통계 RPC들이 공유하는 `public.v_player_match_rows` View는 원본 경기 한 건을 P1/P2의 관점으로 각각 한 행씩 표현한다. 당시 계산 설계 문서에 보존된 정의는 다음과 같다.

```sql
CREATE VIEW public.v_player_match_rows AS
SELECT
  m.id AS match_id,
  m.p1_name AS player_name,
  m.p2_name AS opponent_name,
  lower(m.winner) = lower(m.p1_name) AS is_win,
  m.p1_main_character_id AS player_main_character_id,
  m.p1_sub_character_id AS player_sub_character_id,
  m.map_id,
  m.start_time,
  m.end_time,
  coalesce(m.end_time, m.created_at) AS played_at
FROM public.matches AS m
UNION ALL
SELECT
  m.id AS match_id,
  m.p2_name AS player_name,
  m.p1_name AS opponent_name,
  lower(m.winner) = lower(m.p2_name) AS is_win,
  m.p2_main_character_id AS player_main_character_id,
  m.p2_sub_character_id AS player_sub_character_id,
  m.map_id,
  m.start_time,
  m.end_time,
  coalesce(m.end_time, m.created_at) AS played_at
FROM public.matches AS m;

REVOKE ALL PRIVILEGES ON TABLE public.v_player_match_rows
  FROM PUBLIC, anon, authenticated;
NOTIFY pgrst, 'reload schema';
```

`lower(winner) = lower(player_name)`은 대소문자를 무시한 승리 판정이며, `winner`가 NULL이면 승패 판정도 NULL로 남는다. 캐릭터 ID NULL을 0으로 보정하는 일은 View 자체가 아니라 소비하는 각 통계 SQL의 규칙이다. `coalesce(end_time, created_at)`는 종료 시각 우선, 없으면 등록 시각으로 `played_at`을 정한다. `UNION ALL`로 원본 경기의 양쪽 관점을 중복 제거 없이 보존한다. View는 물리 캐시 테이블이 아니다.

`REVOKE`는 API 역할의 View 직접 조회를 막고 RPC가 정한 결과 상한을 우회해 원본 관점 행 전체를 읽는 것을 방지하기 위한 명령이다. 이 View 조각의 transaction 및 현재 운영 환경에서의 적용 상태는 DB 상태와 함께 별도로 확인해야 한다.

### 14.2 대시보드 통계 RPC 원문

```sql
-- 05. 대시보드 통계 RPC
-- 처음 읽는다면 01-start-here.md, 02-data-flow.md, 03-calculation-design.md를 먼저 읽습니다.
-- Supabase SQL Editor에서 이 파일 전체를 실행합니다.
-- BEGIN~COMMIT 구간은 함수와 권한을 변경합니다. 그 뒤 SELECT들은 읽기 전용 검증입니다.
-- 함수는 전체 경기 행 대신 집계 JSON 하나를 반환합니다.
BEGIN;

-- 기존 같은 이름의 함수를 새 정의로 교체합니다.
CREATE OR REPLACE FUNCTION public.get_dashboard_statistics()
-- 반환되는 값의 형식은 JSON입니다.
RETURNS jsonb
-- 함수 본문은 SQL 쿼리 한 개입니다.
LANGUAGE sql
-- 데이터를 변경하지 않는 읽기 함수임을 표시합니다.
STABLE
-- 함수 소유자 권한으로 실행합니다. 아래에서 owner를 postgres로 지정합니다.
SECURITY DEFINER
-- 호출 환경과 무관하게 객체 탐색 경로를 고정합니다.
SET search_path = pg_catalog, public
-- $function$ 표식 사이가 함수의 실제 SQL 본문입니다.
AS $function$
WITH
-- 현재 순간과 한국 날짜를 한 번 정해 계산 전체에서 재사용합니다.
clock AS MATERIALIZED (
  SELECT
    statement_timestamp() AS now_at,
    (statement_timestamp() AT TIME ZONE 'Asia/Seoul')::date AS today
),
-- 선수 관점 View에서 정상 이름을 가진 행만 가져옵니다.
-- 누락된 캐릭터 ID는 기존 정규화 규칙에 맞춰 0으로 처리합니다.
valid_player_rows AS MATERIALIZED (
  SELECT
    match_id,
    btrim(player_name) AS player_name,
    btrim(opponent_name) AS opponent_name,
    is_win,
    coalesce(player_main_character_id, 0)::integer AS main_character_id,
    coalesce(player_sub_character_id, 0)::integer AS sub_character_id,
    played_at
  FROM public.v_player_match_rows
  WHERE nullif(btrim(player_name), '') IS NOT NULL
    AND nullif(btrim(opponent_name), '') IS NOT NULL
),
-- View의 양쪽 선수 관점 행을 경기 ID로 묶어 원본 경기 단위로 되돌립니다.
valid_matches AS MATERIALIZED (
  SELECT
    match_id,
    max(played_at) AS played_at
  FROM valid_player_rows
  GROUP BY match_id
),
-- 경기 수, 공백 제거한 고유 플레이어 수, KST 오늘 대전 수를 계산합니다.
summary AS (
  SELECT
    (SELECT count(*) FROM valid_matches) AS total_matches,
    (SELECT count(DISTINCT player_name) FROM valid_player_rows) AS total_players,
    (
      SELECT count(*)
      FROM valid_matches AS m
      CROSS JOIN clock AS c
      WHERE m.played_at >= (c.today::timestamp AT TIME ZONE 'Asia/Seoul')
        AND m.played_at <= c.now_at
    ) AS today_matches
),
-- 플레이어별 메인/서브 두 슬롯을 각각 펼쳐 캐릭터별 픽 수를 셉니다.
character_counts AS (
  SELECT
    character_ids.character_id,
    count(*) AS pick_count
  FROM valid_player_rows AS r
  CROSS JOIN LATERAL (
    -- VALUES 두 행이 메인·서브 캐릭터 슬롯 하나씩을 나타냅니다.
    VALUES (r.main_character_id), (r.sub_character_id)
  ) AS character_ids(character_id)
  GROUP BY character_ids.character_id
),
-- 선수 관점별 캐릭터 조합의 경기 수와 승리 수를 계산합니다.
combo_counts AS (
  SELECT
    -- 캐릭터 ID를 정렬해 태그 순서만 다른 조합을 하나로 합칩니다.
    least(main_character_id, sub_character_id) AS character_a_id,
    greatest(main_character_id, sub_character_id) AS character_b_id,
    count(*) AS games,
    -- TRUE인 승리만 계산합니다. NULL은 승리로 간주하지 않습니다.
    count(*) FILTER (WHERE is_win IS TRUE) AS wins
  FROM valid_player_rows
  GROUP BY
    least(main_character_id, sub_character_id),
    greatest(main_character_id, sub_character_id)
  -- 10전 미만 조합은 고승률 목록 후보에서 제외합니다.
  HAVING count(*) >= 10
),
-- 오늘을 포함한 KST 기준 최근 30일의 날짜 행을 만듭니다.
activity_days AS (
  SELECT c.today - offsets.day_offset AS activity_date
  FROM clock AS c
  CROSS JOIN generate_series(29, 0, -1) AS offsets(day_offset)
),
-- 경기 없는 날도 0으로 출력하기 위해 날짜 목록에서 경기로 LEFT JOIN합니다.
activity_counts AS (
  SELECT
    d.activity_date,
    count(m.match_id) AS match_count
  FROM activity_days AS d
  LEFT JOIN valid_matches AS m
    -- 날짜 시작 시각 이상
    ON m.played_at >= (d.activity_date::timestamp AT TIME ZONE 'Asia/Seoul')
   -- 다음 날 시작 시각 미만(시작 포함·끝 제외)
   AND m.played_at < ((d.activity_date + 1)::timestamp AT TIME ZONE 'Asia/Seoul')
  GROUP BY d.activity_date
),
-- KST 기준 최근 14일에서 직전 7일과 최근 7일을 플레이어별로 나눕니다.
player_periods AS (
  SELECT
    -- 대소문자만 다른 이름을 같은 급상승 후보로 묶습니다.
    lower(r.player_name) AS player_key,
    -- 화면에 보여줄 이름은 가장 최근 경기의 표기를 사용합니다.
    (array_agg(r.player_name ORDER BY r.played_at DESC NULLS LAST, r.match_id DESC))[1] AS player_name,
    count(*) FILTER (
      WHERE r.played_at < ((c.today - 6)::timestamp AT TIME ZONE 'Asia/Seoul')
    ) AS previous_games,
    count(*) FILTER (
      WHERE r.played_at < ((c.today - 6)::timestamp AT TIME ZONE 'Asia/Seoul')
        AND r.is_win IS TRUE
    ) AS previous_wins,
    count(*) FILTER (
      WHERE r.played_at >= ((c.today - 6)::timestamp AT TIME ZONE 'Asia/Seoul')
    ) AS recent_games,
    count(*) FILTER (
      WHERE r.played_at >= ((c.today - 6)::timestamp AT TIME ZONE 'Asia/Seoul')
        AND r.is_win IS TRUE
    ) AS recent_wins
  FROM valid_player_rows AS r
  CROSS JOIN clock AS c
  WHERE r.played_at >= ((c.today - 13)::timestamp AT TIME ZONE 'Asia/Seoul')
    AND r.played_at < ((c.today + 1)::timestamp AT TIME ZONE 'Asia/Seoul')
  GROUP BY lower(r.player_name)
),
-- 두 기간 각각 10전 이상인 사람의 기간별 승률을 계산합니다.
rising_candidates AS (
  SELECT
    player_key,
    player_name,
    previous_games,
    previous_wins,
    recent_games,
    recent_wins,
    previous_wins::numeric * 100 / previous_games AS previous_rate,
    recent_wins::numeric * 100 / recent_games AS recent_rate
  FROM player_periods
  WHERE previous_games >= 10
    AND recent_games >= 10
),
-- 승률이 실제로 상승한 후보 중 상승폭이 가장 큰 한 명을 고릅니다.
rising AS (
  SELECT *
  FROM rising_candidates
  WHERE recent_rate > previous_rate
  ORDER BY
    recent_rate - previous_rate DESC,
    recent_games DESC,
    -- 위 조건까지 완전히 동률일 때 이름 순으로 고정합니다.
    player_key COLLATE "C" ASC
  LIMIT 1
)
-- 앱 API가 사용하는 응답 필드를 한 JSON 객체에 담습니다.
SELECT jsonb_build_object(
  -- 총 경기 수, 고유 플레이어 수, 한국 시간 기준 오늘 경기 수
  'totalMatches', s.total_matches,
  'totalPlayers', s.total_players,
  'todayMatches', s.today_matches,
  -- 캐릭터 배열: ID, 픽 횟수, 전체 캐릭터 슬롯 대비 비율
  'characters', coalesce(
    (
      SELECT jsonb_agg(
        jsonb_build_object(
          'id', ranked.character_id,
          'count', ranked.pick_count,
          'rate', ranked.pick_count::numeric * 100 / (s.total_matches * 4)
        )
        -- 픽 횟수 내림차순, 동률은 캐릭터 ID 오름차순
        ORDER BY ranked.pick_count DESC, ranked.character_id ASC
      )
      FROM (
        SELECT character_id, pick_count
        FROM character_counts
        ORDER BY pick_count DESC, character_id ASC
        LIMIT 6
      ) AS ranked
    ),
    -- 데이터가 없으면 SQL NULL 대신 빈 JSON 배열
    '[]'::jsonb
  ),
  -- 태그 조합 배열: ID 2개, 경기/승리 수, 승률
  'combos', coalesce(
    (
      SELECT jsonb_agg(
        jsonb_build_object(
          'ids', jsonb_build_array(ranked.character_a_id, ranked.character_b_id),
          'games', ranked.games,
          'wins', ranked.wins,
          'rate', ranked.wins::numeric * 100 / ranked.games
        )
        ORDER BY
          ranked.wins::numeric / ranked.games DESC,
          ranked.games DESC,
          ranked.character_a_id ASC,
          ranked.character_b_id ASC
      )
      FROM (
        SELECT character_a_id, character_b_id, games, wins
        FROM combo_counts
        ORDER BY
          wins::numeric / games DESC,
          games DESC,
          character_a_id ASC,
          character_b_id ASC
        LIMIT 6
      ) AS ranked
    ),
    '[]'::jsonb
  ),
  -- 해당자가 없으면 JSON null을 반환
  'rising', coalesce(
    (
      SELECT jsonb_build_object(
        'name', player_name,
        'previous', jsonb_build_object('games', previous_games, 'wins', previous_wins),
        'recent', jsonb_build_object('games', recent_games, 'wins', recent_wins),
        'previousRate', previous_rate,
        'recentRate', recent_rate
      )
      FROM rising
    ),
    'null'::jsonb
  ),
  -- 최근 KST 날짜 30개의 그래프 데이터
  'activity', (
    SELECT jsonb_agg(
      jsonb_build_object(
        -- API 내부에서 안정적으로 처리할 ISO 날짜
        'key', to_char(activity_date, 'YYYY-MM-DD'),
        'label',
          -- 화면에 보여줄 월/일 문자열
          extract(month FROM activity_date)::integer::text
          || '/'
          || extract(day FROM activity_date)::integer::text,
        'count', match_count
      )
      -- 과거에서 오늘 순으로 정렬
      ORDER BY activity_date
    )
    FROM activity_counts
  )
)
FROM summary AS s;
$function$;

ALTER FUNCTION public.get_dashboard_statistics() OWNER TO postgres;

-- 예상치 못한 기본/기존 실행 권한을 회수합니다.
REVOKE ALL PRIVILEGES
  ON FUNCTION public.get_dashboard_statistics()
  FROM PUBLIC, anon, authenticated;

-- 브라우저 경로의 anon/authenticated만 RPC를 실행할 수 있게 합니다.
GRANT EXECUTE
  ON FUNCTION public.get_dashboard_statistics()
  TO anon, authenticated;

-- PostgREST가 함수 정의를 다시 읽도록 알립니다.
NOTIFY pgrst, 'reload schema';

-- 함수와 권한 변경을 확정합니다.
COMMIT;

-- 검증 1: DB 카탈로그에서 owner/security/search_path/실행 권한을 읽습니다.
SELECT
  -- 함수 이름
  p.proname AS function_name,
  -- 내부 owner ID를 사람이 읽을 수 있는 역할 이름으로 변환
  pg_get_userbyid(p.proowner) AS owner_name,
  -- true이면 SECURITY DEFINER 설정
  p.prosecdef AS is_security_definer,
  -- 함수에 고정한 search_path 등 실행 설정
  p.proconfig AS function_settings,
  -- anon 역할의 EXECUTE 권한 여부
  has_function_privilege('anon', p.oid, 'EXECUTE') AS anon_can_execute,
  -- authenticated 역할의 EXECUTE 권한 여부
  has_function_privilege('authenticated', p.oid, 'EXECUTE') AS authenticated_can_execute
-- PostgreSQL이 함수 정의/속성을 저장하는 시스템 카탈로그
FROM pg_proc AS p
-- 함수가 public 스키마에 있는지 이름으로 찾기 위해 스키마 카탈로그와 연결
JOIN pg_namespace AS n ON n.oid = p.pronamespace
-- public 스키마 안에서 대상 함수 하나만 검사
WHERE n.nspname = 'public'
  AND p.proname = 'get_dashboard_statistics';

-- 검증 2: 실제 반환 JSON과 배열 상한을 검사합니다.
-- 함수 응답을 payload라는 이름의 한 행 결과로 준비
WITH result AS (
  SELECT public.get_dashboard_statistics() AS payload
)
SELECT
  -- JSON 전체를 출력해 육안으로도 응답을 확인
  payload,
  -- 활동 날짜는 정확히 30개
  jsonb_array_length(payload -> 'activity') AS activity_days,
  -- 캐릭터 배열은 최대 6개
  jsonb_array_length(payload -> 'characters') AS character_count,
  -- 조합 배열은 최대 6개
  jsonb_array_length(payload -> 'combos') AS combo_count,
  -- rising은 JSON object 또는 null
  jsonb_typeof(payload -> 'rising') AS rising_type
-- 위에서 준비한 단일 결과를 검사
FROM result;
```

### 14.3 플레이어 랭킹 RPC 원문

```sql
-- 06. 플레이어 순위 RPC
-- 처음 읽는다면 01-start-here.md, 02-data-flow.md, 03-calculation-design.md를 먼저 읽습니다.
-- Supabase SQL Editor에서 이 파일 전체를 실행합니다.
-- BEGIN~COMMIT은 함수와 권한을 변경하고, 뒤의 SELECT들은 읽기 전용 검증입니다.
-- 함수는 최대 10명의 집계 결과만 반환하며 전체 경기 행은 반환하지 않습니다.
BEGIN;

-- 기존 같은 이름의 순위 함수를 새 정의로 교체합니다.
CREATE OR REPLACE FUNCTION public.get_player_rankings()
-- 반환값은 JSON 배열입니다.
RETURNS jsonb
-- 함수 본문이 SQL 쿼리 하나임을 나타냅니다.
LANGUAGE sql
-- 데이터 변경이 없는 읽기 함수입니다.
STABLE
-- View 소유자 권한으로 읽기 위해 함수 소유자 권한으로 실행합니다.
SECURITY DEFINER
-- 객체 탐색 경로를 고정합니다.
SET search_path = pg_catalog, public
-- $function$ 사이가 함수 본문입니다.
AS $function$
-- View의 두 선수 관점 행을 먼저 정리합니다.
WITH player_rows AS MATERIALIZED (
  SELECT
    -- 이름 양끝 공백 제거
    btrim(player_name) AS player_name,
    -- View가 계산한 플레이어 관점 승리 여부
    is_win,
    -- 누락 ID는 0 처리 후 작은 ID부터 태그 조합 정규화
    least(
      coalesce(player_main_character_id, 0)::integer,
      coalesce(player_sub_character_id, 0)::integer
    ) AS character_a_id,
    greatest(
      coalesce(player_main_character_id, 0)::integer,
      coalesce(player_sub_character_id, 0)::integer
    ) AS character_b_id
  FROM public.v_player_match_rows
  WHERE nullif(btrim(player_name), '') IS NOT NULL
    AND nullif(btrim(opponent_name), '') IS NOT NULL
),
-- 플레이어별 총 경기와 승리를 세고 20전 미만을 제거합니다.
player_totals AS (
  SELECT
    player_name,
    count(*) AS games,
    -- TRUE만 승리로 셉니다.
    count(*) FILTER (WHERE is_win IS TRUE) AS wins
  FROM player_rows
  GROUP BY player_name
  HAVING count(*) >= 20
),
-- 플레이어/태그 조합마다 사용 횟수를 셉니다.
team_totals AS (
  SELECT
    player_name,
    character_a_id,
    character_b_id,
    count(*) AS games
  FROM player_rows
  GROUP BY player_name, character_a_id, character_b_id
),
-- 각 플레이어의 조합을 가장 많이 사용한 순서로 매깁니다.
ranked_teams AS (
  SELECT
    player_name,
    character_a_id,
    character_b_id,
    games,
    row_number() OVER (
      PARTITION BY player_name
      -- 사용 횟수 내림차순, 완전 동률이면 ID 오름차순
      ORDER BY games DESC, character_a_id ASC, character_b_id ASC
    ) AS team_rank
  FROM team_totals
),
-- 대표 조합을 붙이고 승률순 상위 10명을 고릅니다.
ranked_players AS (
  SELECT
    totals.player_name,
    totals.games,
    totals.wins,
    -- integer 나눗셈으로 소수점이 사라지지 않도록 numeric으로 승률 계산
    totals.wins::numeric * 100 / totals.games AS rate,
    teams.character_a_id,
    teams.character_b_id,
    teams.games AS team_games
  FROM player_totals AS totals
  JOIN ranked_teams AS teams
    ON teams.player_name = totals.player_name
   AND teams.team_rank = 1
  ORDER BY
    -- 승률 높은 순. 여기서는 비율 비교라 100을 곱하지 않아도 순서는 같습니다.
    totals.wins::numeric / totals.games DESC,
    totals.games DESC,
    -- 동률 순위의 출력 순서를 고정합니다.
    totals.player_name COLLATE "C" ASC
  LIMIT 10
)
-- 최대 10명 배열을 JSON으로 반환합니다.
SELECT coalesce(
  jsonb_agg(
    jsonb_build_object(
      'name', player_name,
      'games', games,
      'wins', wins,
      'rate', rate,
      -- 대표 조합에는 캐릭터 ID 두 개와 사용 경기 수를 넣습니다.
      'team', jsonb_build_object(
        'ids', jsonb_build_array(character_a_id, character_b_id),
        'games', team_games
      )
    )
    ORDER BY
      wins::numeric / games DESC,
      games DESC,
      player_name COLLATE "C" ASC
  ),
  -- 집계 대상이 하나도 없으면 SQL NULL 대신 빈 JSON 배열
  '[]'::jsonb
)
FROM ranked_players;
$function$;
```

### 14.4 프로필 통계와 이름 검색 RPC 원문

```sql
-- 07. 플레이어 프로필 통계 및 이름 검색 RPC
-- 처음 읽는다면 01-start-here.md, 02-data-flow.md, 03-calculation-design.md를 먼저 읽습니다.
-- Supabase SQL Editor에서 이 파일 전체를 실행합니다.
-- 파일의 BEGIN~COMMIT 구간은 두 RPC 함수/권한을 변경하고 이후 SELECT는 읽기 전용 검증입니다.
-- 첫 함수는 플레이어 프로필 통계, 두 번째 함수는 prefix 이름 검색을 담당합니다.
BEGIN;

-- 기존 프로필 통계 함수를 이 정의로 교체합니다.
CREATE OR REPLACE FUNCTION public.get_player_statistics(
  -- 필수 프로필 이름
  p_player_name text,
  -- 선택 상대 이름. 생략되면 NULL
  p_opponent_name text DEFAULT NULL
)
-- 반환값은 JSON 객체입니다.
RETURNS jsonb
-- 변수와 조건문을 쓸 수 있는 PL/pgSQL 함수입니다.
LANGUAGE plpgsql
-- 데이터를 변경하지 않는 읽기 함수입니다.
STABLE
-- View를 소유자 권한으로 읽습니다.
SECURITY DEFINER
-- 객체 탐색 경로를 고정합니다.
SET search_path = pg_catalog, public
-- $function$ 표식 사이가 함수 본문입니다.
AS $function$
-- 함수 안에서 쓸 지역 변수와 입력값 정리
DECLARE
  -- 플레이어 이름 양끝 공백 제거
  v_player_name text := btrim(p_player_name);
  -- 빈 상대 이름은 선택하지 않은 것과 같은 NULL로 정리
  v_opponent_name text := nullif(btrim(p_opponent_name), '');
  -- 마지막에 만들어 반환할 JSON
  v_result jsonb;
BEGIN
  -- 필수 플레이어 이름이 없으면 잘못된 입력 SQLSTATE 22023으로 명시적 오류
  IF v_player_name IS NULL OR v_player_name = '' THEN
    RAISE EXCEPTION 'Player name must not be empty'
      USING ERRCODE = '22023';
  END IF;

  -- 두 이름 모두 최대 100자를 허용합니다.
  IF length(v_player_name) > 100 OR length(v_opponent_name) > 100 THEN
    RAISE EXCEPTION 'Player names must not exceed 100 characters'
      USING ERRCODE = '22023';
  END IF;

  WITH
  -- 요청 플레이어에게 해당하는 View 행만 가져와 이름과 캐릭터 값을 정규화합니다.
  -- MATERIALIZED는 이 함수의 여러 집계 단계가 같은 범위의 행을 재사용함을 나타냅니다.
  profile_rows AS MATERIALIZED (
    SELECT
      match_id,
      btrim(player_name) AS player_name,
      btrim(opponent_name) AS opponent_name,
      is_win,
      -- NULL 캐릭터 ID는 기존 규칙대로 0으로 보고 integer로 변환합니다.
      coalesce(player_main_character_id, 0)::integer AS main_character_id,
      coalesce(player_sub_character_id, 0)::integer AS sub_character_id,
      map_id,
      start_time,
      end_time,
      played_at
    FROM public.v_player_match_rows
    WHERE lower(btrim(player_name)) = lower(v_player_name)
      -- 상대 이름이 없는 불완전한 행은 집계에서 제외합니다.
      AND nullif(btrim(opponent_name), '') IS NOT NULL
  ),
  -- 프로필 총 경기/승리/시간/마지막 접속을 계산합니다.
  profile_summary AS (
    SELECT
      count(*) AS games,
      -- TRUE 승리만 셉니다.
      count(*) FILTER (WHERE is_win IS TRUE) AS wins,
      -- 시작과 종료가 모두 있고 음수가 아닌 경기 시간만 초 단위로 합칩니다.
      coalesce(
        sum(extract(epoch FROM (end_time - start_time)))
          FILTER (
            WHERE start_time IS NOT NULL
              AND end_time IS NOT NULL
              AND end_time >= start_time
          ),
        0
      ) AS play_seconds,
      -- 종료 시각 우선, 없으면 played_at으로 가장 최근 활동을 정합니다.
      max(coalesce(end_time, played_at)) AS last_access
    FROM profile_rows
  ),
  -- 태그 캐릭터 ID 순서를 정규화해 조합별 경기/승리 수를 계산합니다.
  team_totals AS (
    SELECT
      least(main_character_id, sub_character_id) AS character_a_id,
      greatest(main_character_id, sub_character_id) AS character_b_id,
      count(*) AS games,
      count(*) FILTER (WHERE is_win IS TRUE) AS wins
    FROM profile_rows
    GROUP BY
      least(main_character_id, sub_character_id),
      greatest(main_character_id, sub_character_id)
  ),
  -- 사용 횟수 상위 조합 최대 5개
  top_teams AS (
    SELECT character_a_id, character_b_id, games, wins
    FROM team_totals
    ORDER BY games DESC, character_a_id ASC, character_b_id ASC
    LIMIT 5
  ),
  -- 맵 ID가 있는 기록만 맵별 경기/승리 수로 집계합니다.
  map_totals AS (
    SELECT
      map_id::integer AS map_id,
      count(*) AS games,
      count(*) FILTER (WHERE is_win IS TRUE) AS wins
    FROM profile_rows
    WHERE map_id IS NOT NULL
    GROUP BY map_id
  ),
  -- 경기 수 상위 맵 최대 50개. 동률은 맵 ID 오름차순
  top_maps AS (
    SELECT map_id, games, wins
    FROM map_totals
    ORDER BY games DESC, map_id ASC
    LIMIT 50
  ),
  -- 상대 이름은 lower 키로 묶고 가장 최근 표기를 함께 고릅니다.
  rival_totals AS (
    SELECT
      lower(opponent_name) AS opponent_key,
      (array_agg(opponent_name ORDER BY played_at DESC NULLS LAST, match_id DESC))[1] AS opponent_name,
      count(*) AS games,
      count(*) FILTER (WHERE is_win IS TRUE) AS wins,
      max(coalesce(end_time, played_at)) AS last_played
    FROM profile_rows
    GROUP BY lower(opponent_name)
  ),
  -- 최근에 만난 상대 최대 5명
  recent_rivals AS (
    SELECT opponent_key, opponent_name, games, wins, last_played
    FROM rival_totals
    ORDER BY last_played DESC NULLS LAST, opponent_key COLLATE "C" ASC
    LIMIT 5
  ),
  -- 사용자가 지정한 특정 상대와의 경기 및 승리 수
  selected_rival AS (
    SELECT
      count(*) AS games,
      count(*) FILTER (WHERE is_win IS TRUE) AS wins
    FROM profile_rows
    WHERE v_opponent_name IS NOT NULL
      AND lower(opponent_name) = lower(v_opponent_name)
  )
  -- 각 통계 CTE 결과를 API 계약에 맞는 JSON 객체로 조립합니다.
  SELECT jsonb_build_object(
    'name', v_player_name,
    'summary', jsonb_build_object(
      'games', s.games,
      'wins', s.wins,
      -- 유효한 승리 외 나머지 경기를 패배로 계산합니다.
      'losses', s.games - s.wins,
      'rate', CASE WHEN s.games = 0 THEN 0 ELSE s.wins::numeric * 100 / s.games END,
      'playSeconds', s.play_seconds,
      'lastAccess', s.last_access
    ),
    'teams', coalesce(
      (
        SELECT jsonb_agg(
          jsonb_build_object(
            'ids', jsonb_build_array(t.character_a_id, t.character_b_id),
            'games', t.games,
            'wins', t.wins,
            -- numeric 변환으로 정수 나눗셈을 방지한 승률
            'rate', t.wins::numeric * 100 / t.games
          )
          ORDER BY t.games DESC, t.character_a_id ASC, t.character_b_id ASC
        )
        FROM top_teams AS t
      ),
      '[]'::jsonb
    ),
    'maps', coalesce(
      (
        SELECT jsonb_agg(
          jsonb_build_object(
            'id', m.map_id,
            'games', m.games,
            'wins', m.wins,
            'rate', m.wins::numeric * 100 / m.games
          )
          ORDER BY m.games DESC, m.map_id ASC
        )
        FROM top_maps AS m
      ),
      '[]'::jsonb
    ),
    'rivals', coalesce(
      (
        SELECT jsonb_agg(
          jsonb_build_object(
            'name', r.opponent_name,
            'games', r.games,
            'wins', r.wins,
            'lastPlayed', r.last_played
          )
          ORDER BY r.last_played DESC NULLS LAST, r.opponent_key COLLATE "C" ASC
        )
        FROM recent_rivals AS r
      ),
      '[]'::jsonb
    ),
    -- 상대를 지정하지 않으면 JSON null, 지정하면 상대 전적 객체
    'selectedRival', CASE
      WHEN v_opponent_name IS NULL THEN NULL
      ELSE (
        SELECT jsonb_build_object(
          'name', v_opponent_name,
          'games', sr.games,
          'wins', sr.wins,
          'rate', CASE WHEN sr.games = 0 THEN 0 ELSE sr.wins::numeric * 100 / sr.games END
        )
        FROM selected_rival AS sr
      )
    END
  )
  INTO v_result
  FROM profile_summary AS s;

  RETURN v_result;
END;
$function$;

-- 기존 이름 검색 함수를 이 정의로 교체합니다.
CREATE OR REPLACE FUNCTION public.search_player_names(
  -- 이름의 시작 부분과 비교할 검색어
  p_query text,
  -- 자동완성 결과에서 제외할 현재 플레이어(선택)
  p_exclude_name text DEFAULT NULL
)
-- 반환값은 JSON 배열입니다.
RETURNS jsonb
-- 함수 본문은 SQL 한 문장입니다.
LANGUAGE sql
-- 데이터 변경이 없는 읽기 함수
STABLE
-- 공개 역할에게 View 직접 권한 없이 함수 소유자 권한으로 검색
SECURITY DEFINER
-- 객체 탐색 경로 고정
SET search_path = pg_catalog, public
AS $function$
-- 검색어/제외 이름을 trim하고 소문자로 바꿉니다.
WITH query AS (
  SELECT
    lower(btrim(coalesce(p_query, ''))) AS query_text,
    lower(btrim(coalesce(p_exclude_name, ''))) AS excluded_name
),
-- View에서 표시 가능한 이름을 정리하고 소문자 비교 키를 만듭니다.
name_rows AS MATERIALIZED (
  SELECT
    lower(btrim(player_name)) AS player_key,
    btrim(player_name) AS player_name,
    played_at,
    match_id
  FROM public.v_player_match_rows
  WHERE nullif(btrim(player_name), '') IS NOT NULL
    AND nullif(btrim(opponent_name), '') IS NOT NULL
),
-- 같은 대소문자 무시 키에 여러 표기가 있으면 가장 최근 표기를 하나 고릅니다.
canonical_names AS (
  SELECT DISTINCT ON (player_key)
    player_key,
    player_name
  FROM name_rows
  ORDER BY player_key, played_at DESC NULLS LAST, match_id DESC
),
-- prefix가 일치하고 제외 대상이 아닌 이름을 정렬해 최대 10개로 제한합니다.
results AS (
  SELECT names.player_key, names.player_name
  FROM canonical_names AS names
  CROSS JOIN query AS q
  WHERE q.query_text <> ''
    AND length(q.query_text) <= 100
    -- 이름 시작부분의 길이가 검색어와 일치하는지 비교합니다.
    AND left(names.player_key, char_length(q.query_text)) = q.query_text
    AND (q.excluded_name = '' OR names.player_key <> q.excluded_name)
  ORDER BY names.player_key COLLATE "C" ASC
  LIMIT 10
)
-- 검색 결과를 JSON 배열로 반환하고, 결과가 없으면 빈 배열을 반환합니다.
SELECT coalesce(jsonb_agg(player_name ORDER BY player_key COLLATE "C" ASC), '[]'::jsonb)
FROM results;
$function$;

-- 검증 1: 두 함수 각각 owner/security/search_path/역할별 실행 권한을 확인합니다.
SELECT
  -- 함수 이름
  p.proname AS function_name,
  -- 내부 owner ID를 사람이 읽을 수 있는 역할 이름으로 변환
  pg_get_userbyid(p.proowner) AS owner_name,
  -- true이면 SECURITY DEFINER 설정
  p.prosecdef AS is_security_definer,
  -- 함수에 고정한 search_path 등 실행 설정
  p.proconfig AS function_settings,
  -- anon 역할의 EXECUTE 권한 여부
  has_function_privilege('anon', p.oid, 'EXECUTE') AS anon_can_execute,
  -- authenticated 역할의 EXECUTE 권한 여부
  has_function_privilege('authenticated', p.oid, 'EXECUTE') AS authenticated_can_execute
-- PostgreSQL이 함수 정의/속성을 저장하는 시스템 카탈로그
FROM pg_proc AS p
-- 함수가 public 스키마에 있는지 이름으로 찾기 위해 스키마 카탈로그와 연결
JOIN pg_namespace AS n ON n.oid = p.pronamespace
-- public 스키마의 두 대상 함수만 검사
WHERE n.nspname = 'public'
  AND p.proname IN ('get_player_statistics', 'search_player_names')
-- 함수 이름 순서로 결과 행을 정렬
ORDER BY p.proname;

-- 검증 2: Trakeas 전체 프로필 통계
-- 상대 필터에 NULL을 주어 전체 프로필 집계를 확인
SELECT public.get_player_statistics('Trakeas', NULL) AS profile_payload;
-- 검증 3: Trakeas와 Feira_Practice의 맞대결 요약
-- 두 번째 인자로 상대 이름을 주어 맞대결 집계를 확인
SELECT public.get_player_statistics('Trakeas', 'Feira_Practice') AS head_to_head_payload;
-- 검증 4: tra로 시작하는 이름 중 Trakeas를 제외해 검색
-- 검색어와 제외 이름을 주어 자동완성 RPC를 확인
SELECT public.search_player_names('tra', 'Trakeas') AS name_suggestions;

-- 검증 5: 결과 배열 상한과 승/패 합계가 맞는지 한 행으로 확인합니다.
-- 맞대결 응답을 profile이라는 이름으로 보관
WITH profile AS (
  SELECT public.get_player_statistics('Trakeas', 'Feira_Practice') AS payload
),
-- 검색 결과를 suggestions라는 이름으로 보관
suggestions AS (
  SELECT public.search_player_names('tra', 'Trakeas') AS payload
)
SELECT
  -- 프로필 응답의 조합/맵/최근 상대 배열 길이
  jsonb_array_length(profile.payload -> 'teams') AS team_count,
  jsonb_array_length(profile.payload -> 'maps') AS map_count,
  jsonb_array_length(profile.payload -> 'rivals') AS rival_count,
  -- 상대를 지정했으므로 JSON object여야 합니다.
  jsonb_typeof(profile.payload -> 'selectedRival') AS selected_rival_type,
  -- 테스트 검색어가 제외 이름만 매치하면 0일 수 있으며 이 데이터에서는 정상입니다.
  jsonb_array_length(suggestions.payload) AS suggestion_count,
  coalesce(
    -- summary에서 games, wins, losses 문자열을 정수로 바꿔 합계를 비교
    (profile.payload -> 'summary' ->> 'games')::integer
      = (profile.payload -> 'summary' ->> 'wins')::integer
        + (profile.payload -> 'summary' ->> 'losses')::integer,
    false
    -- 응답 값이 없거나 NULL이어도 검증 결과를 참으로 위장하지 않음
  ) AS summary_totals_match
-- 두 CTE의 각각 한 행을 나란히 놓고 검증 결과 하나를 만듦
FROM profile
CROSS JOIN suggestions;
```

### 14.5 전체·개인 경기 페이지 RPC 원문

```sql
-- 전체 경기 페이지 RPC입니다.
CREATE OR REPLACE FUNCTION public.get_all_matches_by_page(
  p_page integer DEFAULT 1,
  p_page_size integer DEFAULT 10
)
RETURNS jsonb
LANGUAGE plpgsql
STABLE
SECURITY INVOKER
SET search_path = pg_catalog, public
AS $$
DECLARE
  v_total_count bigint;
  v_offset bigint;
  v_matches jsonb;
BEGIN
  IF p_page IS NULL OR p_page < 1 THEN
    RAISE EXCEPTION 'p_page must be greater than or equal to 1'
      USING ERRCODE = '22023';
  END IF;

  IF p_page_size IS NULL OR p_page_size < 1 OR p_page_size > 100 THEN
    RAISE EXCEPTION 'p_page_size must be between 1 and 100'
      USING ERRCODE = '22023';
  END IF;

  v_offset := (p_page::bigint - 1) * p_page_size;

  SELECT count(*)
  INTO v_total_count
  FROM public.matches;

  SELECT coalesce(
    jsonb_agg(page_rows.match_json ORDER BY page_rows.id DESC),
    '[]'::jsonb
  )
  INTO v_matches
  FROM (
    SELECT
      id,
      jsonb_build_object(
        'id', id::text,
        'p1_name', p1_name,
        'p2_name', p2_name,
        'p1_score', p1_score,
        'p2_score', p2_score,
        'winner', winner,
        'start_time', start_time,
        'end_time', end_time,
        'created_at', created_at,
        'p1_main_character_id', p1_main_character_id,
        'p1_sub_character_id', p1_sub_character_id,
        'p2_main_character_id', p2_main_character_id,
        'p2_sub_character_id', p2_sub_character_id,
        'map_id', map_id
      ) AS match_json
    FROM public.matches
    ORDER BY id DESC
    LIMIT p_page_size
    OFFSET v_offset
  ) AS page_rows;

  RETURN jsonb_build_object(
    'page', p_page,
    'page_size', p_page_size,
    'total_count', v_total_count,
    'matches', v_matches
  );
END;
$$;

REVOKE ALL ON FUNCTION public.get_all_matches_by_page(integer, integer) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION public.get_all_matches_by_page(integer, integer)
  TO anon, authenticated;

-- 개인별 대전 기록 페이지 RPC를 생성할 때 실행한 SQL입니다.
CREATE OR REPLACE FUNCTION public.get_player_matches_by_page(
  p_player_name text,
  p_page integer DEFAULT 1,
  p_page_size integer DEFAULT 10,
  p_sort text DEFAULT 'time'
)
RETURNS jsonb
LANGUAGE plpgsql
STABLE
SECURITY INVOKER
SET search_path = pg_catalog, public
AS $$
DECLARE
  v_total_count bigint;
  v_offset bigint;
  v_matches jsonb;
BEGIN
  IF p_player_name IS NULL OR btrim(p_player_name) = '' THEN
    RAISE EXCEPTION 'p_player_name is required'
      USING ERRCODE = '22023';
  END IF;

  IF p_page IS NULL OR p_page < 1 THEN
    RAISE EXCEPTION 'p_page must be greater than or equal to 1'
      USING ERRCODE = '22023';
  END IF;

  IF p_page_size IS NULL OR p_page_size < 1 OR p_page_size > 100 THEN
    RAISE EXCEPTION 'p_page_size must be between 1 and 100'
      USING ERRCODE = '22023';
  END IF;

  IF p_sort IS NULL OR p_sort NOT IN ('time', 'wins', 'losses') THEN
    RAISE EXCEPTION 'p_sort must be time, wins, or losses'
      USING ERRCODE = '22023';
  END IF;

  v_offset := (p_page::bigint - 1) * p_page_size;

  SELECT count(*)
  INTO v_total_count
  FROM public.matches
  WHERE p1_name = p_player_name
     OR p2_name = p_player_name;

  WITH filtered_matches AS (
    SELECT
      id,
      p1_name,
      p2_name,
      p1_score,
      p2_score,
      winner,
      start_time,
      end_time,
      created_at,
      p1_main_character_id,
      p1_sub_character_id,
      p2_main_character_id,
      p2_sub_character_id,
      map_id
    FROM public.matches
    WHERE p1_name = p_player_name
       OR p2_name = p_player_name
  ),
  numbered_matches AS (
    SELECT
      row_number() OVER (ORDER BY id ASC) AS match_number,
      filtered_matches.*
    FROM filtered_matches
  ),
  page_rows AS (
    SELECT
      numbered_matches.*,
      CASE
        WHEN p_sort = 'wins' AND winner = p_player_name THEN 0
        WHEN p_sort = 'losses' AND winner IS DISTINCT FROM p_player_name THEN 0
        ELSE 1
      END AS sort_group
    FROM numbered_matches
    ORDER BY sort_group, id DESC
    LIMIT p_page_size
    OFFSET v_offset
  )
  SELECT coalesce(
    jsonb_agg(
      jsonb_build_object(
        'id', id::text,
        'match_number', match_number,
        'p1_name', p1_name,
        'p2_name', p2_name,
        'p1_score', p1_score,
        'p2_score', p2_score,
        'winner', winner,
        'start_time', start_time,
        'end_time', end_time,
        'created_at', created_at,
        'p1_main_character_id', p1_main_character_id,
        'p1_sub_character_id', p1_sub_character_id,
        'p2_main_character_id', p2_main_character_id,
        'p2_sub_character_id', p2_sub_character_id,
        'map_id', map_id
      )
      ORDER BY sort_group, id DESC
    ),
    '[]'::jsonb
  )
  INTO v_matches
  FROM page_rows;

  RETURN jsonb_build_object(
    'page', p_page,
    'page_size', p_page_size,
    'total_count', v_total_count,
    'matches', v_matches
  );
END;
$$;

REVOKE ALL ON FUNCTION public.get_player_matches_by_page(text, integer, integer, text)
  FROM PUBLIC;

GRANT EXECUTE ON FUNCTION public.get_player_matches_by_page(text, integer, integer, text)
  TO anon, authenticated;

NOTIFY pgrst, 'reload schema';
```

## 15. 데이터 원본·페이지 API·적용과 검증의 세부 계약

### 15.1 Tracker에서 프론트엔드까지 이어지는 경기 데이터 계약

경기 수집 주체는 RPCS3 프로세스의 경기 상태를 읽는 Windows Tracker다. Tracker는 닉네임, 점수, 승자, 양 플레이어 캐릭터 ID, 맵 ID, 경기 시작·종료 시각 등을 Supabase PostgreSQL의 `public.matches`에 등록하고, 프론트엔드는 이를 읽어 화면을 만든다. 프론트엔드 작업은 Tracker 동작이나 DB 스키마를 필요 없이 재설계하는 범위가 아니었다.

| `public.matches` 필드 | 역할 및 화면에서 주의할 점 |
|---|---|
| `id` | 자동 생성되는 `bigint identity primary key`; API JSON에서 문자열로 유지해 JavaScript 정밀도 손실 방지 |
| `p1_name`, `p2_name` | 플레이어 표시명. 공백·빈 값·대소문자 취급은 각 기능의 계약에 맞게 정리 |
| `p1_score`, `p2_score` | 경기 점수 |
| `p1_main_character_id`, `p1_sub_character_id` | P1의 태그 캐릭터 ID 두 칸 |
| `p2_main_character_id`, `p2_sub_character_id` | P2의 태그 캐릭터 ID 두 칸 |
| `map_id` | 맵 ID. `0`은 유효한 Arena이고 `NULL`은 과거 기록에서 발생할 수 있는 미상/누락 값이므로 둘을 합쳐 처리하지 않음 |
| `winner` | 승자 표시명. NULL 또는 이름 비교 의미를 임의로 패배와 동일시하지 않음 |
| `start_time`, `end_time` | Tracker가 기록한 경기 시작·종료 시각. 플레이 시간에는 둘 다 있고 종료가 시작 이후인 경우만 사용 |
| `created_at` | DB 등록 시각. 종료 시각이 없을 때 일부 기록의 표시·집계 fallback에 사용 |

당시 데이터베이스 맥락 문서는 관계형 PostgreSQL을 사용하며 경기 테이블 하나만으로도 관계형 DB라는 점, 플레이어/맵/캐릭터 별도 테이블과 FK를 두지 않는 점, 현재 기능에서 명시적 중복 방지 UNIQUE 제약이 핵심 구조가 아니라는 점을 기록했다. 캐릭터와 맵 ID는 프론트엔드의 이름·이미지 매핑을 통해 표시한다. 이 구분 덕분에 NULL 맵 108건을 Arena로 바꾸거나 알 수 없는 승자를 패배로 세는 잘못된 보정을 피할 수 있었다.

수집 쪽은 RPCS3에서 플레이하는 경기 결과를 감지하는 Windows Tracker이며, 당시 인수인계 자료는 Python 3.12와 Nuitka로 EXE를 빌드한다고 기록했다. 이 프론트엔드 발전 작업에서 Tracker 메모리 주소나 감지 로직을 수정하지 않고, 이 단계를 별도 데이터 생산자로 취급했다. 프론트엔드는 서버가 저장한 기록을 소비하고 표시한다.

초기 고수준 구현 계획에는 30초 이내 동일 P1/P2·점수 기록을 중앙 DB에서 병합하는 중복 제거가 제안돼 있었다. 이것은 계획 문서에 기재된 안이지, 현재 운영 DB에 해당 UNIQUE/Upsert 규칙이 실제 적용됐다는 증거로 취급하지 않는다. 프론트엔드는 실제 원본 행의 ID와 응답 계약으로 기록을 다룬다.

공개 조회·삽입 권한의 상세는 Supabase RLS와 당시 운영 설정에 따른다. 프론트엔드는 경기 기록 수정/삭제 기능을 임의로 만들지 않고, 닉네임과 DB 응답은 외부 입력으로 취급하며, 사용자 이름을 HTML 문자열로 직접 삽입하지 않고 React 텍스트 렌더링을 사용한다. 공개 anon 키와 service-role 키는 서로 다르며, service-role 키를 클라이언트 번들에 넣지 않는다.

### 15.2 경기 페이지 API의 입력·정렬·검증 원문

#### 전체 경기 페이지

- 브라우저 URL은 `/api/matches?page=N`이다.
- `page`를 생략하면 1을 사용하고, 그 외 값은 양의 정수인지 검사한다.
- 서버는 클라이언트가 지정하는 임의의 page size를 받지 않고 DB RPC에 `p_page_size = 10`을 전달한다.
- DB는 `id DESC` 순서에서 `(page - 1) × page_size`만큼 건너뛰고 현재 행만 돌려준다.
- 전체 건수 `total_count`는 별도로 세어 페이지 수를 계산한다.
- API의 응답 `page`, `page_size`가 요청 계약과 일치하는지 확인한다.
- 전체 목록의 화면 번호는 `total_count - (page - 1) × page_size - index`로 계산하며 실제 DB ID와 혼동하지 않는다.

#### 개인 경기 페이지

- 브라우저 URL은 `/api/matches/player?name=...&page=N&sort=...`이다.
- `name`은 양끝 공백을 제거한 뒤 비어 있지 않아야 한다.
- `page`는 생략 시 1이며 양의 정수여야 한다.
- `sort`는 `time`, `wins`, `losses` 중 하나만 허용하고 생략 시 `time`이다.
- 페이지 크기는 10으로 고정한다.
- 각 플레이어의 시간순 위치를 `row_number() OVER (ORDER BY id ASC)`로 부여해 `match_number`로 반환한다.
- 정렬은 시간순에서 최신 ID 우선, 승리 우선/패배 우선은 해당 그룹 먼저 배치한 뒤 각 그룹 안에서 최신 ID 우선이다.
- 승리 정렬에서 `winner = p_player_name`, 패배 정렬에서 `winner IS DISTINCT FROM p_player_name`을 사용하므로 NULL winner도 해당 predicate상 패배 그룹에 들어간다는 SQL 의미를 보존한다.
- 총건수와 페이지 행은 동일한 플레이어 필터(`p1_name = name OR p2_name = name`)를 사용한다.

#### 공통 페이지 응답 파서

`normalizeMatchPage(value, requireMatchNumbers)`는 외부 값을 `unknown`으로 받아 다음 순서로 검증한다.

1. 최상위 값이 객체인지 검사한다.
2. `page`와 `page_size`가 안전한 양의 정수인지 검사한다.
3. `total_count`가 안전한 0 이상의 정수인지 검사한다.
4. `matches`가 배열인지 검사한다.
5. 각 경기 항목이 객체인지 검사한다.
6. 각 행을 `normalizeMatch`로 변환하고 실패 행을 묵살해 배열에서 빼지 않는다.
7. 반환 행 수가 `page_size`를 넘지 않는지 검사한다.
8. 개인 목록 모드에서는 모든 `match_number`가 안전한 양의 정수인지 검사하며 번호가 없으면 오류를 낸다.
9. DB bigint ID는 문자열로 보존하고 `p1_name`, `start_time` 등의 DB 이름을 앱 내부 `p1Name`, `startAt` 형태로 변환한다.

성공한 빈 페이지와 네트워크/API 오류를 합치지 않는다. Route Handler는 입력 오류 HTTP 400, Supabase 환경 설정 부재 HTTP 503, RPC 오류나 응답 계약 오류 HTTP 502를 반환하며 응답은 `Cache-Control: no-store`다. 캐시 없는 API 실패는 UI의 명시적 오류가 되고, 유효 캐시가 있는 갱신 실패는 이전 데이터와 갱신 오류를 함께 유지한다.

#### 동작 예와 전체성 검사

172건에 page size 10이면 전체 페이지 수는 `ceil(172 / 10) = 18`이고 마지막 페이지에는 두 행이 있다. 완전성 확인은 첫 페이지가 정상이라는 사실만으로 끝나지 않는다. `total_count`에 따라 끝 페이지까지 불러온 뒤 반환 행 수와 고유 경기 ID 수가 모두 172인지 확인해야 한다. 실제 기록된 2026-10-01 검사에서 이 조건을 확인했다. 이 표본은 1,000건 초과 데이터 스트레스 테스트가 아니다.

테스트는 페이지 JSON 파서, 문자열 ID 보존, 잘못된 행의 명시적 거부, 잘못된 `total_count`, 개인 번호 검증, 페이지 크기 계약을 다룬다. 전체·개인 Hook은 페이지/프로필/정렬 변경 시 이전 브라우저 요청을 취소하고 오류를 기록한다. 과거 `useMatches()`·`usePlayerMatches()` 호환 함수는 빈 결과를 반환하는 레거시 entry일 뿐 전체 행을 가져오는 요청을 하지 않으며 현재 페이지 화면은 전용 페이지 Hook을 사용한다.

### 15.3 DB 적용 순서와 권한·응답 검증 절차

당시 기록된 적용 순서는 선수 관점 View가 존재하고 직접 조회 권한이 차단돼 있는지 확인한 뒤 통계 함수를 순차적으로 설치하는 방식이었다.

1. `get_dashboard_statistics()` 정의와 반환 계약 적용.
2. `get_player_rankings()` 정의와 반환 계약 적용.
3. `get_player_statistics()` 및 `search_player_names()` 정의 적용.
4. 전체·개인 경기 목록의 `get_all_matches_by_page()`와 `get_player_matches_by_page()` 정의/권한 적용.
5. 각 통계 파일의 카탈로그 조회로 함수 소유자가 `postgres`인지, `SECURITY DEFINER`, `search_path = pg_catalog, public`, anon/authenticated EXECUTE 권한이 예상과 맞는지 확인.
6. View는 anon/authenticated 직접 SELECT가 거부되는지 확인.
7. API 경로에서 HTTP status, JSON 응답과 parser 결과를 확인.
8. DB JSON 응답 길이가 캐릭터 6, 조합 6, 랭킹 10, 프로필 팀 5/맵 50/상대 5/선택 상대 1, 활동 30의 계약을 위반하지 않는지 확인.
9. 테스트 데이터 결과에서 `games = wins + losses`와 각 화면의 필수 필드를 확인.
10. 브라우저에서 대시보드, 순위, 프로필, 검색과 전체/개인 기록을 확인.

각 함수 SQL의 `BEGIN`과 `COMMIT` 사이는 DB 정의와 권한의 transaction이다. COMMIT 후의 SELECT는 읽기 검증이다. 이는 DB transaction의 원자성을 보장하지만, 이미 적용된 DB에서 해당 파일을 검토 없이 재실행해도 된다는 뜻은 아니다. View 생성/권한 차단, 역할 존재, 운영 DB 정책 및 RPC 서명은 대상 환경에 따라 먼저 확인해야 한다. SQL 배포 결과를 바꾸면 애플리케이션 호출부·parser·문서·테스트를 같은 변경에서 동기화한다.

통계 RPC는 `SECURITY DEFINER`이며 소유자를 `postgres`로 설정하고 `search_path`를 `pg_catalog, public`으로 고정했다. 호출자가 View 직접 SELECT 권한이 없어도 소유자 권한 함수로 정해진 집계를 실행할 수 있게 하기 위한 설계다. 당시 확인 환경에서 `matches`의 FORCE RLS는 비활성으로 기록됐으므로 postgres 소유 함수가 일반 역할의 RLS 조건으로 제한되지 않을 수 있다. 따라서 anon/authenticated에게 실행권한을 주는 각 함수는 반환 JSON의 범위와 개인정보 공개 적합성을 검토해야 한다. 현재 서비스의 공개 경기 전제에서 설정된 권한을 향후 비공개 경기·테넌트·인증 데이터 도입 후에도 그대로 유지해도 된다고 가정하면 안 된다. 반면 경기 페이지 함수는 SQL 원문처럼 `SECURITY INVOKER`이며 권한 모델이 다르다.

기록된 표본 확인은 View의 172경기→344 관점 행, NULL 승자 판정 0건, anon/authenticated 직접 View 조회 거부, 순위 3명 모두 20전 이상, Trakeas 프로필 30전/17승/13패, 팀 4개·맵 22개·상대 1명, `Fei` prefix가 `Feira_Practice`를 반환한 결과를 포함한다. `tra`에서 Trakeas를 제외한 빈 후보 결과도 정상 동작으로 확인했다.

### 15.4 통계 전체 표본 대조의 추가 데이터 세부

172경기 전체 표본을 기존 JavaScript 계산과 새 DB 집계 간에 대조했을 때 다음을 함께 기록했다.

- 캐릭터 ID `NULL` 0건 및 등록되지 않은 ID 0건. 명시적 ID 0은 기존 매핑 규칙에 따라 폴로 표시됐다.
- 맵 ID 미등록 0건, `map_id IS NULL` 108건. 두 집계 모두 NULL 맵을 맵별 통계에서 제외했다.
- 누락 또는 파싱할 수 없는 경기 시각 0건.
- 승패 NULL 0건.
- 캐릭터 픽 횟수와 승률은 일치했으며 ID 6/62 동률의 화면 순서만 tie-break 기준 차이가 있었다.
- 변경 전 기준으로 대시보드의 경기/플레이어/rolling 24시간 수, 태그 조합 수치, KST 활동과 급상승 구간 결과는 당시 JavaScript 계산과 일치했다.

날짜 기준을 KST로 통일했기 때문에 KST 밖 사용자의 예전 브라우저-local 계산과 달력 날짜 경계는 다를 수 있다. 이는 모든 사이트 방문자가 같은 경기를 같은 날짜로 보는 일관성 선택이다. 과거 통계와의 비교 때는 분모·타임존·승패 NULL·맵 NULL 같은 규칙을 먼저 동일하게 맞춰야 한다.

SQL의 NULL 승패 의미도 보존해야 한다. View의 `lower(winner) = lower(player_name)`은 `winner`가 NULL이면 `is_win`도 NULL로 남긴다. `count(*) FILTER (WHERE is_win IS TRUE)`는 이 행을 승리로 세지 않으며, 프로필 JSON의 `losses = games - wins`와 개인 목록의 `winner IS DISTINCT FROM p_player_name` 정렬은 NULL 결과를 패배 쪽으로 포함한다. 당시 표본은 NULL winner가 0건이어서 실제 대조에는 영향이 없었지만, 향후 데이터에 미판정 경기가 들어오면 이 구현은 “승리·패배·미판정”을 3상태로 보존하지 않는다는 것을 명확히 해야 한다. 미판정 경기가 실제로 발생할 경우 통계 정의를 변경할지는 도메인 결정을 거쳐야 하며 이 과거 기록만으로 임의 변경하지 않는다.

### 15.5 API 왕복과 DB 함수 실행 관측값 원기록

2026-09-30 로컬 production build의 Next.js API를 한 번씩 순차 호출한 결과는 다음과 같다. 이 값은 DB 실행 시간과 다른 앱+네트워크 경로의 단일 관측이다.

| API | 한 번 관측한 시간 |
|---|---:|
| 대시보드 | 2,515 ms |
| 플레이어 순위 | 70 ms |
| 프로필 통계 | 73 ms |
| 이름 검색 | 54 ms |

2026-10-01 Supabase SQL Editor에서 사용자가 네 RPC를 `EXPLAIN (ANALYZE, BUFFERS, TIMING ON)`으로 각각 한 번 실행해 전달한 기록:

| RPC | Planning Time | Execution Time | Shared buffer hit |
|---|---:|---:|---:|
| 대시보드 | 0.047 ms | 18.977 ms | 1,227 |
| 랭킹 | 0.045 ms | 4.040 ms | 835 |
| 프로필 | 0.089 ms | 5.382 ms | 1,040 |
| 이름 검색 | 0.044 ms | 3.405 ms | 607 |

EXPLAIN 출력은 바깥 함수 호출 statement의 `Result` 노드를 보여 줬으며 함수 안의 개별 SQL 실행계획을 펼치지 않았다. 따라서 해당 execution time은 내부의 전체 함수 각 구문을 분해한 상세 프로파일이 아니다. 네 API 호출과 네 SQL 결과는 호출 환경과 대상이 다르며 서로 직접 비교할 수 없다. 표본 172경기에서 각 한 번 측정했을 뿐 반복 평균·동시 사용자 부하·수만 건 계획·운영 서버 성능 보증은 아니다.

캐시 전후 측정 역시 동일한 로컬 데이터 원본과 브라우저, 환경 변수를 사용하려 했지만 최적화 전/후 `.next` 산출물은 같은 빌드가 아니었다. 당시 최적화 전 빌드는 2026-09-30, 이후 빌드는 2026-10-02 생성이며 `BUILD_ID`가 달랐다. 최적화 전 폴더의 `ProfileView.tsx`와 `useProfileStatistics.ts`에는 미커밋 변경도 존재했다. 이 차이는 비교 교란요인이므로 404ms 대 407.5ms의 중앙값 차이나 590ms 프로필 직접 방문을 엄밀한 통제 성능 차이라고 해석하면 안 된다.

구현 후 기능 테스트에서는 실제 IndexedDB 저장, API 차단으로 오프라인 재검증 실패를 재현했을 때 프로필 통계와 경기 기록이 유지되고 오류가 보이는 점, 연결 복구 뒤 정상 재요청, 닉네임 자동완성 후보 선택/이동을 확인했다. 오래된 캐시 교체 시 데이터 영역 강조와 카운터 동작을 확인했으며 390px 모바일·standalone PWA에서 프로필 경기 목록의 가로 넘침이 없는지 확인했다. 다만 새 경기 응답을 실제 앱에 주입해 카드 등장 모션 전체를 종단 간으로 검증한 것은 아니고, 모든 화면의 시각 회귀 전수 검사를 수행한 것도 아니다.

캐시 갱신 효과의 당시 기록은 오래된 캐시를 새 응답이 바꿀 때 데이터 영역을 약 1초 강조하고, 통계 숫자를 약 0.65초 카운트업/다운하며, 새 경기 ID가 추가된 카드만 약 1.2초 등장·강조시키는 동작이다. 기존 경기 업데이트·페이지 이동·최초 로드에는 새 카드 강조를 주지 않는다. 기존 캐시 갱신 모션은 사용자 요청에 따라 운영체제 reduced-motion 설정과 무관하게 재생하도록 기록되었다. 이는 리팩터 계획 당시의 일반 UI 모션에서 `prefers-reduced-motion`을 존중하자는 접근성 목표와 범위가 다른 뒤 단계 결정이므로, 두 요구를 하나의 합의였던 것처럼 합치지 않는다.

### 15.6 SQL 및 데이터 흐름을 읽기 위한 용어 보충

| SQL 용어 | 이 프로젝트에서의 의미 |
|---|---|
| row / 행 | `matches`의 원본 경기 또는 View의 플레이어 관점 경기 한 줄 |
| RPC | 이름과 인자로 PostgreSQL 함수를 호출하는 데이터베이스 API 경로 |
| View | 반복 가능한 SELECT 정의. 일반 View는 집계 결과를 저장한 물리 캐시가 아님 |
| CTE (`WITH`) | 긴 쿼리를 이름 붙은 계산 단계로 나눈 부분 |
| `MATERIALIZED` | 해당 쿼리에서 CTE 중간 결과를 만들고 재사용하도록 표시 |
| `btrim(x)` | 문자열 앞뒤 공백 제거 |
| `coalesce(a, b)` | 왼쪽부터 첫 non-NULL 값을 반환 |
| `nullif(a, b)` | 두 값이 같으면 NULL, 다르면 첫 값을 반환 |
| `FILTER (WHERE ...)` | 조건을 만족하는 행만 집계 함수에 포함 |
| `::integer`, `::numeric`, `::date` | 정수, 소수 계산, 날짜로 명시 변환 |
| `->`, `->>` | JSON 값을 JSON 타입 또는 text로 추출 |
| `ASC`, `DESC` | 오름차순·내림차순 |
| `LIMIT` | 해당 SELECT 결과 최대 행 수. 앞선 전체 집계 대상 수와는 다름 |
| `[start, end)` | start 포함·end 제외의 시간 범위 |
| `COLLATE "C"` | 데이터베이스 locale에 덜 의존하는 고정 문자 정렬 |
| `SECURITY DEFINER` / `INVOKER` | 함수 소유자 권한 / 호출자 권한으로 실행하는 옵션 |
| `search_path` | 스키마 이름을 생략한 DB 객체를 찾는 순서. 보안 함수에서는 고정 필요 |
| `REVOKE` / `GRANT EXECUTE` | 기본 권한 회수 후 특정 역할의 함수 실행만 허용 |
| PostgREST schema reload notification | 함수/스키마 변경 뒤 PostgREST가 API 스키마 캐시를 다시 읽도록 알림 |

### 15.7 2026-10-03 대시보드의 ‘오늘 대전’ 기준 변경

기존 대시보드 카드는 `최근 24시간 대전`이라는 이름으로 현재 시각부터 24시간을 거슬러 올라가는 rolling window를 표시했다. 사용자가 의도한 “오늘 몇 경기가 있었나”라는 의미에 맞춰 집계와 표시 계약을 한국 시간 기준의 오늘로 변경했다.

- 기준 구간은 KST 오늘 00:00 이상, 통계 조회 시각 이하이다. 자정 직전 기록과 조회 시각 이후의 미래 경기 시각은 집계에서 제외한다.
- 홈 카드 문구는 `오늘 대전`, 보조 문구는 `한국 시간 기준`이다.
- 대시보드 응답 필드는 `recentDayMatches`에서 `todayMatches`로 변경됐다. 화면, 응답 파서, 기존 순수 계산 함수와 테스트도 같은 계약으로 맞췄다.
- 경계 테스트는 KST 자정 직전, 자정 정각, 현재 시각, 미래 시각의 경기 포함 여부를 확인한다. 대시보드 및 계산 관련 Vitest 11개, 변경 파일 ESLint, TypeScript 검사가 통과했다.
- 저장소의 최신 DB 정의는 [`docs/statistics/05-dashboard-statistics.sql`](../../ttt2_web_v2/docs/statistics/05-dashboard-statistics.sql)이다. 운영 DB는 SQL Editor에서 이 정의를 적용해야 새 `todayMatches` 필드를 반환한다.
- 이 기록 작성 시점에는 사용자가 SQL을 Supabase에서 실행했는지와 앱의 운영 배포 여부를 확인하지 못했다. 따라서 코드·테스트 변경은 확인됐지만 운영 DB와 배포 사이트에 적용 완료됐다고 간주하지 않는다.
